# ATC-0029 design: release pipeline

Task: ATC-0029 (`.atc/tasks/ATC-0029.yaml`), base 28d9079. The Owner's rulings
in the record bind this design: draft Releases only, no PyPI publish, no
governance change, no version bump.

## 1. Workflow shape

One workflow, `.github/workflows/validate.yml`, keeps its three validation
jobs and gains a fourth job, `draft-release`.

Triggers:

    on:
      push:
        tags: ['v*']
      workflow_dispatch:
        inputs:
          tag:
            description: Release tag to validate and draft (empty validates the selected branch only)
            required: false
            default: ''

- A plain dispatch (`tag` empty) behaves as today: the three validation jobs
  on the dispatched branch, no release.
- A tag push `v*` runs the validation jobs on the tag, then `draft-release`.
- A dispatch with `tag: v0.3.0` (or `v0.4.0`) runs the validation jobs and
  `draft-release` on that tag's tree. This is how the existing tags get their
  Releases.

The release tag is `inputs.tag || github.ref_name`; the release runs when
`github.ref_type == 'tag' || inputs.tag`.

### Building from the tag's tree

Every job's `actions/checkout` gets `ref: ${{ inputs.tag || github.ref }}`,
so a dispatch on `v0.3.0` validates and builds the tree at `v0.3.0`, never
`main`. The steps themselves come from the workflow file at the ref the run
was started from (`main` for a dispatch), applied to the tag's tree. For
v0.3.0 and v0.4.0 that is the same file: `validate.yml` has not changed since
v0.3.0 (`git diff v0.3.0 HEAD -- .github/workflows/validate.yml` is empty),
and the scripts those steps call exist in both trees. If a later workflow
change outgrows an old tree, the dispatch fails in validation and drafts
nothing.

### Concurrency

    concurrency:
      group: ${{ github.workflow }}-${{ inputs.tag && format('refs/tags/{0}', inputs.tag) || github.ref }}
      cancel-in-progress: ${{ github.ref_type != 'tag' && !inputs.tag }}

Plain validation keeps "newest run per branch wins". A release run is keyed by
its tag ref, `refs/tags/<tag>`, whether a tag push or a dispatch naming the
tag started it. Dispatches for v0.3.0 and v0.4.0 run side by side; a tag push
and a dispatch for one tag run one after the other, so the second finds the
first one's draft and refuses (§ 6). A release run is never cancelled halfway
through creating a draft.

### `draft-release` job

`needs: [schemas, shell-install, python-adapter]`, `runs-on: ubuntu-latest`,
checkout with `fetch-depth: 0` (it needs the previous tag and the log). Steps:

1. **Guards**, each stopping the job with a message:
   - the tag matches `^v[0-9]+\.[0-9]+\.[0-9]+$` (a `v*` push such as
     `v1-test` validates but drafts nothing);
   - `refs/tags/<tag>` exists, is the checked-out commit, and is an
     ancestor of `origin/main` (a Release only for an integrated revision);
   - the tag equals `v` + `version` in `adapters/python/pyproject.toml` at
     that tree;
   - no Release exists for the tag (see § 6).
2. **Versions**: atc from `adapters/python/pyproject.toml`, atc-testkit from
   `__version__` in `adapters/python/atc-testkit/src/atc_testkit/__init__.py`.
3. **Build** the assets of § 2 into `$RUNNER_TEMP/dist`.
4. **Notes** as § 4 says, into `$RUNNER_TEMP/notes.md` (not uploaded).
5. **Create** the draft:
   `gh release create <tag> --draft --verify-tag --title "atc <v> (atc-testkit <tv>)" --notes-file <notes> <assets>`
   with `GH_TOKEN: ${{ github.token }}`.

Every step of the job is inline in the workflow, so a dispatch on an old tag
needs nothing the old tree lacks beyond `scripts/build_testkit_release.py`
(§ 2).

## 2. Assets

| Asset | Built by |
| --- | --- |
| `atc-conformance-<v>.tar.gz` | `git archive --format=tar.gz --prefix=atc-conformance-<v>/ <tag> shared/conformance` |
| `atc_testkit-<tv>-py3-none-any.whl` | `scripts/build_testkit_release.py --output-dir <dist>` from the tag's `adapters/python` |
| `atc-testkit.json` | the same builder: the consumer release record (name, version, source digest, wheel digest) |
| `SHA256SUMS` | `sha256sum` over the three files above, run inside `<dist>` so lines carry bare file names (`sha256sum -c SHA256SUMS` works after download) |

The wheel comes from the repository's own builder (`adapters/python/atc-testkit/README.md`
§ Distribution), present in both v0.3.0 and v0.4.0: it builds from a clean
snapshot of the sources with fixed archive timestamps and checks the whole
wheel payload against that snapshot. The job checks the wheel's file name
carries the testkit version it read in step 2. The conformance archive comes
from the Git object, not the working tree, so its content is exactly the
tag's.

The atc-testkit build backend is `setuptools>=68`, unpinned, so a rebuild can
use a newer setuptools; the wheel's contents are the tag's sources either way.
Pinning it is a testkit change and stays out of this task.

## 3. Tag and title

The Release sits on the existing tag `v<atc version>`; the workflow creates no
tag (`--verify-tag` refuses a missing one). The title names both versions in
the form the tag annotations already use: `atc 0.4.0 (atc-testkit 0.11.0)`.
The body's first line repeats it.

## 4. Release notes

No release notes file exists in the repo. The notes already written for each
release are the bodies of the `chore(release): atc …` commits
(`936d14a` for 0.4.0, `43740eb` for 0.3.0). The body is generated from Git,
with no CHANGELOG file:

    atc <v> (atc-testkit <tv>)

    <body of the newest commit in <prev>..<tag> whose subject starts "chore(release): atc ">

    ## Tasks
    - ATC-NNNN: <scope of each .atc/tasks/ATC-*.yaml added in <prev>..<tag>>

    ## Assets
    Verify with: sha256sum -c SHA256SUMS

`<prev>` is `git describe --tags --abbrev=0 --match 'v[0-9]*' <tag>^`. When
that finds no earlier tag, or `<tag>` is the root commit (v0.1.0 is), the
range is the tag's whole history. With no matching release commit, the
section is the tag annotation's message. The step runs in the adapter's locked
environment and reads each record's `task_id` and `scope` with PyYAML.

The draft is where the Owner edits before publishing. Two known gaps for the
existing tags: v0.3.0's release commit body speaks of atc-testkit 0.10.1 while
the tag ships 0.10.2, and the 0.10.1 notes sit in a separate
`chore(release): atc-testkit` commit the rule does not pick up.

## 5. Permissions

Top level `permissions: contents: read`, so the validation jobs get a
read-only token. `draft-release` alone sets `permissions: contents: write`,
the minimum for `gh release create` and asset upload. No other scope, no
secrets beyond `github.token`.

## 6. Re-runs

A run stops when a Release (draft or published) already exists for the tag.
To redo a draft the Owner deletes it and dispatches again; the workflow never
edits or deletes a Release (Owner ruling 11-13). The lookup lists the
repository's Releases, drafts included, since the by-tag endpoint omits
drafts.
