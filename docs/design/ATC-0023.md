# ATC-0023 設計：測試預設全速、安全地用滿這台主機

Task: ATC-0023（`.atc/tasks/ATC-0023.yaml`）。狀態：design，等 Owner 裁決 §10 後才實作。
規格依據：`docs/TESTKIT.md` § Stages、§ Host worker budget、§ Commands；
ATC-0018 的 Owner 裁決（O2、O3、O4）記在 `.atc/tasks/ATC-0018.yaml` 的 `decisions`。

## 1. 問題

在這台 24 logical CPU / 32 GB 的主機上：

- `atc test run` 沒帶 `-n` 時取 1 個 token、序列執行（`testrun._worker_request`）。全 suite 要 835 s（§5）。
- 不帶 flag 的 default 是 `min(MAX_WORKERS 8, logical CPUs, memory ceiling)`（`stages.default_workers`、`resolve_workers`），但 pool 有 18 個 token。
- memory ceiling 用的是沒量過的 `PER_WORKER_MIB` 1024 加 `RESERVE` 1 GiB（`workers.py`）。實測每個 worker 約 84 MiB（§4），高估約 12 倍。available 低的時候，default 會被切到 1。
- pytest 的進度只寫進 `~/.atc/tmp/<scratch>/runs/<ts>-<label>.log`。agent 的 foreground call 要等結束才有輸出。verifier 的 stdout 要等它結束才寫進 `<candidate>.verify.log`，所以 worker 為什麼被切，跑的當下沒有人看得到。
- 重開機前，kernel nonpaged pool 洩漏到 18.5 GB（平常約 1 GB），available 因此長時間偏低，沒有任何工具指出原因。
- writer 的 `--select` 涵蓋幾乎整個 suite 時，跟 reviewer 的 `atc verify` 重複跑（ATC-0022 選了約 49 個 test file，浪費約 8 分鐘）。

## 2. 案例：ATC-0022 的 verifier 只用 1 個 worker

現象：pool row `"label": "verifier db460536a650", "stage": "parallel", "want": 1, "floor": 1, "tokens": [1]`，時間 2026-11-11 23:25（+0800）。parallel stage log
`~/.atc/tmp/systmp/w4a704f/pytest-parallel.log` 的 header 寫 `-n 1`，basetemp 底下只有 `popen-gw0`。

逐一排除：

| 來源 | 結論 | 依據 |
| --- | --- | --- |
| `ATC_TEST_WORKERS_HELD`（nesting） | 排除 | `verifier.main` 的 `resolve_workers` 和 `open_budget` 讀同一個 `environ`。HELD 有設的話 `open_budget` 回 `Budget(None)`，不會留下 pool row，但 row 存在。`git_integrate._verify_candidate` 也不設 HELD。 |
| host file `test_workers` | 排除 | `~/.atc/config.toml` 不存在。 |
| flag | 排除 | verifier 不收 flag。 |
| memory ceiling | **成因** | 唯一能讓 default 變成 1 的路徑：`memory_cap = max(1, (available − 1 GiB) // 1 GiB)`。 |

用 worktree 的程式碼重現 `resolve_workers`，把 `available_memory` 固定成不同的值，host file 不存在：

| available | 結果 |
| --- | --- |
| 2.1 GiB | `workers: 1 (default 8, memory ceiling: 2.1 GiB available)`，floor 1 |
| 2.9 GiB | `workers: 1 (…)`，floor 1 |
| 3.0 GiB | `workers: 2 (…)`，floor 2 |
| 5.5 GiB | `workers: 4 (…)`，floor 2 |
| 19.0 GiB | `workers: 8 (default)`，floor 2 |

available 低於 3 GiB 時就是 1。重開機前 nonpaged pool 洩漏到 18.5 GB，available 長時間在 2 GB 上下，跟 coordinator 的推測（約 2 GB 可用，cap = 1）一致。verifier 被中途停掉，沒有留下 `<candidate>.verify.log`，所以當下的確切值無法回溯；但程式路徑只有這一條。

程式上有兩個缺陷，讓一次低讀數決定了整個 stage：

1. **resolve 時間太早**：`verifier.main` 在 static checks（workspace、policies、diff check）之前就呼叫 `resolve_workers`。parallel stage 開跑時用的是更早的記憶體讀數。
2. **記憶體重複切、floor 跟著塌**：`resolve_workers` 先依記憶體把 count 切成 1，`Workers.floor()` 再取 `min(FLOOR, count)` = 1。`Budget.acquire` 自己在發 token 時本來就會重讀記憶體（`_memory_room`，還把 60 秒內剛 grant 的 run 算進去），但它拿到的 want 已經是 1，就算記憶體回升也只能給 1。

修正併入 §3.1（記憶體只在 `acquire` 當下判斷一次，floor 固定是 `FLOOR`）、§3.2（每 worker 成本用實測值）、§3.3（開始時印出原因，§3.6 由 `atc doctor` 指出 nonpaged pool 洩漏）。

## 3. 設計

### 3.1 沒帶 `-n` 的 default：pool 與記憶體允許的上限，elastic

**want**：

- 在 pool 內（本機，`CI` 沒設、沒有 HELD、`test_worker_pool` ≠ 0）：want = pool size（這台主機是 18）。記憶體不在 resolve 時切，只在 `Budget.acquire` 依當下的 `_memory_room` 切。
- 在 pool 外（CI、`test_worker_pool = 0`）：want = `min(logical CPUs, memory ceiling)`。沒有 acquire 可以延後判斷，所以在 resolve 時切。
- 移除 default 的 `MAX_WORKERS` 8 上限。`MAX_WORKERS` 只保留一個用途：flag 可以超賣小 runner 的上限（`most_flag_workers`）。

**elastic grant**（ATC-0018 的行為，保留）：floor 2，拿當下空著的 token，最多到 want 和 memory room。不等湊滿 want，所以同時跑的 run 會分著用，不會排隊。floor 固定是 `FLOOR`，不再跟著被記憶體切小的 count 變成 1（§2 缺陷 2）。memory room 低於 floor 時，`acquire` 照現行規則仍給 floor（`max(floor, room)`）；2 個 worker 實測約 0.5 GiB（§4），成本很小。

**`-n N` flag**：維持固定需求（ATC-0018 O2 與 2026-11-11 的裁決）。依記憶體切、依 pool size 切、需要時改寫成實際拿到的數量，floor = want。

**小 run 的上限（O4）**：只選了幾個 test 卻拿 18 個 token，會擋住別的 run，多出來的 worker 也只是空等。`atc test run` 在取 token 之前先跑一次 `pytest --collect-only -q`，want 再加一個上限 `ceil(items / ITEMS_PER_WORKER)`，`ITEMS_PER_WORKER` = 8，下限 `FLOOR`。全 suite 1851 個 test collect 只要 1.44 s（實測），跟 run 本身比可以忽略。stages runner（gate、verifier、CI runner）已經有 test paths，同樣套用。

**各入口的 default**：

| 入口 | 現在 | 提案 |
| --- | --- | --- |
| `atc test run`，沒有 `-n` | 1 個 token，序列 | 上面的 default（等同今天的 `-n auto`，但 want 是 pool size） |
| `atc test run -n 0` | 1 個 token，序列 | 不變：明確要求序列 |
| `atc test run -n auto` / `logical` | default 8，floor 2 | 跟沒帶 `-n` 一樣 |
| gate `--run`、CI runner `--stages` | `default_workers()` | 同上的 default；`--workers N` 仍是 flag |
| verifier（`atc integrate`、`atc verify`） | resolve 在 static checks 之前 | 改在 parallel stage 的 `acquire` 當下決定（§2）；仍然沒有 flag，host file `test_workers` 仍是它唯一的覆寫方式 |
| `atc test mutants` | 每個 mutant 1 個 token | 不變：mutant 本來就序列跑 |

`atc integrate` 已經用 `integration.lock` 序列化，verifier 在 pool 裡跟其他 run 一樣分配，`ATC_WORKER_MAX_WAIT` 的規則不變。

### 3.2 每個 worker 的記憶體：實測校正，並依專案自動記錄

實測（§4）：tree 峰值 private ≈ 287 MiB + 84 MiB × workers；單一 worker group 最重 275 MiB。

**default（O1）**：`PER_WORKER_MIB` 改為 **256 MiB**，約邊際成本的 3 倍，也涵蓋最重的單一 group。以 available 3 GiB 為例：(3 − 1) / 0.25 = 8 個 worker（今天是 2）；5.5 GiB 時 18 個（今天是 4）。

**其他專案（O2）**：不寫死一個數字，從過去的 run 自動記錄：

- Windows 上每個 stage 的 process tree 本來就在 kill-on-close Job 裡（`StageJob`）。stage 結束、關閉 Job 之前，用 `QueryInformationJobObject(JobObjectExtendedLimitInformation)` 讀 `PeakJobMemoryUsed`（整個 Job 的 commit 峰值），除以這次的 worker 數，就是這次的每 worker 成本。實作的第一步是先驗證：沒設 memory limit 的 Job 是否也會累計這個峰值；不會的話，改成在 stage 結束時加總每個 process 的 `PeakProcessMemoryUsed`。
- Linux / macOS：`resource.getrusage(RUSAGE_CHILDREN).ru_maxrss`，取最大的單一子 process，當作每 worker 成本的估計。
- 記錄在 `~/.atc/run/memory/<project key>.json`（project key 是 tree 的 repository identity），保留最近 10 次的每 worker 值。下一次的估計 = 最近 10 次的最大值 × 1.25，下限 128 MiB。
- 優先順序：專案在 `[tool.atc-testkit]` 宣告的 `worker_memory_mib` > 自動記錄 > default 256 MiB。§3.3 那一行會寫出用的是哪一個來源。

**`RESERVE`（O6）**：維持 1 GiB。available 本身已經扣掉 collector、signal_feed 等常駐程式正在用的記憶體；RESERVE 是留給它們成長的空間，加上 `_memory_room` 會把 60 秒內剛 grant 的 run 按全額算進去。

### 3.3 進度可見（item c，含 f）

- **開始時一行說清楚拿到幾個、被什麼限制（f）**：`atc test run` 和每個 stages runner（gate、verifier、CI runner）在 parallel stage 拿到 token 之後，一定印出一行到 stdout，不只在被切的時候才印：

  `workers: <granted> of <pool> (<source> <want>; <limit>)`

  `<limit>` 是實際卡住數量的那一個，例如：
  - `workers: 18 of 18 (default 18)`
  - `workers: 1 of 18 (default 18; memory ceiling: 2.1 GiB available, 1024 MiB/worker default)`
  - `workers: 6 of 18 (default 18; host budget: 6 of 18 free, 2 runs active)`
  - `workers: 4 of 18 (default 18; 31 tests collected, 8 per worker)`
  - `workers: 8 (flag 8; CI, no pool)`

  保留 `workers:` 開頭（現有的格式和 test 都靠它）。每 worker 記憶體寫出來源：`default`、`recorded` 或 `pyproject`。
- **同一行寫進 stage log 的 header**：`stages.log_header` 已經寫了 `time slack:`，`workers:` 行也一起寫進去。verifier 跑到一半時，從 stage log 就看得到用了幾個、為什麼（§2）。
- **`atc test run` 開頭印 log path**：已經有了（`LOG <path>`，`testrun.run`），保留。`--progress` 也已經能把 pytest 輸出串流到 console。
- **pool row 多記兩個欄位**：`log`（stage 或 run 的 log 路徑）和 `limit`（上面那一行括號裡的內容）。`atc test run` 寫自己的 run log；`run_stages` 寫每個 stage 的 `log_for(stage)`。
- **`atc test status`（新指令，O8）**：唯讀，用 `Pool.status(prune=False)` 讀 row，不刪任何東西、不拿任何 lock，每列一個 run：

  `<label> pid <pid> <stage> <tokens>/<want> workers held <time> progress <pct>% (<limit>) log <path>`

  等待中的 run 寫 `waiting <time> for <floor>`。progress 取 log 最後 8 KiB 裡最後一個 `[ NN%]`；pytest 的 `-q` 輸出每行都有這個標記。沒有標記時寫 `progress -`。`--json` 把同樣的欄位放在 `runs` 底下。沒有任何 run 時印 `IDLE worker pool: <free> of <size> free`。`atc doctor` 現有的 pool 段落不變。

### 3.4 `--select` 涵蓋幾乎整個 suite 時跳過（item e）

**偵測**：`atc test run --select <base>` 拿到 selector 的 test paths 後，`--collect-only -q` 分別 collect 選中的 paths 和整個 tree（§3.1 本來就要做的 collect，多一次全 tree 的 collect 約 1.5 s）。比例 = 選中的 test items / 全部 items。用 items 不用檔案數，因為各個 test file 的大小差很多。root 的 selector 選到 full suite 時，`--json` 會把每個檔案都列出來（`selected_files`），所以 items 比例也能正確辨認這種情況。

**門檻**：`[tool.atc-testkit] select_full_fraction`，0 到 1 的數字，default **0.5**（O5），專案可以調整；設 1 等於關掉。依據（§5）：選中一半時，writer 在 18 個 worker 上約花 70 s，序列約 420 s，而 verifier 無論如何都會跑完整的那一次。

**輸出**：超過門檻時不跑，印

`SELECT <base>: <n> changed paths, <k> test paths, <a> of <b> tests (<pct>%) >= select_full_fraction <f>`
`SKIPPED_WIDE the reviewer's atc verify runs these; run them here with --wide, or the touched files with --touched`

exit 0（沒有 test 失敗），但 token 用 `SKIPPED_WIDE`，跟 `PASS` 分開。atc-review 的 writer 步驟 1 加一句：step report 照實寫出 `SKIPPED_WIDE` 這一行，不能寫成 PASS。

**writer 仍然拿得到快速回饋**：

- `--touched`：只跑 diff 裡直接改到的 test file，加上**直接** import 被改到的 module 的 test file（一層，不做遞移閉包）。selector 協定加一個可選旗標 `--direct`；root 的 `select_tests.py` 用 `Graph._edges` 實作一層的版本。不支援 `--direct` 的專案，`--touched` 退回只跑 diff 裡的 test file。`--touched` 不受門檻限制。
- `--wide`：照常跑整個選集，給 report 前要先確認的 writer 用。
- coordinator 2026-11-11 的指示（writer 只跑 `atc integrate --check` 加改到檔案的針對性測試）在這裡變成工具的 default 行為，brief 不必再寫完整指令。

### 3.5 GNU make jobserver 相容

atc 不在 make 底下跑，pytest-xdist 也不是 jobserver client，所以**不實作** client，也不把 pool export 出去（O7）。只做偵測：`MAKEFLAGS` 含 `--jobserver-auth` 時，`workers:` 行加上 `make jobserver present, not joined`，讓使用者知道兩邊的 token 不互通。哪天真的有專案在 `make -j` 底下跑 atc，再開 task 實作 client：POSIX 是 `fifo:PATH`，Windows 是 named semaphore。

### 3.6 `atc doctor` 回報記憶體與 kernel nonpaged pool（item g）

只在 Windows：用 `GetPerformanceInfo`（psapi）讀 `PhysicalAvailable`、`PhysicalTotal`、`KernelNonpaged`，乘以 `PageSize`。這個 API 在這台主機上可以讀到（測試進行中讀到 nonpaged 2.26 GiB、available 17.4 / 31.8 GiB）。

- 一般情況：`READY memory: 17.4 of 31.8 GiB available; kernel nonpaged pool 1.0 GiB`
- 超過門檻：`WARN memory: kernel nonpaged pool 18.5 GiB (above 4.0 GiB): a driver is leaking kernel memory; test workers are cut by the memory ceiling until a reboot frees it`
- available 低到不夠 floor（< RESERVE + 2 × 每 worker 成本）：`WARN memory: 2.1 GiB available, test runs get <n> workers`
- `--json`：`memory` 欄位，含 `available`、`total`、`nonpaged`、`nonpaged_threshold`、`warnings`。

**門檻（O10）**：`max(4 GiB, PhysicalTotal / 8)`，這台主機是 4 GiB。依據：平常約 1 GB；全 suite 在 18 個 worker 下跑的時候讀到 2.26 GiB；洩漏時到了 18.5 GB。4 GiB 高於正常負載約 1.8 倍，遠低於洩漏值。host file 可用 `nonpaged_pool_warn_gib` 覆寫。

`WARN` 是 `atc doctor` 新增的狀態字（現在只有 `READY`、`NOT_READY`、`ERROR`）。它不改變 exit code，因為主機還是能跑測試，只是變慢（O9）。

## 4. 每個 worker 的記憶體：量測

**方法**（腳本放在 session scratchpad 的 `measure.py`、`one.sh`，不進 repo）：在 foreground 啟動 `atc test run`，每 0.25 s 用 psutil 掃一次它的整個 process tree：

- 每個 process 的 `peak_pagefile`（private commit 峰值，由 kernel 記錄，不會因取樣而漏掉）。
- 每次取樣的 tree 總 private bytes，取最大值。
- top-level xdist worker = cmdline 含 `exec(eval(sys.stdin` 且祖先裡沒有其他 worker 的 process；worker group = worker 加上它所有的子孫（test 自己開的 subprocess、nested pytest）。
- 系統 available memory 的最低點。

量測用的 tree 是 HEAD 的 `git archive` 副本（scratch `ATC-0023-measure`），在副本裡寫入 `worker_memory_mib = 64`，讓 memory ceiling 不會切掉要量的 worker 數。主機條件：重開機後，available 約 19 GiB，CPU 約 5%。每次 run 之前確認 `~/.atc/run/workers` 是空的；run 期間 ledger 只有自己的 1 個 row（`max_ledger_rows` = 1），一次只跑一個。

| run | tree 峰值 private | tree 峰值 working set | 單一 worker group 峰值（max / median） | worker 本身的 private（max） |
| --- | --- | --- | --- | --- |
| `-n 4` | 623 MiB | 926 MiB | 275 / 27 MiB | 34 MiB |
| `-n 8` | 1064 MiB | 1547 MiB | 236 / 27 MiB | 34 MiB |
| `-n 12` | 1265 MiB | 1622 MiB | 231 / 34 MiB | 34 MiB |
| `-n 18` | 1803 MiB | 2386 MiB | 233 / 127 MiB | 34 MiB |
| 序列（5 段中最大的一段） | 332 MiB | 542 MiB | — | — |

線性擬合（`-n 4` 到 `-n 18`）：tree 峰值 private ≈ 287 MiB 固定（`atc`、pytest main、collection）+ **84 MiB × workers**。worker 本身只有約 28–34 MiB；其餘來自 test 開的 git、uv、pwsh、nested pytest 等 subprocess。最重的單一 group 是 275 MiB。

系統 available 在 run 期間下降 1.7–4.5 GiB，比 tree 本身多，多出來的是 test 寫進 scratch 的檔案的 dirty page cache 和 Defender 掃描。這部分在 run 結束後回收，`_memory_room` 每次 grant 時重讀 available，已經反映進去。

## 5. 預期加速：量測

同樣的主機條件、同一個 tree，全 suite（1851 個 test，`-q --durations=15`）。序列 baseline 因為單次超過 foreground 10 分鐘的上限，把 48 個 test file 輪流分成 5 段，各自跑完再加總；每段多算一次 startup，所以序列的數字略偏高。

| 設定 | 耗時 | 相對序列 |
| --- | --- | --- |
| 序列（今天 `atc test run` 沒帶 `-n`） | 835 s（318 + 112 + 105 + 168 + 134） | 1.0× |
| `-n 4`（今天 available 約 5.5 GiB 時 default 拿到的數量） | 238 s | 3.5× |
| `-n 8`（今天 default 的上限） | 175 s | 4.8× |
| `-n 12` | 152 s | 5.5× |
| `-n 18`（提案在空閒主機上的 default） | 138 s | 6.0× |

結論：

- 對 writer 最常見的情況（沒帶 `-n`）：835 s → 138 s，快 **6.0×**。
- 對今天的 `-n auto`：空閒主機上 175 s → 138 s（1.27×）；available 約 5.5 GiB 時是 238 s → 138 s（1.7×）；available < 3 GiB 時（§2 的情況）從序列速度 → 至少 8 個 worker（256 MiB/worker）。
- 8 到 18 的邊際收益遞減。最慢的單一 test 是 14.3 s（`test_integrate_reuse.py`），不是拖尾；推測是 CPU 被 test 開的 subprocess（git、uv、nested pytest）吃滿，再加上固定約 20–30 s 的 startup 和 collection。所以 default 用 pool size，不再往上加。

## 6. Prior art：採用或不採用

依 `.agents/handoffs/2d-test-workers-prior-art.md`。

| 來源 | 重點 | 決定 | 理由 |
| --- | --- | --- | --- |
| GNU make jobserver | token pool，跨 process 共用，拿空著的 slot | 採用模型（已是 ATC-0018 的設計） | 同一種 token 模型；ATC 的 byte-range lock 會在 process 結束時由 OS 自動釋放，不會像 pipe token 那樣漏掉。 |
| make 的 implicit token（每個 client 自帶一個 slot） | 不用等就能起步 | 採用其意 | 對應 ATC 的 floor 2：只要有 2 個空著就開跑，不等湊滿 want。 |
| make jobserver 協定 | MAKEFLAGS、fifo、semaphore | 不採用，只偵測（§3.5） | 沒有使用者在 make 底下跑；xdist 不是 client。 |
| Ninja `-l` load average | 依 load 降速 | 不採用 | Windows 沒有 load average；ATC 的對應物是 `acquire` 當下的 memory room。 |
| Ninja / Gradle 的 pool 不能超過全域 `-j` | 上限一致 | 已有 | flag 被 pool size 切（2026-11-11 的裁決）。 |
| Bazel `--local_ram_resources` | CPU+RAM 預算，每個 action 宣告成本 | 採用「CPU+RAM 一起管」，不採用「宣告的估計值」 | ATC-0018 已經是 CPU+RAM。Bazel 的 RAM 估計被量到低了約 160 倍；ATC 的 1024 MiB 則高了約 12 倍（§4）。教訓都是成本要量，不要猜：§3.2 改用實測加自動記錄。 |
| Bazel 預設 `HOST_RAM × 0.67`（未證實） | 依總記憶體 | 不採用 | 這台主機的常駐程式和 kernel pool 可能占去大半（§3.6）；ATC 看 available。 |
| Bazel：每個 invocation 自己一套 tracker | 不跨 invocation | 不採用 | ATC 的重點就是跨 run 共用。 |
| pytest-xdist `auto` = physical cores、`logical` = logical cores | 只看 CPU | 部分採用 | pool 是 logical 的 3/4（ATC-0018 O3）；§5 顯示 18 個 worker 仍比 12 個快，以 logical 為準是對的。 |
| Jest：單次 run 用 cores − 1，watch 用一半 | 保留給互動 | 已有 | pool 3/4，其餘 1/4 留給 session、editor、Git、OS。 |
| nextest `threads-required` | 每個 test 的權重 | 不採用（現在） | xdist 無法把單一 test 排成占多個 slot。重 test 用 `xdist_group` 和 serial stage 處理。 |
| Buck2 local resources、Nix、Cargo、Go | 固定數量，沒有記憶體 | 無可採用 | 沒有跨 run 共用，也沒有記憶體輸入。 |

## 7. 風險

- **常駐 collector 和 signal_feed 的記憶體壓力**：available 是即時讀數，加上 RESERVE 1 GiB、60 秒 ramp 計算，只在 `acquire` 時判斷。run 中途記憶體被別人吃掉時不會縮減 worker。18 個 worker 的 tree 峰值是 1.8 GiB（§4）。commit limit 65.8 GiB（含 pagefile），最壞情況是 paging 變慢，不是 OOM。
- **負載下的 flake**：§5 的每一次 run（4 到 18 個 worker）都是 PASS。worker 變多時 timer 類的 test 比較容易超時；現有的 time slack（`ATC_TEST_TIME_SLACK`，default 2 s）先不動。如果出現新的 flake，修的是 test 的設計（等待條件），不是調高數字。
- **Windows**：每個 worker 啟動的 process creation 和 import 成本、Defender 掃描新檔案的成本，已經包含在 §5 的數字裡。
- **kernel pool 洩漏再發生**：§3.3 那一行和 §3.6 的 `atc doctor` 會直接指出原因；修正在主機端（重開機或更新驅動），不在 atc。
- **小 run 占滿 pool**：用 §3.1 的 collect 上限處理。
- **一個 run 拿走全部 18 個 token**：elastic 的設計讓後來的 run 只要等 floor 2 空出來。ATC-0018 已有 `WAIT` 行和 `WORKER_WAIT_TIMEOUT`，加上 `atc test status` 可以看到是誰占著。

## 8. 要改的地方

- `atc-testkit`：`stages.py`（default、resolve、`workers:` 行、log header）、`workers.py`（`PER_WORKER_MIB`、row 的 `log`/`limit`、Job peak 記錄）、`testrun.py`（default、collect 上限、`--select` 門檻、`--touched`、`--wide`）、`verifier.py`（resolve 時機）、`project.py`/`config.py`（`select_full_fraction`）。
- `atc_cli`：`atc test status`、`atc doctor` 的 memory 段落與 `WARN` 狀態。
- root `scripts/select_tests.py`：`--direct`。
- 文件：`docs/TESTKIT.md`（§ Stages、§ Host worker budget、§ Commands、§ What a project supplies）、`docs/ATC_HOME.md`（`~/.atc/run/memory/`、`nonpaged_pool_warn_gib`）、`shared/skills/atc-review/SKILL.md` writer 步驟 1 加 `SKIPPED_WIDE` 一句（技能檔，不是 governance）。
- 不改 governance；不改版號（release 由 coordinator 統一處理）。

## 9. 測試

每條 guard 一個 mutant：default 不再受 8 限制；pool 內 resolve 不依記憶體切；floor 不塌到 1；開始時一定印 `workers:` 行，而且寫出限制原因；collect 上限；門檻 `SKIPPED_WIDE` 與 `--wide`、`--touched`；`atc test status` 唯讀（不刪 stale row）；Job peak 的記錄與讀取；`MAKEFLAGS` 偵測；`atc doctor` 的 nonpaged 門檻與 `WARN` 不改 exit code。
