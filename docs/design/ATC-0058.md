| 執行方式 | wall | pytest 回報 |
| --- | --- | --- |
| `-n 0`（今天的 mutant run） | 264 s | 89 passed in 262.5 s |
| `-n 4 --dist loadgroup` | 95 s | 93.5 s |

### 1.3 已知 testkit 缺陷：mutant 窄化記下帶 group 後綴的 node ID

在 `ef47abf` 以 18 個 worker 跑 baseline 後，第一個 mutant 重現 `INCONCLUSIVE integ_supp_before_own -> pytest exit 4: ERROR: not found: ...test_testkit_evidence.py::test_integrated_comm`。

根因：行記錄的 context 是
`adapters/python/tests/test_testkit_evidence.py::test_integrated_commit_reuses_its_record@tests/test_testkit_evidence.py`。
pytest-xdist 3.6.1 在 `--dist loadgroup` 下，於 worker 的 `pytest_collection_modifyitems` 把 `@<group>` 接到 `item._nodeid` 後面（`xdist/remote.py:220`）。atc-testkit 的 plugin 會替用到 module 範圍 fixture 的測試加上 `xdist_group`，所以這類測試的 node ID 都帶後綴。`lines.py` 的 `_name`（`PLUGIN_SOURCE` 內）直接用 `item.nodeid`，記錄器與 collected 清單都存了帶後綴的 ID，窄化後交給 pytest 的參數因此找不到測試。錯誤訊息裡的 ID 看起來被截斷，是 pytest 解析含 `@` 與 `/` 的參數時的顯示結果，不是寫入時截斷。同一次 `supp_kind` 的 89 個測試沒有後綴，`integ_supp_before_own` 的 89 個中有 2 個有。

ATC-0055 讓 baseline 走 xdist 之後，這個缺陷才出現；單行程 baseline 不加後綴。

## 2. 分層與執行順序

驗證分三層，每層用自己的標準工具，結果都以輸入為 key 記錄（§ 5）：

1. **lint stage**：靜態規則，讀檔案文字與 AST，不執行產品碼。由 pre-commit 執行。
2. **behaviour tests**：pytest，只放執行產品碼並斷言行為的測試。
3. **mutants**：只由 reviewer 在 `strict` 下執行。

每個入口都先跑 lint：commit 時的 pre-commit hook、`atc test ID`、`atc test ID --lint`、integration verifier。lint 失敗即停，不跑 pytest。

## 3. lint stage

### 3.1 執行器：pre-commit

pre-commit 是跨語言 hook 執行器的事實標準：每個 hook 以 `rev` 釘住版本，在自己隔離的環境安裝（Python、Node、Go 等），只跑變更檔，同一份設定可供 commit hook、`--from-ref/--to-ref` 範圍執行與 CI 使用。

- 設定：repo 根目錄 `.pre-commit-config.yaml`，每個 hook 有 `rev`；`default_install_hook_types: [pre-commit]`。testkit 既有的 pre-push hook 照舊由 testkit 安裝，兩者寫不同的 `.git/hooks` 檔。
- pre-commit 本身是 Python 套件，與各 lint 工具同放在 `adapters/python` 的 `lint` dependency group，由 `uv.lock` 釘住；呼叫一律是 `uv run --locked --group lint pre-commit ...`，`local` hook 的工具也以 `uv run --locked --project adapters/python --group lint` 執行。
- hook 環境放在 `PRE_COMMIT_HOME=~/.atc/cache/pre-commit`，與 testkit 隔離環境既有的 uv、ruff cache 同一處（`docs/ATC_HOME.md`）。
- 範圍執行：`pre-commit run --from-ref <base> --to-ref <sha> --show-diff-on-failure`。
- 「lint 不進 atc-maintain」（Owner 11-16）：lint 的設定與執行在 pre-commit 與 atc-testkit。atc-maintain 只提供它本來就有的產生器 `--check`，由 pre-commit 的 `local` hook 呼叫（§ 3.2 drift 列）。

## 5. 以輸入為 key 的 evidence

### 5.1 key

借用 Bazel 的 action key 與 Nx 的 `inputs`：一個 check 的結果以「check 的身分 + 它讀的檔案內容」為 key，與 commit SHA、`main` 的位置無關。

- **輸入集合**：tree 中所有追蹤的檔案，扣除 documentation-only 分類器判為非輸入的路徑（`docs/` 下的 Markdown、`.atc/tasks/`、選擇器對應不到任何測試的 Markdown；root 的分類規則見 `docs/TESTKIT.md` § The workspace root's verifier）。哪些 Markdown 被測試讀到，root 已由選擇器與 `ROOT_READ_UNDECLARED` 掌握，所以輸入集合沿用同一個分類器，不另立第二套判斷。
- **輸入 digest**：對 `git ls-tree -r <commit>` 中屬於輸入集合的每一列 `<mode> <blob> <path>` 排序後取 sha256。Git blob ID 已是內容 hash，不讀檔案。
- **check 身分**：verifier argv、stage（name、marker、ignore）、selection、selector name 與 version、testkit version、platform、time slack、`dependency_inputs`。
- **key**：`sha256(canonical JSON {identity, inputs})`，存為 `<git-common-dir>/atc/verification-evidence/inputs/<key>.json`，內容不可變，同樣 14 天清除。

### 5.2 誰寫、誰讀

- **pytest 每個測試檔一筆**（Bazel 的 test target 粒度）：`atc test ID` 在 tree 乾淨（`HEAD` 等於 sha，`git status --porcelain` 前後皆空）或 `--sha` export 中跑完，每個 PASS 的測試檔寫一筆。tree 不乾淨時不寫，並印一行說明。
- **verifier**：每個 stage 先查每個選到的測試檔的 key，只執行沒有 PASS 記錄的檔案，log 寫 `REUSED <n> files, RUN <m> files`。全部命中時 stage 不啟動 pytest。
- **`atc integrate`**：candidate record 的比對由 `expected_main`、`reviewed` 與 tree 相等，改為 candidate tree 的輸入 digest 與 check 身分相等；`expected_main`、`reviewed` 留作稽核欄位，不比對。
- **pre-push gate**：同一個 key。
- **mutant baseline**：`baseline.json` 的 `sha` 欄位改為輸入 digest，所以 docs 修改後的 amend 不必重跑 baseline。
- **lint 不快取**：只跑變更檔，秒級；實作時量測，結果寫進 step report。

每筆 evidence 都綁一個 revision：

- 輸入 key 的記錄寫明它實際執行的 commit（`ran_on`）與該 commit 的輸入 digest。
- 重用不改那筆記錄。重用的那一方另寫自己的結果，寫明它所驗證的 revision，以及 `reused_from: {ran_on, inputs, key}`：verifier 寫在 report，`atc integrate` 寫在 integration record 的 `reused`（沿用既有欄位），gate 寫在它印出的 verdict。
- 所以每個 revision 的 evidence 都以那個 revision 為名，可追到實際執行的那次 run。§ 8.2 的論證依靠這一點。

效果：

- reviewer PASS 後 writer 只改 docs：新 tip 的輸入 digest 不變，candidate 重用。
- `main` 只前進了 docs：candidate 重用。
- writer 在乾淨 tree 上跑過的測試檔，reviewer 的 `--candidate` 不重跑；writer 的執行因此可重用，不重複（Owner 11-16）。

### 5.3 可信度的界線

- 記錄只在乾淨 tree 寫，由同一個 testkit 在同一台主機的隔離環境產生。
- reviewer 的獨立性在讀 diff 與寫 mutant，不在重跑同樣的位元組。
- 未宣告的讀取（測試讀了被歸為非輸入的 Markdown）仍由 full suite 的 `ROOT_READ_UNDECLARED` 抓到，與今天 documentation-only 例外的界線相同。

## 6. mutant 速度

### 6.1 每個 mutant 用 worker budget

- baseline 取得的 grant 持有到最後一個 mutant，不再縮成 1 個 token（ATC-0055 § 2.2 的 `shrink`）。理由：reviewer 的 mutant 階段是 task 的關鍵路徑，總時間優先（Owner 11-16）。先取整份、持有到底，也沒有逐 mutant 重新排隊的互等問題。
- 每個 mutant 以 `-n min(grant, ceil(tests / 8)) --dist loadgroup -x` 執行；只有 1 個 worker 時以 `-n 0` 在行程內跑，省下 xdist 啟動成本。
- 實測：89 個測試從 264 s 降到 73 s。

### 6.2 先跑會殺的測試

- baseline 的 plugin 同時記下每個測試的 call 時間，存在行記錄中。
- mutant 的測試依序排列：先放 mutant 自己 `tests` 中的 node ID（writer 列的 killing test，§ 7.2），其餘依 baseline 時間由快到慢。
- 這是 PIT（pitest）的做法：只跑涵蓋被改行的測試，並依執行時間排序，最快的先跑。`-x` 下 KILLED 的 mutant 只付到殺掉它的那個測試為止；SURVIVED 的仍跑完全部。

### 6.3 不採用的做法

- **mutmut 式的 in-process trampoline**：測試會啟動 Git 與 CLI 子行程，子行程從檔案讀原始碼，in-process 切換碰不到它們。
- **再縮測試清單**：§ 1.2 的 89 個都真的執行到被改的那行。

### 6.4 缺陷修正（§ 1.3）

- plugin 以 `@pytest.hookimpl(tryfirst=True)` 實作 `pytest_collection_modifyitems`，在 xdist 改 `_nodeid` 之前把原 node ID 存進 `item.stash`；`_name` 讀 stash，沒有時才用 `item.nodeid`。不去解析後綴格式，所以 xdist 改格式也不影響。
- 回歸測試：baseline 以 `-n 2` 執行、目標測試用 module 範圍 fixture（帶 `xdist_group`）時，mutant 得到 `KILLED`，而不是 `INCONCLUSIVE`。

## 7. 審查流程

### 7.1 reviewer 順序

順序為 lint → 讀 → mutants → candidate：

1. `atc test ID --lint --sha <sha>`：lint 失敗即 FAIL，不讀不跑。
2. 讀 diff（atc-review 步驟 1、3、5、6）。讀出 FAIL 級問題時直接送 FAIL，不再執行任何測試。
3. `strict`：`atc test ID --mutants`。
4. `atc test ID --candidate`。

mutants 排在 candidate 前：ATC-0057 的 survivor 本身就是 FAIL finding，先跑 mutants 可以在 FAIL 時省掉 candidate；而 candidate 有 § 5 的重用，排在後面成本低。

### 7.2 `strict` 的 writer 清單

step report 中每個 guard 寫成 `file:line` → 它擋什麼 → 預期殺掉它的測試 node ID。

- reviewer 把該 node ID 放進 mutant 的 `tests`，§ 6.2 讓它先跑。
- 列不出 killing test 的 guard 是 writer 自己找到的測試缺口，在 report 中寫明。
