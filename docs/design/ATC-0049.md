# ATC-0049 設計：由 Owner 用 uv 從 tag 安裝 `atc`，交付內容由 manifest 從 Git objects 讀取

這份設計涵蓋 ATC-0049 的新範圍，依據是 Owner 11-15 的裁決：

- 「我們還不是大型專案」：不做單一執行檔。

舊實作只當參考，位置是舊 `main` 5afbab7 與舊 branch tip e0ff6c9。第 B 步從那裡取回保留的部分。

## 1. 改什麼、為什麼

0.6.0 的已安裝 `atc` 會以 editable 方式裝在 release copy（`~/.atc/releases/<tag>`）上。release copy 是 workspace root repository 的一個 locked worktree。這帶來三個問題：

- `atc` 自己會建立 worktree 並呼叫 uv 安裝自己。
- 在 Windows 上，替換執行中的 `atc.exe` 會失敗（0.6.0 安裝時出現 WinError 32），所以需要 rename-aside。
- 「已安裝版本」是靠 release copy 的 HEAD 與 tag 來判斷的。

新做法：

1. **安裝**：Owner 從自己的終端機跑 `uv tool install --force`，來源是 tag。uv 會建立一般的（非 editable）tool 環境，`atc` 不碰自己的安裝。
2. **版本識別**：已安裝的 revision 是 uv 寫下的 PEP 610 記錄（`direct_url.json` 的 `vcs_info.commit_id`），不再是 release copy 的 HEAD。
3. **交付內容**：沿用第 1 步的設計。sync 依 `atc-manifest.yaml` 交付內容，從 content repository 的 Git objects 讀取。content repository 是 `governance_checkout`，沒有設定時是 `~/.atc/content` 的 cache。這部分與安裝方式無關，原樣保留。

  - 在 governance checkout 中，對照 `main` tip 的 Git objects。
  - 在其他 workspace 中，對照 target 的 `workspace` 項目。
  - doctor 不 fetch；cache 缺少時回 `WARN`。
- **root 解析**：只認 `workspace.yaml`。順序是 `--root`、`ATC_ROOT`、最近的上層 `workspace.yaml`；都沒有時回 `WORKSPACE_NOT_FOUND`。`init`、`doctor` 與 `--help` 改用 cwd。

- **`atc checkout NAME SHA [--no-git] [--remove]`**：建立 project 的 build tree，也就是 `main` 上某個 commit 的 detached、locked worktree，或匯出的 scratch。為此保留 `scratch.unregister`。
- **測試與 conformance**：root-resolution fixtures、`test_manifest_content.py`、`test_build_checkout.py` 中與上列項目相關的測試，以及根 `.gitignore` 改成 `/workspace.yaml`。

### 3.2 wheel 必須帶上 `scripts/`（實測發現）

我在 scratch 目錄實測：

- 工具自己的格式也一起打包。這些檔案以前以相對於程式碼位置的方式讀取，第 B 步逐一改掉：

| 讀取者 | 讀什麼 | 改為 |

### 3.3 已安裝 revision 的識別

我在 scratch 目錄實測兩種來源。兩次寫下的 `agent_traffic_control-*.dist-info/direct_url.json` 只差 `url` 這一欄，`vcs_info` 相同：

```json
{"url": "file:///C:/Users/Andy%20Liu/Hami",
 "vcs_info": {"vcs": "git", "commit_id": "c1de26ac4de6d7413f12f3aca33865e243b7f42c", "requested_revision": "v0.6.0"},
 "subdirectory": "adapters/python"}
```

- 本機 checkout：`git+file:///…/Hami@v0.6.0#subdirectory=adapters/python`，結果如上。
- GitHub：`git+https://github.com/yulinnliu/agent-traffic-control@v0.6.0#subdirectory=adapters/python`，`url` 改為 GitHub 網址，其餘相同。

因此 D7 local-first 可行：governance host 從自己的 checkout 安裝，不需要網路，也不需要先 push。

`atc` 的讀法：

```python
importlib.metadata.distribution("agent-traffic-control").read_text("direct_url.json")
```

讀出後取 `vcs_info.commit_id`（已安裝的 revision）與 `requested_revision`（通常是 tag）。新增的 `release_pin.installed()` 回傳 `Release(commit, tag)` 或 None。

結果分三種：

| 安裝方式 | `direct_url.json` | `atc` 的行為 |
| --- | --- | --- |
| `uv tool install` 從 git tag 或 SHA | 有 `vcs_info.commit_id` | 這就是已安裝的 release。release pin 與 sync 預設 target 都用它 |
| `uv run` 在 topic worktree（editable） | 只有 `dir_info: {"editable": true}`（已實測） | 視為開發用 `atc`：不比對 pin（同 0.6.0 的非 release copy），sync 預設 target 為最新 tag。doctor 回 `READY development install from <path>` |
| 從本機路徑以非 editable 安裝，或沒有 `direct_url.json` | 沒有 `commit_id` | doctor 回 `WARN`，說明無法確認安裝的 revision、請從 tag 安裝；task flow 不比對 pin |

## 6. 其他工具的做法（只留與新範圍有關的）

- **uv tools**：`uv tool install` 為每個 tool 建立隔離環境，可以從 git URL 加 `@<ref>` 與 `#subdirectory=` 安裝；`--force` 重新安裝；receipt 記錄來源。[uv: Tools][uv-tools]、[uv: Using tools][uv-guide-tools]
- **pipx**：同一種模式，每個應用程式一個隔離 venv，接受 `git+` 加 ref 的規格，升級就是重新安裝。[pipx docs][pipx]
- **PEP 610 / Direct URL Data Structure**：從 VCS 安裝的 distribution 會在 `direct_url.json` 記錄 `vcs_info.commit_id` 與 `requested_revision`，editable 則記 `dir_info.editable`。這是 § 3.3 的依據。[PEP 610][pep610]、[Direct URL Data Structure][direct-url]
- **pre-commit**：設定檔用 `rev:` 釘住 hook repository 的 tag 或 SHA，並把 clone 快取在本機。這對應 project 的 `.atc/atc.lock` 釘住精確 revision，加上 `~/.atc/content` cache。[pre-commit: Plugins][precommit]

[uv-tools]: https://docs.astral.sh/uv/concepts/tools/
[uv-guide-tools]: https://docs.astral.sh/uv/guides/tools/
[pipx]: https://pipx.pypa.io/stable/
[pep610]: https://peps.python.org/pep-0610/
[direct-url]: https://packaging.python.org/en/latest/specifications/direct-url-data-structure/
[precommit]: https://pre-commit.com/#plugins
