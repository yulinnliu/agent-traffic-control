# ATC-0039 design: tag-only sync and the release pipeline's notes

Task: ATC-0039 (`.atc/tasks/ATC-0039.yaml`), base 3bcc2ab. The record binds
this design: projects sync to the latest release tag by default with an
Owner-named SHA as the exception, the governance version-resolution rule
changes with it (authorized, routed through `GOVERNANCE_CHANGES.md`), release
notes are committed and form the Release body, v0.5.0 is the first release
made through the pipeline, PyPI is a name check only. Agents create no tag,
push, Release or upload.

## 1. What already exists

ATC-0029 (`docs/design/ATC-0029.md`, commits 7c86a47, 4142d13) built the CI
half the record names:

- `.github/workflows/validate.yml` runs on a pushed `v*` tag and on
  `workflow_dispatch` (with a `tag` input for existing tags), validates the
  tag's tree, and its `draft-release` job builds
  `atc-conformance-<v>.tar.gz`, the `atc_testkit-<tv>-py3-none-any.whl`
  wheel, `atc-testkit.json` and `SHA256SUMS`, then creates a draft Release
  `atc <v> (atc-testkit <tv>)` with `contents: write` on that job alone.
- Guards: release-tag form, tag on `origin/main`, tag equals `v` + the
  `atc` version, no Release (draft or published) for the tag yet.
- The README badge exists in both READMEs.

`gh release list` shows no Release yet, so the workflow has not drafted one.
A tag push is the Owner's act, so the rule that full CI is started by the
Owner (governance `VERIFICATION.md` § Full regression timing and evidence
reuse, "started by manual dispatch") holds unchanged: no `push` to a branch
and no `pull_request` trigger is added.

This task splits the release job so no build code holds the write token
(§ 1.1), changes its notes source (§ 4) and adds tag-only sync (§ 2, § 3).

### 1.1 Release job supply chain

Today `draft-release` holds `contents: write` while it runs code it does not
pin: `actions/checkout@v4` and `astral-sh/setup-uv@v6` by mutable tag,
`uv run` with the build dependencies `uv` installs, and `GH_TOKEN` in the
job's `env`, so every step sees the write token. `actions/checkout` also
persists the job token in `.git/config` by default, and `setup-uv` takes
`github.token` as its `github-token` input default. `SHA256SUMS` is made by
the same job, so it proves nothing against that job.

The release becomes two jobs:

- `release-build` (`needs` the three validation jobs, `contents: read`):
  checkout with `persist-credentials: false`, the guards that need Git (tag
  form, tag on `origin/main`, checkout equals the tag, tag equals
  `v` + `atc` version), the asset build and `SHA256SUMS`, the notes file
  read from `origin/main` (§ 4). It uploads the assets and the notes as one
  workflow artifact and exposes the two versions as job outputs.
- `release-draft` (`needs: release-build`, `contents: write`): no checkout,
  no `setup-uv`, no `uv`, no project code. It downloads the artifact,
  verifies `sha256sum -c SHA256SUMS` against what the build job produced,
  runs the no-Release-yet guard and `gh release create --draft
  --verify-tag`. `GH_TOKEN` is set in the `env` of those two `gh` steps
  only.

Every `uses:` in the workflow (validation jobs included: one pin set for one
file) is pinned to a full 40-hex commit SHA with the version tag in a
trailing comment, e.g. `actions/checkout@<sha> # v4.x.y`;
`actions/upload-artifact` and `actions/download-artifact` are added the same
way. The SHAs are resolved read-only at implementation time from each
action's release tag (`gh api repos/<owner>/<action>/git/ref/tags/<tag>`,
peeled to the commit) and reported in the step report. A step comment in
the workflow states the split's reason in one line.

## 2. Governance and bootloader wording

### `shared/governance/CORE.md` § Effective authority and revocation

Resolution precedence, item 3 and the paragraph after the list, become:

    3. otherwise, the latest release tag of the authoritative governance
       repository: the highest `vMAJOR.MINOR.PATCH` tag reachable from its
       canonical branch, resolved once at task start and frozen as an exact
       SHA.

    A SHA the Owner names explicitly replaces the release tag in 3; it must
    be on the canonical branch, and it is an exact revision supplied by the
    task authority in the sense of 1. A project's pin (2) moves only by
    sync, which takes the revision 3 resolves unless the Owner names one.
    A task in the governance source repository itself binds that
    repository's canonical branch tip at task start, since it changes the
    governance it reads.

Item 1, item 2 and "The working agent must not select an older governance
revision merely to obtain more permissive rules" stay as they are. The last
sentence of the new paragraph records what `atc task new --project root`
already does (`task_records.bound_governance` binds the root's `main`), so
no code changes for it.

### `AGENTS.md` § Governance bootloader

    Resolve governance in this order: exact source/revision from task
    authority (a task record here binds this repository's `main` at task
    start; a SHA the Owner names counts as one); otherwise approved
    project/task pin; otherwise the `governance_source` recorded in
    `workspace.yaml`, at its latest release tag on `main` resolved once and
    frozen as its SHA; otherwise stop.

`shared/templates/ATC_README.md` (a project's bootloader) reads its lock and
names no tip, so it stays unchanged. `CLAUDE.md` stays unchanged.

### Routing

The change follows `GOVERNANCE_CHANGES.md` § Editing canonical rules and
policy: targeted edit of the one list item and one new paragraph, read back
against the rest of `CORE.md`, authority in the record's second decision. It
needs no edit to `GOVERNANCE_CHANGES.md` itself, which holds procedure and no
change log, so ATC-0038's edits to that file do not meet this task.
`GIT_WORKFLOW.md` is not touched, since ATC-0038 edits it. Its § Governance
sync commits stays true in substance (sync runs from the ATC checkout on
`main` with no tracked change; the revision it names carries the Owner's
approval), but "Sync renders from the ATC checkout on `main`" becomes loose
once sync renders the target's tree read from that checkout. Follow-up after
ATC-0038 integrates: one sentence there naming the sync target (§ 3) as what
sync renders.

## 3. `atc onboard` and the readers of a project's synced files

### Target revision

`atc onboard --check|--sync --project NAME|--all` resolves one target
revision per run, read in the ATC checkout (no fetch):

- default: the highest tag matching `^v[0-9]+\.[0-9]+\.[0-9]+$` among
  `git tag --merged refs/heads/main`, by version order;
- `--revision <40-hex SHA>` (new option): the Owner-named SHA; it must be a
  commit in the history of `main`.

New stops, before any project is planned: `NO_RELEASE_TAG` (no release tag
on `main` and no `--revision`), `REVISION_NOT_ON_MAIN`. `--revision` with
`--root-only` is a usage error: `--root-only` renders the checkout it runs
in, as today. The run prints the target as its first line,
`target: v0.5.0 (<sha>)` or `target: <sha> (named)`, and `--json` gains a
top-level `target` object (`revision`, `tag`, `named`); both are new output,
not breaking (`shared/conformance/CLI.md` § Versions and compatibility).

### Rendering from the target's tree

Sync and check render every file they own (bootloader, vendored governance,
pointer line, `CLAUDE.md`, adapters and their supporting files, the
`VERIFICATION_SECTION_MISSING` gate's reading of `GIT_WORKFLOW.md`) from the
target revision's tree, exported once per run with the testkit's existing
`checkout.export` (`git archive` of that commit into a temporary directory,
removed at the end of the run). `build_plan` and `verification_gate` take
that tree as their render source; `workspace.yaml`, the source name, tag
lookup and the history checks keep reading the real checkout. The lock
records the target revision instead of `HEAD`, and so do the sync commit and
its `integrations.jsonl` line: `root_commit_revision` keeps its checks on the
checkout (on `main`, no tracked change) and returns the target, so
`commit_sync`'s subject, body, `source_revision`, `source_tag` and
`source_after` name the target, not `HEAD`. `RELEASE_TAGS` in
`release_tags` (today the glob `v[0-9]*`) takes the strict
`vMAJOR.MINOR.PATCH` form of the target rule, so the commit label and the
target never name different tags.

Tag lookup is local: sync never fetches, so the ATC checkout must hold the
release tags. The Owner creates each tag in this checkout before pushing it,
so it holds them; a host that did not create the tag fetches tags first.
`docs/LAYOUT.md` states this beside the lock rules.

The rendering code is the installed `atc` (the checkout's `main`), applied
to the target's sources. A change to how sync renders the same sources is a
change to what the lock means and lands in a minor release (`CLI.md`
§ Versions and compatibility), so the release projects sync to is the one
that carries it. Running the tag's own `onboard` code from the export was
considered and left out: it needs a second environment per run and buys
nothing while render changes ship only in releases. A test renders an older
release's tree (§ Tests) to prove `main`'s render code against older
sources.

### Never backwards by default

Projects are locked today at `main` SHAs past v0.4.0. Before the first
release through this pipeline, the default target is v0.4.0, which would
move them back. Rule: when the default target is a strict ancestor of the
project's locked revision, the project gets one plan line
`skip .atc/atc.lock locked at <sha>, ahead of <tag>; sync never moves a
project back without --revision` and nothing else is planned or written,
under `--check` and `--sync` alike, exit 0 for that project. A named
`--revision` moves the lock wherever it points on `main`, back included
(rollback is the Owner's call).

The lock's other rules stay: it moves when sync changes any file it writes,
when its `source` differs, and when its revision is not in the history of
`main`; a release that changes no file of a project leaves its lock where it
is.

### `bootstrap add`

`apply()` (create missing files of a new project) takes the same default
target, so a newly added project starts at the latest release.

### `atc validate --projects`

`check_atc_dir` and the adapter check compare a project's synced files with
the ATC working tree today, which would report every project synced to a
release as drifted once `main` moves past it. They compare with the tree of
the project's locked revision instead (one export per distinct locked
revision per run), which is what `docs/LAYOUT.md` already states: the files
"are current when they equal what the locked revision renders". The
history check on the lock stays.

### Shell installer

`scripts/link-skills.sh` and `check-skills.sh` keep installing and checking
the checkout they run from (its `HEAD`): a repository without the Python
runtime picks the release by checking out its tag. The shell-install CI job
is unchanged.

### Docs

`docs/LAYOUT.md` § `.atc/atc.lock` replaces "the ATC `HEAD`" with the sync
target and adds the never-backwards rule and the local-tags requirement;
§ Tracked gains
`docs/releases/<tag>.md` (§ 4). `adapters/python/README.md` (`onboard` row)
and both READMEs' `onboard` examples name `--revision`.

### Tests

`adapters/python/tests/test_tooling.py` and `test_onboard_sync_commit.py`
(onboard cases) gain: default target is the highest merged release tag; a non-release tag (`v1-test`) and a tag
off `main` are ignored; `NO_RELEASE_TAG`; `--revision` on and off `main`;
rendering comes from the target tree while the working tree differs; a
render from the real v0.4.0 tree (exported from this repository's tag) by
the current code gives the bootloader, governance and adapters byte-equal to
that tree's sources; the lock, the sync commit subject and the
`integrations.jsonl` line name the target, and a `v1-test`-style tag never
appears in the label; a project ahead of the default target is skipped
and untouched, and moves with `--revision`; `validate --projects` passes a
project at an older release than `main` and fails one that drifted from its
lock. Existing onboard tests that build an ATC fixture repo tag it so the
default resolves.

## 4. Release notes and the Release body

- Notes live at `docs/releases/v<atc version>.md`, committed in the release
  commit (governance `DELIVERY.md` § Close-out: release notes are committed).
  No CHANGELOG.
- Shape: first line `atc <v> (atc-testkit <tv>)`; a summary; `## Breaking`
  (each breaking change, deprecation and removal, per `CLI.md` § Versions and
  compatibility); `## Tasks` (each task record added since the previous tag,
  ID and one line); `## Assets` with the `sha256sum -c SHA256SUMS` line.
- `release-build` reads the notes from `origin/main`
  (`git show origin/main:docs/releases/<tag>.md`) and hands the file to
  `release-draft`, which passes it verbatim as `--notes-file`; a missing or
  empty file stops `release-build` before any draft. Reading from
  `origin/main` rather than the tag's tree lets a tag cut before this rule
  get its Release from a notes file committed later; for v0.5.0 the file is
  in both. The generator that builds the body from the release commit and
  the task records goes away, so one mechanism produces every body.
- Older tags v0.1.0 to v0.4.0 have no notes file, so a dispatch for one
  stops until a file is committed. Pending the Owner's ruling, the release
  commit adds `docs/releases/v0.3.0.md` and `v0.4.0.md` from their release
  commit bodies (936d14a, 43740eb; v0.3.0's text corrected to atc-testkit
  0.10.2, the version its tag ships); v0.1.0 and v0.2.0 get no Release.
- v0.5.0 notes cover everything in `v0.4.0..` the release commit: 62 commits
  at the base, more after ATC-0038 and this task. Breaking for 0.5.0 at
  least: the governance resolution change (§ 2) and `onboard`'s default
  target (§ 3); the release step lists the rest from the range.

## 5. Release commit (the task's last step)

On top of `main` as it stands then (a rebase onto it first): `atc` 0.5.0 in
`adapters/python/pyproject.toml` and `uv.lock`; `atc-testkit` 0.12.0 in
`atc_testkit/__init__.py` (features landed since 0.11.0, e.g. 7889af0,
3a4d46d, 3bcc2ab, so a minor version under `CLI.md`); the version mentions
the 0.4.0 release commit touched (both READMEs, the testkit README);
`docs/releases/v0.5.0.md`. Subject `chore(release): atc 0.5.0, atc-testkit
0.12.0`. After integration the Owner pushes `main`, then creates and pushes
tag `v0.5.0`; the tag push runs the workflow and leaves a draft for the Owner
to publish. Projects then move with `atc onboard --sync --all`.
