# ATC-0070 設計：lint stage 在規則變更後仍檢查既有的檔

範圍見 task record `.atc/tasks/ATC-0070.yaml`，來源是 `docs/design/ATC-0062.md` § 3 的 lint stage 一點與 § 6 決定 1。§ 1 是現況與缺口，§ 2 是量測，§ 3 是設計，§ 4 回答 task 要定的三件事，§ 5 是不採的方案，§ 6 是實作與測試，§ 7 是 Owner 的裁決。設計於 `e0e1059` 審查 PASS，Owner 2026-11-20 照建議裁決 § 7 的三件事（record 的 `decisions`）。

## 1. 現況與缺口

### 1.1 每個入口 lint 哪些檔

| 入口 | 範圍 | 程式 |
| --- | --- | --- |
| commit hook | staged 的檔 | pre-commit 自己 |
| `atc test ID`、`atc test ID --lint` | `base_sha` 以來改過的檔加 untracked，`--files <paths>` | `testrun.run_lint` → `lint.run_paths` |
| integration verifier（含 reviewer 的 `--candidate`） | `--from-ref <ATC_EXPECTED_MAIN_SHA> --to-ref <ATC_INTEGRATION_SHA>` | `verifier._lint` → `lint.range_argv` |
| CI | `--all-files` | root 的 `.github/workflows/validate.yml`；專案依模板自備 |

### 1.2 缺口

規則是檔，被規則檢查的是另一批檔。一個 range 只改了規則（`.pre-commit-config.yaml` 的 hook 或 `rev`、`shared/lint/**` 或 `.atc/lint/**`、ruff 或 markdownlint 的設定、`uv.lock` 裡 ruff 的版本），`--from-ref --to-ref` 只 lint 這個 range 改到的檔，而規則檔本身多半不是任何 hook 的對象（模板 `exclude` 掉 `.atc/`）。結果是：既有的檔在新規則下的違規，verifier 判 PASS，要等 CI 的 all-files job 或之後某個碰到那個檔的 topic 才發現，而那個 topic 與規則變更無關。

### 1.3 sync 繞過 verifier

`atc sync` 把 `shared/lint/**` 渲染進專案的 `.atc/lint/**`，直接在專案的 `main` commit（governance `GIT_WORKFLOW.md` § Governance sync commits），不經 `atc integrate`，所以沒有 verifier 跑在這個變更上。之後每個 topic 的 range 都從 sync 之後開始，range 裡不會有 `.atc/lint/**`，任何「range 改到規則就 `--all-files`」的觸發都看不到它。sync 的 commit hook 也不會：模板 `exclude: ^(\.atc/|...)`，`.atc/lint/**` 被排除。

## 3. 設計：lint stage 一律檢查整棵樹

lint stage 的每個入口（commit hook 除外）都 lint 這棵樹的每個檔，不再依 range 或改過的檔縮小範圍。理由：

- 缺口（§ 1.2）與 sync 繞過（§ 1.3）是同一件事：某個規則的變更沒有在既有的檔上執行過。不論規則是怎麼變的（topic、sync、依賴升級帶來新的 ruff 版本、專案改了自己的設定），整棵樹在自己的規則下乾淨，是唯一不必列舉輸入就成立的保證，也就是 CI all-files job 已經給的保證，提前到 verifier。
- 成本（§ 2）：專案每次多幾秒，root 多約 20 秒。lint stage 的定義就是不跑產品程式的靜態規則（governance `VERIFICATION.md` § Testing），它的成本與 test stages 不同量級。
- 每個入口結果相同：writer 的 `atc test ID`、reviewer 的 `--lint --sha` 與 `--candidate`、`atc integrate` 的 verifier 看同一個範圍，writer 不會在 review 才第一次看到 `LINT_FAILED`。

### 3.1 每個入口怎麼跑

- **verifier**：candidate 是乾淨的 Git checkout，lint 列的 argv 是 `python -m pre_commit run --show-diff-on-failure --color never --all-files`。`lint.range_argv` 換成 `lint.tree_argv`，`verifier._lint` 不再需要 `base`、`sha`。
- **`atc test ID` 與 `--lint` 在 worktree**：pre-commit 的 `--all-files` 取 `git ls-files`，不含 untracked 的檔，而 writer 的新檔常是 untracked。這個 run 把 worktree 的 index 複製成 `<scratch>/lint.index`，以 `GIT_INDEX_FILE` 指向這份副本 `git add -A`，再在同一個 `GIT_INDEX_FILE` 下跑 `--all-files`，結束後刪掉它。worktree 自己的 index 不被改動；ignored 的檔不在其中。pre-commit 4.7.0（root 釘的版本）的 `git.get_all_files` 以繼承的環境跑 `git ls-files`，而 `--all-files` 不 stash（`commands/run.py` 的 `stash = not args.all_files and not args.files`），所以兩者成立；`tests/test_testkit_lint.py` 證明。
- **副本從 worktree 的 index 開始**，不從空 index：`git add -A` 只對 stat 與 index 不同的檔重新 hash，寫進共用 object store 的只有改過或 untracked 的檔的 blob，和 writer 之後 `git add` 會寫的相同；從空 index 開始則每次 run 都要 hash 整棵樹、寫入每個檔的 blob。
- **每個 hook 都繼承 `GIT_INDEX_FILE`**，不只 pre-commit 自己。經由 Git 讀 index 的 hook 看到的是副本，含 untracked 的檔：root 的 `release` hook（`release_check.tasks_since` 的 `git diff --cached`，不改環境）屬此類，所以 writer 新增、尚未 `git add` 的 task record 也被算進去，與 commit 之後的結果相同。移除 `GIT_*` 變數的 hook 讀 worktree 自己的 index：`markdown-links`（`atc_testkit.docs --tracked` 經 `git_env()`）屬此類，untracked 的 Markdown 要到 `git add` 之後才被它檢查；verifier 的 candidate 沒有 untracked 的檔，兩者在那裡一致。這是可接受的差異：差的是尚未加入 index 的檔，verifier 一定會檢查到。`tests/test_testkit_lint.py` 以一個讀 index 的 hook 證明 hook 看到副本。
- **`--sha` 的 export**：照現行作法給 export 一個 `<scratch>/lint.git`、`git add -A`，再跑 `--all-files`。
- 三者共用 `lint.run_tree(top, place, python, env, log)`，取代 `run_paths`；`lint.existing`、`files_argv` 與 `range_argv` 移除。
- **commit hook** 不變：它是 pre-commit 給 commit 的便利，lint staged 的檔，不是 gate。
- **CI** 不變。

### 3.2 輸出與 token

- token 不變：`LINT_FAILED`、`LINT_NOT_CONFIGURED`。
- `atc test` 的通過行改為 `LINT PASS every file; log <path>`，失敗行改為 `STOP LINT_FAILED: pre-commit exited <code>; log <path>`（不再有檔數）。`LINT no changed file` 移除：整棵樹至少有 `.pre-commit-config.yaml`。
- `atc test ID --lint` 不再依 `base_sha`：沒有 `base_sha` 的 record 也跑。

### 3.3 sync 之後誰承擔新規則的違規

sync 帶來更嚴的規則後，該專案每個進行中的 topic，只要它的樹仍含新規則拒絕的檔，在 `atc test` 與 verifier 都得到 `LINT_FAILED`，直到修正的 commit 進了 `main`、topic rebase 到它之上；lint stage 沒有略過的方法。所以違規會擋住與它無關的 topic，直到修正落地。這是正確的時點：違規在 `main` 上，越早被看到越好，而不是等到某個碰巧改到那個檔的 topic。writer 在 step report 照實回報，coordinator 決定在該 topic 修，或另開 task 修完再回來。§ 7 決定 2 問 Owner 是否還要 sync 印一行提示。

## 4. task 要定的三件事

1. **`--all-files` 的觸發**：沒有觸發，lint stage 每次都檢查整棵樹（§ 3）。
2. **sync 改 `.atc/lint/**` 繞過 verifier**：下一次任何入口的 lint 就以新規則檢查每個檔（§ 3.3），不需要 sync、ledger 或 verifier 知道 sync 發生過。
3. **root 的 `shared/lint/**` 與專案的 `.atc/lint/**`**：兩者不再需要被列出。root 與專案的差別只剩各自的 `.pre-commit-config.yaml`，而那本來就是各自擁有的檔。

## 5. 不採的方案

### 5.1 range 改到 lint 輸入才 `--all-files`（task record 原本的寫法）

要成立需要三件東西，每一件都是新的維護點：

- **輸入清單**。`.pre-commit-config.yaml` 與 `.atc/lint/` 之外，專案的 ruff 設定（`pyproject.toml` 或 `ruff.toml`）、`.markdownlint-cli2.jsonc`、釘 ruff 版本的 `uv.lock` 都是規則的輸入；root 還有 `shared/lint/`、`adapters/python/pyproject.toml`（ruff、import-linter）、`adapters/python/sgconfig.yml`、`adapters/python/lint/ast-grep/`、`adapters/python/uv.lock`。testkit 無法從 pre-commit 設定推出 hook 讀哪些設定檔，所以要一個新的 `[tool.atc-testkit]` 鍵（例如 `lint_inputs`）由每個 repo 宣告，漏列就回到 § 1.2 的缺口，而且沒有任何東西會發現漏列。這正是 ATC-0062 § 1.2 描述的「手寫副本」問題。
- **sync 的 lint base**。§ 1.3 的 sync commit 在每個 range 之前，range 觸發看不到它。要看到，得把起點往前推到「最近一次跑過 lint 的整合」：由 atc 從 integration ledger（`<git common dir>/atc/integrations.jsonl`）找 base 的 first-parent 祖先中最近一個非 sync、非 records-only 整合的 `candidate_sha`，以新的環境變數傳給 verifier 與 `atc test`。這把 ledger 的語意接進 lint stage，也要 `--candidate` 與 `atc integrate` 算出相同的值才能重用 evidence。
- 只看 commit 路徑來辨認 sync commit（「只動 ATC-managed 路徑的 commit」）不成立：sync 也改 `AGENTS.md` 的 pointer line（`docs/LAYOUT.md` § The manifest 的 `pointer-line`），而只改 task record 的 commit 也是 managed-only。

換來的是 root 每次省約 20 秒、專案省幾秒（§ 2）。

### 5.2 sync 在 commit 前跑 lint stage

sync 不跑任何專案的程式，也沒有專案的 `.venv`；在 Integration Slot 內建 hook 環境（Vale 首次約 35 秒、300 MB）並跑專案的 hook，會讓 sync 依賴每個專案的環境狀態。失敗時也沒有好的結局：停下來會讓已經由 ATC repository 整合核准的 revision 卡在專案的既有違規上，而修違規又需要新規則先到專案。

### 5.3 範圍維持 range，只靠 CI 的 all-files job

這是現況。root 有 CI，但違規會在 verifier PASS、整合、push 之後才被發現；專案的 CI 由專案自備，沒有保證。

## 7. Owner 的裁決

1. **lint stage 的範圍：每個入口一律整棵樹**（§ 3），取代 record 原本範圍寫的「range 改到 lint 輸入才 `--all-files`」（§ 5.1）；record 的 `title` 與 `scope` 已照此改寫。
2. **sync 改到 `.atc/lint/**` 時不印提示。** 下一個 `atc test` 就會看到違規（§ 3.3），提示只是提前一步說同一件事，而且 sync 無法知道有沒有違規。
3. **writer 反覆跑的 `atc test ID <tests>` 也 lint 整棵樹**，與 verifier 相同，writer 不會在 review 才第一次遇到 `LINT_FAILED`；代價是 root 每次多約 20 秒。
