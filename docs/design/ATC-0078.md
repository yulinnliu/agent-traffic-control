# ATC-0078：專案端 enforcement 重產與 state 路徑 deny 的設計

範圍見 task record `.atc/tasks/ATC-0078.yaml`。§ 1 是現況，§ 2 是專案自己重新產生 enforcement 檔的指令，§ 3 是 state 路徑的 deny，§ 4–§ 6 是測試、文件與版本，§ 8 是要 Owner 裁決的事。各節寫的是建議選項下的設計；其他選項的差異寫在 § 8。

## 1. 現況

- **重產只能在 ATC worktree。** 專案改 `policies/hard-deny.yaml` 之後要重產 `generated/enforcement/` 與兩份 copy（hami-quant `AGENTS.md:144-149`、hami-quant-trading `AGENTS.md:232`），唯一的入口是 maintainer 指令 `atc-maintain guard --policies DIR --out DIR`，它只在 ATC worktree 裡跑（`shared/conformance/CLI.md` § Command groups）。兩個專案的 copy 位置相同：`.claude/settings.json` 的 `permissions.deny` 等於 `generated/enforcement/claude-code/settings.json` 的 deny，`scripts/git-hooks/pre-commit` 等於 `generated/enforcement/git-hooks/pre-commit`；兩者的 CI 以 `jq` 與 `diff -u` 比對（hami-quant `.github/workflows/ci.yml:106-124`、hami-quant-trading `ci.yml:245-261`）。copy 目前靠手動複製。
- **machine-local 段是第二套機制。** `generate_enforcement.py:160-186` 把 `workspace.yaml` 每個專案的 `state` root 轉成 `Edit(//<abs>/**)`，寫到 `--local-out`，再由人合併進專案的 `.claude/settings.local.json`；`validate_workspace.py:837-852` 在 `atc sync --check` 回報缺少（rin-vn）或不同（hq、hqt、heartopia、ria）。同一件事 PreToolUse hook 已經做到：`_table`（`generate_enforcement.py:431-435`）為每個 `state` root 加一條 `state.<name>` 的 edit/write rule，對每個 Claude Code 與 Codex session、每個 worktree、file tool 與 shell 寫入都生效，並且隨 map 自動重組。machine-local 段反而在 worktree 裡無效：Windows 上 Claude Code 從 CWD 讀 `.claude/settings.local.json`，worktree session 讀不到專案根的那份（`docs/ENFORCEMENT.md` § Machine-local segment）。
- **state 下的子路徑沒有可攜的寫法。** policy glob 不能含 `${...}`（`unresolved-token`，`generate_enforcement.py:71-78`）。HQT-0035 的裁決因此把 `~/Hami/state/hami-quant-trading-data/demo-authorizations/**` 與 `.../demo-authorization-imports/**`（read 與 write）寫死在 hami-quant-trading 的 policy（`policies/hard-deny.yaml:51-54`），只在 `workspace_root` 恰為 `~/Hami` 的主機上對。
- **hook 不看讀取。** Claude Code 的 matcher 是 `Bash|PowerShell|Edit|Write|NotebookEdit`（`generate_enforcement.py:61`），engine 只檢查含 `edit` 或 `write` 的 rule（`pretooluse_hook.py:41-42`、`:331`）。read 的 deny 只存在於各專案 commit 的 `.claude/settings.json`，以 policy 寫下的 glob 原樣生效。

## 2. 專案端重新產生：`atc policy render`

### 2.1 指令面

```text
atc policy render ID [--check] [--json]
```

- 新的 Task lifecycle 群組指令 `policy`（在 `test` 旁），第一個 subcommand `render`。它以 task ID 為對象、只寫 task 的 worktree，所以屬於 Task lifecycle。`ID` 是 task ID；指令照 `atc test ID` 的方式解析 record、專案與 managed worktree（同樣的 refusal，worktree 不在時 `NO_WORKTREE`），只寫該 worktree。workspace root 的 task 停在 `ROOT_POLICY`：workspace policy 只由 hook 組表，沒有 enforcement 檔；它的檢查是 `atc-maintain policies check`，該指令也回報 `unresolved-token`。
- 讀 worktree 的 `policies/hard-deny.yaml`，以 `generate_enforcement.render` 寫 `generated/enforcement/` 的三個檔（內容、LF、`pre-commit` 的 0755 與現在相同），再更新存在的 copy（§ 2.4）。
- 是 task-flow 指令，`CLI.md` § Release pin 的清單加上 `policy render`：專案的 `atc.lock` 不是已安裝 release 時停在 `RELEASE_MISMATCH`，使 render 用的產生器與專案 pin 的 governance 同版。
- `atc-maintain guard` 留下 hook table 的形式（`--hook-out`、`--live-hook-table`、`--live-*-hooks`）；`--policies/--out`、`--live-claude`、`--live-codex`、`--live-hook` 的形式改由 `atc policy render` 承擔，一個問題一個入口（D6）。

### 2.2 輸出 token（`CLI.md` § Output、§ Exit codes）

| 情況 | stdout verdict | exit | `--json` 欄位 |
| --- | --- | --- | --- |
| 寫了檔 | `RENDERED <n> files`，`-v` 每檔一行 | 0 | `files`（寫入的路徑） |
| 都已是最新 | `CURRENT enforcement files` | 0 | `files: []` |
| `--check` 有差異 | `DRIFT <n> files`，每檔一行原因 | 1 | `drift` |
| policy 有問題 | `STOP POLICY_INVALID: <n> problems`，每個 problem 一行，`hint: fix policies/hard-deny.yaml, then run atc policy render <ID>` | 1 | `problems` |
| root 的 task | `STOP ROOT_POLICY: <ID> is a task of the workspace root, whose policy has no enforcement files`，`hint: check it with atc-maintain policies check; the hook composes it from main` | 1 | |
| worktree 沒有 policy | `STOP NO_POLICY: <worktree> has no policies/hard-deny.yaml`，`hint: a project without a policy has no enforcement files` | 1 | |
| copy 不是合法 JSON | `STOP SETTINGS_INVALID: .claude/settings.json: <錯誤>`，`hint: fix the file's JSON, then run again`；什麼都不寫 | 1 | |

`--check` 依 `CLI.md` § Flags and names 不寫入，比對 `generated/enforcement/` 與兩份 copy。

### 2.3 誰跑

writer（agent）在 task 的 worktree 跑，產物和 policy 的改動一起 commit、一起被 review；reviewer 以 `--check` 確認。不需要 Owner 指令。workspace policy 只擋 `atc guard --install/--reset` 與 `atc-maintain guard --hook-out`，`atc policy render` 不在其中，也不需要新的 deny：它寫的內容由已在 diff 裡的 policy 決定。

### 2.4 copy

- **`.claude/settings.json`**（存在時）：讀 JSON（去掉 UTF-8 BOM），把 `permissions.deny` 換成產生的 deny list，其他 key 與其順序不動，2-space indent、結尾換行寫回。檔案存在但沒有 `permissions` 或 `deny` 時建立該 key。
- **`scripts/git-hooks/pre-commit`**（存在時）：整檔換成產生的 hook。

兩個位置是 ATC 對專案的約定，寫進 `docs/ENFORCEMENT.md` § Outputs 的 Consumer 欄；不存在的 copy 不建立（D2）。

### 2.5 `atc sync --check` 之後

`check_project_enforcement`（`validate_workspace.py:815-834`）照舊在 `generated/enforcement/` 與 policy 不符時 fail，並且也比對存在的兩份 copy；訊息的修正指令從 `run atc-maintain guard` 改成 `run atc policy render <task ID> in a task for <project>`。

## 3. state 路徑的 deny

### 3.1 `${state}` token

- 專案 policy 的 filesystem glob 可以以 `${state}/` 開頭，意思是 `workspace.yaml` 裡該專案的 `state` root。例：`${state}/demo-authorizations/**`。
- 其他位置的 `${state}`、其他名字的 token、workspace policy 裡的 `${state}` 仍是 `unresolved-token`：workspace policy 沒有單一的 state root。
- schema `hard-deny.schema.json` 的 `pathGlob` description 改寫為上述規則；`unresolved_tokens` 改成接受專案 policy 的前導 `${state}/`。

### 3.2 產生器

`${state}` rule 是 hook-only，同 `with_args` 等欄位的 command：

- `claude-code/settings.json` 不 render 它（committed 檔不放絕對路徑，也沒有可攜形式）。
- `git-hooks/pre-commit` 把它列在「Not git-enforced here」。
- Codex 本來就不 render filesystem rule。

### 3.3 hook

- **組表。** `_table` 對專案 policy 的 `${state}` rule，以該專案的 `state` 解析成絕對路徑（`_norm(base / state)` 接上其餘部分），`scope` 為 None，modes 照寫。專案在 map 沒有 `state` 時不產生 rule，`atc guard`、`atc doctor` 與 `atc sync --check` 回報一行（§ 3.6），不使組表失敗：組表失敗會擋下每個呼叫。key 已含 map 的 sha256，map 改了就重組。
- **讀取檢查。** Claude Code 的 matcher 加上 `Read|Grep|Glob`。engine 取 `Read` 的 `file_path`、`Grep` 與 `Glob` 的 `path`（`Glob` 的 `pattern` 為絕對路徑時也取），對含 `read` 的 filesystem rule 比對，命中即拒絕，理由的格式同寫入。讀取不套用 write roots 與 protected。
- **範圍。** 因此所有含 `read` 的 rule（workspace policy 的 `**/.env`、`~/.ssh/**` 等，與各專案 policy 的）都由 hook 對每個 Claude Code session 生效，不再只在 commit 了 `settings.json` 的專案裡生效。
- **已知限制**（寫進 § PreToolUse hook 的 Known limits）：
  - 搜尋根在被拒目錄之上（例如在 `workspace_root` 下 `Grep`）時，只比對 `path` 本身，不檢查它會走進哪些子目錄。
  - shell 的讀取（`cat`、`Get-Content`）不在模型內。
  - Codex 沒有讀取用的 tool，不受讀取檢查。
- **成本。** 每個 `Read`、`Grep`、`Glob` 呼叫多啟動一次 `atc hook`。本機量測：`atc hook --table` 對一個 Read payload 五次 69–89 ms（PowerShell `Measure-Command`，含 pipeline）。

### 3.4 移除 machine-local 段

hook 已以 `state.<name>` 擋下每個 state root 的寫入，所以：

- 產生器移除 `--local-out`、`--live-claude-local`、`LOCAL_FILE`、`local_settings`、`machine_local`、`MACHINE_LOCAL`；`--live-claude` 比對整份 deny list。`--workspace` 只供 hook table 的形式使用。
- `validate_workspace.report_machine_local` 與其呼叫（`:1094`）移除。
- `docs/ENFORCEMENT.md` § Machine-local segment 改成 § State token，寫 § 3.1–§ 3.3。
- 各專案現有 `.claude/settings.local.json` 裡的 `//` 項是使用者的未追蹤檔，本 task 不動；它們與 hook 重複但無害，要不要清掉由 Owner 自己決定。

### 3.5 誰跑

- 專案 policy 的 `${state}` rule 與一般 policy 改動相同：writer 在 task 裡改、review、Owner integrate；integrate 之後 hook 從 `main` 自動重組，不需要任何合併或指令。
- matcher 改變後，每台主機的 hook entry 變成 outdated（`atc guard` 已檢查 entry 是否與 render 一致）。Owner 在安裝新 release 之後，於自己的 terminal 跑一次：

```text
atc guard --install
```

  在那之前讀取檢查不生效，寫入檢查不受影響。

### 3.6 `atc sync --check` 之後

- 不再有 `machine-local state deny missing/differs` 的行。
- 新增只回報、不 fail 的一行：`sync --check: <label>: filesystem.deny[<i>] names ${state} but workspace.yaml gives <project> no state; the hook skips it`。
- hook entry outdated 由既有的 `report_hook` 回報（`pretooluse hook ENTRY_OUTDATED` 一行與 `atc guard --install` 的 hint）；`atc guard` 以 `ENTRY_OUTDATED` 停，`atc doctor` 的 `pretooluse entries` 報 ERROR `ENTRY_OUTDATED`。
- § 2.5 的 enforcement 檢查。

### 3.7 合併 untracked `settings.local.json`（只在 D3 不選 A 時）

D3-B（合併進 `~/.claude/settings.json`）與 D3-C（合併進專案的 `.claude/settings.local.json`）共用同一個合併規則：

- 擁有的項目以 `//` 前綴辨識（現在 `MACHINE_LOCAL` 的定義）。
- 合併時移除所有擁有的項目，把新的段放在原本第一個擁有項目的位置（沒有則接在 deny 最後），其他項目、其他 key 與其順序不動。
- 不是合法 JSON 時 `STOP SETTINGS_INVALID`，不寫入。寫入時先寫暫存檔再 replace。
- 限制：使用者手寫的 `//` 項也會被當成擁有而移除。

## 8. 要 Owner 裁決的事（Decisions for the Owner）

每項一個決定，建議的選項在前。

### D1 專案重產的指令面

- **A（建議）`atc policy render ID [--check]`。** 新的 Task lifecycle 群組指令，以 task ID 找到 worktree。改變：`CLI.md` 多一個指令；`atc guard` 維持「hook，Owner 的」單一意義，deny rule 不必區分 flag。
- **B `atc guard --render ID [--check]`。** 改變：沒有新指令，但同一個指令混合 agent 可跑的寫入與 Owner 專屬的 `--install/--reset`；bare `atc guard` 已是 check，`--check` 的意義要另外說明。
- **C `atc sync` 的一步。** 改變：sync 在專案 `main` 上直接 commit，重產的檔不經 review；policy 的改動先 integrate、產物後補，兩者之間 CI 會報 drift。

### D2 copy 的範圍

- **A（建議）約定位置，存在才更新。** `.claude/settings.json` 的 `permissions.deny` 與 `scripts/git-hooks/pre-commit`（§ 2.4）；`sync --check` 一併比對。改變：ATC 文件寫下專案的 copy 位置；兩個現有專案不必改 layout。
- **B 只寫 `generated/enforcement/`。** 改變：copy 仍手動，`render --check` 只看 `generated/`；專案 CI 繼續把關 copy。
- **C 專案宣告 copy 清單。** 例如 policy 的頂層 `enforcement_copies`。改變：schema 多一個欄位；目前兩個專案的位置相同，宣告沒有實際差異。

### D3 state root 的 machine-local deny

- **A（建議）只靠 hook，移除 machine-local 段**（§ 3.4）。改變：沒有任何合併或 Owner 指令；worktree 與 Codex 都涵蓋；`sync --check` 的五行回報消失。原生的 `Edit(//...)` 這一層防護不再存在。
- **B 由 `atc guard --install` 合併進 `~/.claude/settings.json`。** 這是 Owner 的指令，worktree 也生效；合併規則見 § 3.7。改變：policy 或 map 每次變動都要 Owner 重跑 `--install`，在那之前段落過時，由 `atc guard`、`atc doctor` 與 `sync --check` 回報；與 hook 是同一件事的兩套機制。
- **C 保留專案根的 `.claude/settings.local.json`，加一個寫入它的指令。** 這是權限檔，由 Owner 跑。改變：worktree session 在 Windows 上讀不到它（§ 1），覆蓋範圍不變差也不變好。

### D4 `${state}` rule 的讀取

- **A（建議）hook 檢查 `Read|Grep|Glob`**（§ 3.3）。改變：policy 變動後自動生效；所有含 read 的 rule 在每個 Claude Code session 生效；每次讀取類呼叫多約 70 ms；Owner 每台主機跑一次 `atc guard --install`。
- **B 原生 `Read(//...)`，隨 D3-B 合併進 `~/.claude/settings.json`。** 改變：讀取沒有額外延遲；每次變動要 Owner 重跑 `--install`，在那之前有空窗；要求 D3 選 B。
- **C 不強制讀取。** `${state}` rule 只擋寫入。改變：HQT-0035 已裁決的 read deny 在換成 `${state}` 後失效，或者 hami-quant-trading 必須保留寫死的 `~/Hami/...`。

### D5 `${state}` 的形式

- **A（建議）只接受專案 policy 的前導 `${state}/`，指自己的 state root。** 改變：規則單純；workspace policy 不能用。
- **B 另外接受 `${state:<project>}`。** 可指其他專案的 state root，workspace policy 也能用。改變：組表要處理未註冊專案名稱的錯誤；目前沒有需要它的 rule。

### D6 `atc-maintain guard` 的 render 形式

- **A（建議）移除 `--policies/--out` 與原生 `--live-*`**，保留 hook table 的形式。改變：產生專案檔只有一個入口；conformance 的 golden 測試直接呼叫產生函式。
- **B 保留為 maintainer 的別名。** 改變：同一件事有兩個入口，兩邊的 help 與文件都要維護。
