# ATC-0054 設計：mutant 只由執行到被改行的測試判定

範圍見 task record `.atc/tasks/ATC-0054.yaml`；要改的 spec 是 `docs/TESTKIT.md` § `atc test ID --mutants FILE`。

## 1. 現況與目標

`atc test ID --mutants FILE`（沒有 `-- TEST...` 時）以「測試檔」為單位選判定測試：`selector --direct` 為 mutant 的 edit paths 挑出的測試檔，加上 mutant 自己的 `tests`。被 kill 的 mutant 在第一個失敗就停（`-x`），成本集中在 survivor：它要跑完所有判定測試。ATC-0052 的 23 個 mutant 串行約 24 分鐘，3 個 survivor 各跑 72–90 個測試（105–174 s），其中 `R-within-error-counts-inside` 改的是沒有測試走到的 `except` 分支。

目標：baseline 記下每個測試執行了被改檔案的哪些行（含測試啟動的子行程），每個 mutant 只跑執行過它所改行的測試；沒有任何測試執行過的 mutant 不跑，直接報 `NOT_COVERED`。

## 2. 行記錄器（line recorder）

### 2.1 選擇：testkit 自帶的 `sys.monitoring` 記錄器

記錄由 runner 自己的小型記錄器完成，不用 coverage.py：

- 被測 tree 的環境不需要新的第三方套件。`adapters/python` 的 `uv.lock` 沒有 coverage；每個採用 atc-testkit 的專案也不必加。
- 只記錄被 mutant 改到的 `.py` 檔，其他檔案的 code object 第一次進入就 `DISABLE`，成本接近零。
- 每個測試要有自己的 context，子行程也要。coverage.py 的 `dynamic_context = test_function` 只作用於 pytest 本身的行程；它的 subprocess 支援（7.10 起的 `patch = subprocess`）不會把測試的 context 帶進子行程。所以就算用 coverage.py，子行程那一半仍要自己做。
- 記錄器的檔案由 runner 從常數寫進 scratch，不 import 被測 tree 的任何程式碼。因此它也能記錄舊 commit 的 export，§ 6 的量測用得到這點。

`sys.monitoring` 需要 Python 3.12 以上；atc-testkit 已要求 `>=3.12`。

### 2.2 檔案與啟動方式

runner 在 baseline 前寫出 `<scratch>/lines/hook/`，裡面有兩個模組：

- `sitecustomize.py`：環境變數 `ATC_LINES_DIR` 存在時啟動記錄器，然後交棒給原本會被 import 的 `sitecustomize`（如果有）：把自己的目錄暫時移出 `sys.path` 再 import 一次。
- `atc_lines_plugin.py`：pytest plugin。baseline 指令加上 `-p atc_lines_plugin`，不依賴專案 conftest 是否載入 `atc_testkit.plugin`。

baseline 的子行程環境（`child_environment` 之後）在 `PYTHONPATH` 前面加上 hook 目錄，並設：

- `ATC_LINES_DIR`：記錄輸出目錄 `<scratch>/lines/data/`。
- `ATC_LINES_FILES`：要記錄的檔案，絕對路徑、`os.pathsep` 分隔。

這一步在 import guard 之後，所以 guard 檢查的 `PYTHONPATH` 不變。子行程繼承環境，所以它們的 interpreter 一啟動就跑 `sitecustomize`。`-I`、`-E` 啟動的子行程，或測試自己組出不含 `PYTHONPATH` 的環境，記錄器看不到（§ 5 說明後果）。

巢狀的 testkit run（測試裡再跑 `atc test`）的 `isolate()` 會覆寫 `PYTHONPATH`。`isolate()` 改為：`ATC_LINES_DIR` 存在時保留 hook 目錄在 `PYTHONPATH` 最前面。這只影響這版之後的 tree；舊 export 裡的巢狀 run 看不到孫行程。

### 2.3 記錄

- tool id：`sys.monitoring.COVERAGE_ID`；被占用時依序用 4、3；都占用就不記錄，`sitecustomize` 不寫 started 標記（見 § 2.4），整個指令退回檔案層級。
- `PY_START`：code object 的 `co_filename`（`normcase(realpath)`）不在 `ATC_LINES_FILES` 就回 `DISABLE`；在的話用 `set_local_events` 對這個 code object 開 `LINE`。
- `LINE`：把 `(context, path, line)` 立刻 append 到本行程的 `<pid>-<random>.tsv`（`os.write` 到 `O_APPEND` 的 fd，不經 buffer），然後回 `DISABLE`。立刻寫入是因為多數子行程在 teardown 被 Job 整棵終止，`atexit` 不會執行。
- context：子行程用啟動時環境變數 `ATC_LINES_CONTEXT` 的值，整個行程固定。pytest 行程（以及 xdist worker）由 plugin 在 `pytest_runtest_protocol` 的 hookwrapper 中切換：進入時把 context 設為該測試、`os.environ["ATC_LINES_CONTEXT"]` 設為同值、呼叫 `sys.monitoring.restart_events()` 讓已 `DISABLE` 的行在新測試重新觸發；結束時恢復為空 context。範圍涵蓋 setup、call、teardown。
- 測試的識別：`<相對於 run 目錄的測試檔路徑>::<nodeid 的其餘部分>`，也就是 mutant run 的命令列能直接接受的形式（run 的目錄是 export 的 root，rootdir 是 `adapters/python`）。
- 空 context：collection、import 階段、測試以外執行的行。
- plugin 另外依執行順序把每個測試的識別寫到 `<scratch>/lines/data/order-<pid>.txt`，保留 baseline 的順序。
- pytest 行程啟動記錄器時寫 `started-<pid>` 標記檔。

每個測試的成本：它執行到的每個 code object 一次 `PY_START` callback（restart 之後），加上被記錄檔案中每個執行到的行一次 `LINE` callback。

### 2.4 baseline 之後的讀取

runner（atc 自己的 Python，只用標準庫）讀 `<scratch>/lines/data/`：

- 沒有 `started-*` 標記：記錄器沒有在 pytest 行程啟動（interpreter 沒有 `sys.monitoring`、tool id 用完、`sitecustomize` 被別的機制擋掉）。印 `NOTE lines: not recorded (<原因>); every mutant is judged by its file-level tests`，每個 mutant 照今天的方式跑。
- 有標記：建出 `(path, line) -> 依 baseline 順序的測試集合`，以及「在空 context 執行過的行」。

## 3. 每個 mutant 的判定測試

### 3.1 被改的行

每個 edit 在原始檔（baseline 用的、未 mutate 的內容，依 `_apply` 相同的換行規則）中找到 `old` 唯一的出現位置，取它涵蓋的行範圍，再用 `ast` 擴成語句：

- 與範圍相交的最內層語句。簡單語句取整個 `lineno..end_lineno`。
- 複合語句（`if`、`for`、`while`、`with`、`try`、`def`、`class`、`match`）只取 header：`lineno` 到第一個 body 語句之前一行；decorator 算在 header。
- 範圍內沒有任何語句（註解、空行）就只用原本的行範圍。

這樣 `inside-always` 這種只改到多行語句續行（`or _within(link, directory))`）的 mutant 會對到整個語句，而 Python 的 `LINE` 事件只落在語句的某幾行也不會漏掉。擴大只會多選測試，不會少選。

### 3.2 選擇規則（依序判斷）

1. 有 `-- TEST...`：不記錄、不縮小，每個 mutant 照今天的方式由給定的測試判定。baseline 也不載入記錄器。
2. mutant 有任何 edit 的檔案不是 `.py`，或記錄器沒有那個檔案的任何資料（沒有任何行程執行過它的任何一行）：這個 mutant 用檔案層級的測試（今天的 selector 加自己的 `tests`），在 verdict 前印 `NOTE <label>: no line record of <path>; judged by its file-level tests`。
3. 被改的行有任何一行在空 context 執行過（import 時執行的 module 層或 `def`、decorator、預設值）：一樣退回檔案層級，NOTE 寫 `lines of <path> run outside a test`。這類行屬於所有 import 它的測試，記錄無法歸屬。
4. 其餘：判定測試是 baseline 中執行過任一被改行的測試，依 baseline 順序。一個都沒有就是 `NOT_COVERED`（§ 4）。

mutant 自己的 `tests`（見 § 7 Q1）：

- 檔案或目錄形式的項目，縮小到其中執行過被改行的測試，與 selector 挑的一樣。
- nodeid（含 `::`）與 pytest option（`-k`、`-m` 等）原樣保留，接在縮小後的清單後面。作者點名到單一測試，就是要它判定。

每個 mutant 的結果寫進 `<scratch>/mutants-covered.json`：label、被改的行（每個 path 的行範圍）、選出的測試或退回的原因、或 `not_covered`，供 reviewer 稽核。`<scratch>/mutants-selected.json`（檔案層級）保留不變。

`NO_TESTS`（baseline 前，selector 與自己的 `tests` 都給不出測試）不變。

### 3.3 命令列長度

測試以識別逐一傳給 pytest。Windows 命令列上限 32 767 字元；總長超過 30 000 字元時改用 pytest 的 `@argfile`（pytest 8.2 起支援），寫在 `<scratch>/lines/<NNN>-<label>.args`。

## 4. `NOT_COVERED`

- verdict 行：`NOT_COVERED <label> -> no baseline test runs <path>:<a>-<b>[, ...]`。不跑 pytest，所以沒有 stage-time 行。
- 它是測試缺口，與 survivor 同等處理：結尾行列出它，exit 1。
- 結尾行：沒有 `NOT_COVERED` 時格式不變。有的時候：
  `done: 23 mutants, 2 survived R-rescan-dropped R-selector-host-env, 1 not covered R-within-error-counts-inside`；
  中止時一樣用 `N of M`，`N` 也計入印出 `NOT_COVERED` 的 mutant。
- 讀這一行的只有 spec 與 `shared/skills/atc-review/references/mutants.md`（已 grep：程式碼中沒有 parser）。

## 5. 正確性：誤差往哪個方向

記錄器的盲點（`-I`、`-E` 子行程、自組環境的子行程、舊 tree 的巢狀 run）只會讓某個測試「看起來沒執行到」：

- 判定測試變少：被 kill 的 mutant 仍要有一個失敗的測試，所以 `KILLED` 不會因為記錄不全而憑空出現。真正會 kill 的測試若被漏掉，結果是 `SURVIVED` 或 `NOT_COVERED`，兩者都 exit 1，reviewer 必須處理。
- 換句話說，縮小選擇不會讓任何缺口被隱藏，最壞情況是 reviewer 要多看一個假的 survivor。§ 6 的量測就是用來確認這種情況是否出現。

session 範圍的 fixture 只在第一個用到它的測試 setup 時執行，所以它執行的行只歸屬那個測試。mutant 只會跑那個測試（加其他執行到的），fixture 仍會在它的 setup 中執行，所以行為一致。

## 6. 量測

輸入（已從會被清掉的 scratchpad 複製到 side-session notes 資料夾）：

- `ATC-0054-input-atc0052-all-mutants.json`：ATC-0052 reviewer 的 23 個 mutant，對 9f06f6577172903aac1624defb4f00034b5a7cf3。
- `ATC-0054-input-atc0052-mutants.log`：舊選擇的 run，baseline 196 passed / 2 skipped，211.79 s；20 KILLED、3 SURVIVED。

方法：在同一台機器、同一時段，對 9f06f65 的 export 跑兩次：

1. 舊選擇：已安裝的 release `atc test ATC-0054 --mutants <file> --sha 9f06f65...`。
2. 新選擇：同一指令，但用這個 worktree 的程式（`uv run --locked atc test ...` 從 `adapters/python`）。

記錄器的檔案由 runner 寫入，所以新選擇在舊 export 上也成立（§ 2.1）；舊 export 的巢狀 run 看不到孫行程（§ 2.2），量測報告會註明。

報告內容：兩次的 baseline 時間（記錄器成本）、總時間、每個 mutant 的 verdict 與測試數。驗收：verdict 相同，唯一允許的差異是 survivor 變成 `NOT_COVERED`。預期 `R-within-error-counts-inside` 變成 `NOT_COVERED`，另兩個 survivor 的測試數大幅下降。

這是否違反「writer 不跑 `--mutants`」的裁決，見 § 7 Q3。

## 7. 待裁決

- **Q1 mutant 自己的 `tests` 是否縮小。** scope 寫「plus its own `tests`」。ATC-0052 的 23 個 mutant 全都在 `tests` 裡點名整個測試檔，而且就是 selector 挑的那個檔；如果自己的 `tests` 原樣全跑，3 個 survivor 仍各跑 72–90 個測試，這次的量測幾乎看不到效果。建議：檔案、目錄形式的項目縮小，nodeid 與 option 原樣保留（§ 3.2）。
- **Q2 記錄器。** 建議 testkit 自帶 `sys.monitoring` 記錄器（§ 2.1）。替代方案是把 coverage.py 加進 `adapters/python` 的 dev 依賴，並要求每個專案也安裝；子行程的逐測試 context 仍要自己做。
- **Q3 量測由誰跑。** Owner 11-16「改，併進 0053」：writer 不寫 mutant 檔、不跑 `--mutants`。§ 6 的量測重放的是 ATC-0052 既有的 mutant 檔，是效能量測，不是檢驗本 task 的 guard，但指令仍是 `--mutants`。建議：由 writer 跑量測並把結果寫進本文件 § 6（scope 把量測列為交付內容），本 task guard 的 strict mutant 仍由 reviewer 寫與跑。另一選項：量測交給 reviewer 在審查時跑。
