# ATC-0054 設計：mutant 只由執行到被改行的測試判定

範圍見 task record `.atc/tasks/ATC-0054.yaml`；要改的 spec 是 `docs/TESTKIT.md` § `atc test ID --mutants FILE`。

## 1. 現況與目標

`atc test ID --mutants FILE`（沒有 `-- TEST...` 時）以「測試檔」為單位選判定測試：`selector --direct` 為 mutant 的 edit paths 挑出的測試檔，加上 mutant 自己的 `tests`。被 kill 的 mutant 在第一個失敗就停（`-x`），成本集中在 survivor：它要跑完所有判定測試。ATC-0052 的 23 個 mutant 串行約 24 分鐘，3 個 survivor 各跑 72–90 個測試（105–174 s），其中 `R-within-error-counts-inside` 改的是沒有測試走到的 `except` 分支。

目標：baseline 記下每個測試執行了被改檔案的哪些行（含測試啟動的子行程），每個 mutant 只跑執行過它所改行的測試。如果記錄器觀察到被改的檔案，但沒有任何測試執行過被改的行，這個 mutant 就不跑，直接報 `NOT_COVERED`。記錄器沒有觀察到的檔案，則退回今天的檔案層級選擇（scope：「A file the coverage could not observe (no data for it) falls back」）。兩者的界線見 § 3.2。

## 2. 行記錄器（line recorder）

### 2.1 testkit 自帶的 `sys.monitoring` 記錄器

記錄由 runner 自己的小型記錄器完成，不用 coverage.py（Owner 11-16「testkit 自帶」）：

- 被測 tree 的環境不需要新的第三方套件。`adapters/python` 的 `uv.lock` 沒有 coverage；每個採用 atc-testkit 的專案也不必加。
- 只對被 mutant 改到的 `.py` 檔開 `LINE` 事件。
- 每個測試要有自己的 context，子行程也要。coverage.py 的 `dynamic_context = test_function` 只作用於 pytest 本身的行程，它的 subprocess 支援不會把測試的 context 帶進子行程，所以這一半無論如何都要自己做。
- 記錄器的檔案由 runner 從常數寫進 scratch，不 import 被測 tree 的任何程式碼，所以也能記錄舊 commit 的 export（§ 6 的量測需要這點）。

`sys.monitoring` 需要 Python 3.12 以上；atc-testkit 要求 `>=3.12`。

### 2.2 檔案與啟動方式

每次 baseline 前，runner 先刪除再重建 `<scratch>/lines/`。同一個 scratch（`<ID>-<sha7>`）可能重跑，舊記錄會讓沒執行的行被當成已執行。接著寫出 `<scratch>/lines/hook/`，裡面有兩個模組：

- `sitecustomize.py`：環境變數 `ATC_LINES_DIR` 存在時啟動記錄器，然後交棒給原本會被 import 的 `sitecustomize`（如果有）：把自己的目錄暫時移出 `sys.path` 再 import 一次。
- `atc_lines_plugin.py`：pytest plugin。baseline 指令加上 `-p atc_lines_plugin`，不依賴專案 conftest 是否載入 `atc_testkit.plugin`。

baseline 的子行程環境（`child_environment` 之後）在 `PYTHONPATH` 前面加上 hook 目錄，並設：

- `ATC_LINES_DIR`：記錄輸出目錄 `<scratch>/lines/data/`。
- `ATC_LINES_FILES`：要記錄的檔案，絕對路徑、`os.pathsep` 分隔。

這一步在 import guard 之後，所以 guard 檢查的 `PYTHONPATH` 不變。只有 baseline 設這些變數；mutant run 的環境沒有 `ATC_LINES_*`，hook 目錄也不在它的 `PYTHONPATH`，所以 mutant run 不記錄任何東西。

子行程繼承環境，所以它們的 interpreter 一啟動就跑 `sitecustomize`。這個 repo 的測試啟動子行程時，環境都是展開 `os.environ` 再加減變數（例如 `test_testkit_testrun.py` 的 `run_command` 只拿掉 `PYTEST_*`），所以 `PYTHONPATH` 與 `ATC_LINES_*` 會傳下去。`test_close_out.py` 直接在 pytest 行程內呼叫 `scratch` 與 `testrun`，不經子行程。記錄器看不到的情況列在 § 5。

巢狀的 testkit run（測試裡再跑 `atc test`）的 `isolate()` 會覆寫 `PYTHONPATH`。`isolate()` 改為：`ATC_LINES_DIR` 存在時，把 hook 目錄保留在 `PYTHONPATH` 最前面。巢狀 run 的 pytest 行程沒有 `-p atc_lines_plugin`，所以：

- 它的 context 固定為啟動時繼承的 `ATC_LINES_CONTEXT`，也就是外層的測試。
- 它只寫 TSV 記錄列，不寫 `started-*` 與 `order-*`（這兩種只由 plugin 寫，見 § 2.3）。
- 它執行的通常是測試自己準備的 fixture tree，路徑不在 `ATC_LINES_FILES`，不會產生記錄列。如果有，記錄列照常歸給外層測試。

讀取端（§ 2.4）不需要特別處理巢狀 run。這只影響這版之後的 tree；舊 export 的巢狀 run 會覆寫 `PYTHONPATH`，看不到孫行程。

### 2.3 記錄

- tool id：`sys.monitoring.COVERAGE_ID`；被占用時依序用 4、3；都占用就不記錄。
- `PY_START`：code object 的 `co_filename`（`normcase(realpath)`）不在 `ATC_LINES_FILES` 就回 `DISABLE`；在的話用 `set_local_events` 對這個 code object 開 `LINE`（之後一直開著，generator 恢復執行時也會觸發）。
- `LINE`：把 `context\tpath\tline\n` 立刻 append 到本行程的 `<pid>-<random>.tsv`（`os.write` 到 `O_APPEND` 的 fd，不經 buffer），然後回 `DISABLE`。立刻寫入的原因：多數子行程在 teardown 被 Job 整棵終止，`atexit` 不會執行。
- context：子行程用啟動時環境變數 `ATC_LINES_CONTEXT` 的值，整個行程固定。pytest 行程（以及 xdist worker）由 plugin 在 `pytest_runtest_protocol` 的 hookwrapper 中切換：進入時把 context 設為該測試、`os.environ["ATC_LINES_CONTEXT"]` 設為同值，並呼叫 `sys.monitoring.restart_events()` 讓已 `DISABLE` 的事件在新測試重新觸發；結束時恢復為空 context。範圍涵蓋 setup、call、teardown。
- 測試的識別：`<相對於 run 目錄的測試檔路徑>::<nodeid 的其餘部分>`，也就是 mutant run 的命令列能直接接受的形式（run 的目錄是 export 的 root，rootdir 是 `adapters/python`）。
- 空 context：collection、import 階段，以及其他不在任何測試中執行的行。
- plugin 依執行順序把每個測試的識別寫到 `<scratch>/lines/data/order-<pid>.txt`，保留 baseline 的順序。
- plugin 在 `pytest_configure` 確認記錄器已在本行程啟動後，寫 `started-<pid>`。

**成本。** `restart_events()` 會重新開啟所有已 `DISABLE` 的事件，包括非記錄檔案的 `PY_START`。因此 pytest 行程（與 xdist worker）中，每個測試執行到的每個 code object 都會再觸發一次 `PY_START` callback（一次 set lookup 加回傳 `DISABLE`），被記錄檔案中每個執行到的行再觸發一次 `LINE` callback。子行程的 context 固定、不呼叫 restart，每個 code object 與每個行一生只觸發一次。§ 6 單獨量出這個成本，並設接受門檻。

### 2.4 baseline 之後的讀取

runner（atc 自己的 Python，只用標準庫）讀 `<scratch>/lines/data/`：

- 只採用以換行結尾、剛好三欄、行號是整數的 TSV 列。子行程寫到一半被終止時留下的殘列會被略過。
- 沒有 `started-*`：記錄器沒有在 pytest 行程啟動（interpreter 沒有 `sys.monitoring`、tool id 用完、`sitecustomize` 被別的機制擋掉、plugin 沒載入）。印 `NOTE lines: not recorded; every mutant is judged by its file-level tests`，每個 mutant 照今天的方式跑。
- 有：建出 `(path, line) -> 依 baseline 順序的測試集合`，以及「在空 context 執行過的行」。

### 2.5 worker budget

host worker budget 不變（`docs/TESTKIT.md` § Host worker budget）：指令仍在 baseline 前取一個 token，持有到結束，涵蓋 baseline 與每個 mutant run。baseline 與 mutant run 的 pytest worker 選項（`-n 0`，或 tests 參數中的 `-n K`）也不變。記錄器不啟動任何新行程，不另取 token。

## 3. 每個 mutant 的判定測試

### 3.1 被改的行

映射用 pristine 文字：baseline 前讀入的、未 mutate 的檔案內容，依 `_apply` 相同的換行規則。mutant 的每個 edit 都在 pristine 文字中找 `old`：

- 每個 edit 的 `old` 在 pristine 中必須剛好出現一次。0 次（例如它依賴前一個 edit 產生的文字）或 2 次以上，這個 mutant 就退回檔案層級（§ 3.2 規則 2），不得判 `NOT_COVERED`。實際套用時 `_apply` 依序作用於當下內容，規則不變。
- 取 `old` 涵蓋的行中，`old` 與 `new` 真正不同的行：逐行比較，去掉兩者開頭與結尾相同的行。整行增刪時，取切口兩側的行。`old` 常帶上下文行來確保唯一，例如 `R-within-error-counts-inside` 的 `old` 包含 `try` 內一定會執行的 `return`；如果把上下文也算進去，它永遠不會是 `NOT_COVERED`。
- 這些行每一行各自擴成語句，最後取並集：
  - 包含該行的最內層簡單語句：整個 `lineno..end_lineno`。
  - 該行落在複合語句（`if`、`for`、`while`、`with`、`try`、`def`、`class`、`match`）的 header：只取 header，即 `lineno` 到第一個 body 語句前一行，decorator 算在 header。
  - 該行不在任何語句裡（註解、空行）：只取這一行。

所以 `inside-always` 這種只改到多行語句續行（`or _within(link, directory))`）的 mutant，會對到整個語句。Python 的 `LINE` 事件只落在語句的某幾行時也不會漏。擴大只會多選測試，不會少選。

### 3.2 選擇規則（依序判斷）

1. 有 `-- TEST...`：不記錄、不縮小，每個 mutant 照今天的方式由給定的測試判定；baseline 也不載入記錄器。
2. 這些情況下，該 mutant 用檔案層級的測試（今天的 selector 加自己的 `tests`），並在 verdict 前印 `NOTE <label>: <原因>; judged by its file-level tests`：
   - 任一 edit 的檔案不是 `.py`；
   - 任一 edit 的檔案沒被觀察到：它在記錄中沒有任何一列，任何 context 都沒有（見下方說明）；
   - 某個 `old` 在 pristine 中不是剛好出現一次（§ 3.1）。

   **「觀察到」以檔案為單位。** 一個 `.py` 檔只要被任何有記錄器的行程載入，它的 module code 就會執行，至少會在空 context 或某個測試的 context 留下記錄列。所以：
   - 檔案有任何記錄列：記錄器觀察到它。被改的行沒有任何測試執行過，就是規則 4 的 `NOT_COVERED`。
   - 檔案一列都沒有：沒有任何有記錄器的行程載入過它。可能是沒有測試用到它（真正的缺口），也可能只在記錄器看不到的行程中執行（§ 5 的盲點，例如以 `-I` 執行的腳本）。記錄分辨不出這兩種情況，所以照 scope 退回檔案層級。真正的缺口會得到 `SURVIVED`（exit 1，仍然看得到）；盲點的情況則由真正執行它的測試判定，不會報出假的缺口。
   - 記錄器整體沒啟動（沒有 `started-*`）時，是 § 2.4 的整體退回，不在這條規則內。
3. 被改的行有任何一行在空 context 執行過（import 時執行的 module 層、`def`、decorator、預設值）：一樣退回檔案層級，原因寫 `lines of <path> run outside a test`。這類行屬於所有 import 它的測試，記錄無法歸屬。
4. 其餘：判定測試是 baseline 中執行過任一被改行的測試，依 baseline 順序。一個都沒有就是 `NOT_COVERED`（§ 4）。

mutant 自己的 `tests`（Owner 11-16「檔案/目錄縮小」）：

- 檔案或目錄項目：縮小到其中執行過被改行的測試，與 selector 挑出的一樣處理。
- nodeid（含 `::`）與 pytest option（`-k`、`-m` 等）：原樣保留，接在縮小後的清單後面。作者點名到單一測試，就是要它判定。

所以 scope 原文「plus its own `tests`」在本設計中是指：自己 `tests` 中的檔案與目錄先依行記錄縮小，再加上去。

每個 mutant 的結果寫進 `<scratch>/mutants-covered.json`，供 reviewer 稽核：label、被改的行（每個 path 的行範圍）、選出的測試，或退回的原因，或 `not_covered`。`<scratch>/mutants-selected.json`（檔案層級）保留不變。

`NO_TESTS`（baseline 前，selector 與自己的 `tests` 都給不出測試）不變。

### 3.3 命令列長度

測試以識別逐一傳給 pytest。Windows 命令列上限是 32 767 字元；總長超過 30 000 字元時改用 pytest 的 `@argfile`（pytest 8.2 起；`adapters/python` 鎖在 8.3.5），檔案為 `<scratch>/lines/<NNN>-<label>.args`。pytest 以 argparse 的 `fromfile_prefix_chars` 讀取，每行一個參數，不經 shell 解析，所以 nodeid 中的空白與引號原樣傳入。

測試：一個 nodeid 含空白與引號的參數化測試經 `@argfile` 傳給 pytest 並被執行；選擇在 30 000 字元的兩側分別產生 inline 與 argfile 兩種命令列。

## 4. `NOT_COVERED`

- 定義：每個被改檔案都有記錄列（記錄器觀察到它），而且被改的行沒有任何 baseline 測試執行過（§ 3.2 規則 4）。檔案沒被觀察到的情況是規則 2 的退回，不是 `NOT_COVERED`。
- verdict 行：`NOT_COVERED <label> -> no baseline test runs <path>:<a>-<b>[, ...]`。不跑 pytest，所以沒有 stage-time 行。
- 它是測試缺口，計入 survivor：結尾行格式不變，`done: M mutants, S survived <labels>` 的 `S` 與 labels 都包含 `NOT_COVERED` 的 mutant，exit 1。哪些是 `NOT_COVERED` 由各自的 verdict 行看出。中止時 `N of M` 的 `N` 也計入印出 `NOT_COVERED` 的 mutant。
- 讀結尾行的只有 spec 與 `shared/skills/atc-review/references/mutants.md`（已 grep：程式碼中沒有 parser）。
- `NOT_COVERED` 是缺口的下界：記錄不全時，一個其實有測試執行到的 mutant 也可能被判 `NOT_COVERED`（§ 5），但被判 `NOT_COVERED` 的 mutant 一定沒有被記錄到的測試執行過它的行。

## 5. 正確性：誤差往哪個方向

`KILLED` 不受選擇影響：`_verdict` 只有在 pytest exit 1 且有 `FAILED` 行時才判 `KILLED`（assertion 規則另要求 junit 中全是 assertion），而失敗必須在 mutant 下真的發生。判定測試變多或變少都不會無中生有出 `KILLED`。

記錄的誤差只會讓缺口更顯眼：

- 記錄多了（例如單行 `if x: raise E` 的 `raise` 沒執行，但整行被記為已執行）：mutant 被跑，得到 `SURVIVED`，仍 exit 1。
- 記錄少了：判定測試變少，真正能 kill 的測試可能被漏掉，結果是 `SURVIVED` 或 `NOT_COVERED`，兩者都 exit 1，reviewer 必須處理。

記錄器看不到的情況（盲點）：

- `-I` 或 `-E` 啟動的子行程（`PYTHONPATH` 被忽略）；
- 測試自己組出不含 `PYTHONPATH` 或 `ATC_LINES_*` 的環境；
- 舊 export 中的巢狀 testkit run（§ 2.2）；
- 不執行而是讀取原始碼的測試（靜態檢查、AST 掃描、`read_text`）：它們從不執行被改的行，所以不會被選上，自己 `tests` 中點名的檔案也會被縮掉（§ 3.2）。ATC-0052 的 23 個 mutant 沒有這種情況。要讓這類測試判定，在 mutant 的 `tests` 寫 nodeid，或用 `-- TEST...`。

session 範圍的 fixture 只在第一個用到它的測試 setup 時執行，它執行的行只歸屬那個測試。若 mutant 改的是這類行，而錯誤只會在後面的測試中顯現，縮小後的選擇可能漏掉那些測試，得到 `SURVIVED`。方向安全，但不保證與檔案層級選擇的結果相同。

## 6. 量測

writer 跑量測（Owner 11-16「writer 跑」）。這是效能量測，不是檢驗本 task 的 guard；本 task guard 的 strict mutant 由 reviewer 寫與跑。reviewer 會獨立讀兩份 log 的 `done:` 行與 verdict 行，核對驗收，才給 PASS。

### 方法

- 輸入：ATC-0052 reviewer 的 23 個 mutant（`ATC-0054-input-atc0052-all-mutants.json`），對 base 9f06f6577172903aac1624defb4f00034b5a7cf3 的 export。所有數字都是在這個 base 上、本 task rebase 到 0e7c123 之前量的。
- **舊選擇法** 用同一份程式碼（實作 commit），但讓 mutant run 不帶 `--lines`，即 ATC-0052 的檔案層級選擇。已安裝的 release v0.6.0 早於那個選擇邏輯，不能代表舊選擇法。
- 因為兩邊的 baseline 測試完全相同（510 passed、2 skipped），舊選擇法的 baseline 就是「同一份程式碼、記錄器關閉」的 baseline。這取代了原本計畫的第 1、3 次 run。
- **新選擇法** 是 `atc test ATC-0054 --mutants … --sha 9f06f65…`（帶 `--lines`）。
- 兩次都在同一台機器、Owner 重開機之前跑。舊選擇法在第 22 個 mutant 後，因 Owner 重開機而停止。第 23 個 `R-selector-host-env` 的舊數字取自同一機器狀態下較早的 chunk 量測（SURVIVED，279 個測試，246.0 s）；判定測試只由 mutant 本身決定，所以與整批時相同。重開機後依 coordinator 指示不重跑。
- log（side-session notes 資料夾）：`ATC-0054-measure-old-all.log`、`ATC-0054-measure-new-all.log`、`ATC-0054-measure-old-5.log`、`ATC-0054-measure-new-5.log`；新選擇法每個 mutant 的行與測試在該次 scratch 的 `mutants-covered.json`。
