## 3. 機制

### 3.1 一個 memo，放在 `git_preflight`

- `git_preflight` 加一個每次 invocation 一份的 memo，用 `contextvars.ContextVar` 持有，`gp.memo()` 是啟用它的 context manager。
- 啟用的地方只有兩個入口：`git_integrate._main`（`atc integrate` 與 `--check`）與 `git_integrate.run_candidate`（`atc test --candidate`），各包住整次 invocation。
- 沒有啟用時，`git()` 與現在完全相同，所以 `close_out`、`push`、`task_records` 的 CLI 等其他命令不受影響。
- 三個 git wrapper 都走同一個底層 `gp.run_git(repo, args, env, input)`，memo 只在這一層：
  - `gp.git`（`git_integrate`、`task_authority` 也用它）。
  - `task_records.git`（`main_prefix` 走這裡，405 次）。
  - `integration_slot._git`（`common_dir` 走這裡）。
  - 三者各自的 env 處理與錯誤型別（`GitError`、`Refusal`、`RuntimeError`）不變。
- 快取的 key 是（wrapper、repository、argv、stdin、傳給 git 的 env 裡所有 `GIT_*` 項）。
  - wrapper 在 key 裡，因為三者的解碼不同（`task_records.git` 用 `errors="replace"`），同一個 argv 的答案不一定相同。
  - env 在 key 裡，所以 env 處理不同的呼叫不會互相拿錯答案。
  - 所以 `integration_slot` 與 `git_preflight` 各問一次 `--git-common-dir`。
- 值是整個 `CompletedProcess`，呼叫端照舊讀 `returncode`、`stdout`、`stderr`。
- 不變式：一次 invocation 裡，會改 ref、`HEAD`、index 或 worktree 紀錄的程式碼，都經過 `gp.run_git`，或在改完後明確呼叫 `gp.memo_invalidate()`。
- invocation 路徑上不經過 `gp.run_git` 的 git 呼叫與檔案操作，以及各自為何不破壞不變式：

| 呼叫 | 做什麼 | 為何安全 |
| --- | --- | --- |
| `task_records.read_blob_bytes`（自己的 `subprocess.run`） | `cat-file --batch` 讀 blob | 唯讀 |
| `git_integrate._checkout_digest` :635 | `cat-file --filters <tree>:<path>` | 唯讀 |
| `atc_testkit.elapsed.project_of` :84 | 沒有 `ATC_PROJECT` 時問 `--git-common-dir` | 唯讀；`_reused` 傳入 `testkit_inputs` 的 project，通常不呼叫 |
| `atc_testkit.inputs.common_directory` :167 | 問 `--git-common-dir` | 唯讀 |
| `managed_worktree.git`、`content._git` | 這兩個模組的 git | `load_workspace`、`root_project`、`infer_project` 只讀 `workspace.yaml` 與路徑，不呼叫它們；量測裡 invocation 內沒有出現 |
| `scratch.forget_worktree`（`_remove_candidate` :214） | 候選目錄已不在時，直接刪 `<common>/worktrees/` 下的管理目錄，改變 `worktree list` 的答案 | 之後明確呼叫 `gp.memo_invalidate()` |
| verifier（另一個行程） | 可能動到候選 checkout | § 3.3 第 3 點 |

- 唯讀的繞過呼叫不必進 memo：量測裡它們在一次 invocation 內不重複。

### 3.2 分層

argv 的形式決定層，表在 `git_preflight` 的一處。表裡沒有的形式一律不快取。

| 層 | 形式 | 何時失效 |
| --- | --- | --- |
| object | 每個 revision 運算元都是 40 位 SHA 的：`rev-parse --verify --quiet <SHA>^{commit\|tree}`、`rev-parse <SHA>^1 <SHA>^2`、`show <SHA>:<path>`、`cat-file -p\|-t <SHA>[:<path>]`、`merge-base`、`merge-base --is-ancestor`、`rev-list`（`--count`、`--reverse`、`--merges`、`--not`）、`log`、`diff --name-only`、`ls-tree`、`merge-tree --write-tree` | 不失效 |
| repository | `rev-parse --show-toplevel`、`rev-parse --path-format=absolute --git-dir --git-common-dir`、`rev-parse --path-format=absolute --git-common-dir`、`remote` | 不失效 |
| ref | ref 名稱的 `rev-parse --verify --quiet <name>^{commit}`、`show <ref>:<path>`、`for-each-ref`、`branch --show-current`、`status --porcelain`、`worktree list`、`rev-parse --disambiguate`、`diff --check`，運算元含 ref 名稱的 object 形式（例如 `merge-base main <SHA>`），帶 ref 集合、reflog、index 或 working tree 旗標的形式（`--all`、`--branches`、`--tags`、`--remotes`、`--glob`、`--exclude`、`--reflog`、`-g`、`--bisect`、`--fork-point`、`--cached`、`--no-index`），只有一個 revision 的 `diff`，以及沒有 revision 運算元的形式（例如 `log -1`，讀 `HEAD`） | § 3.3 |

- object 層成立的理由：40 位 hex 在 git 裡一律當 object ID 解析，不會被同名的 ref 蓋過；object 以內容定址，它的 commit、tree、祖先關係與檔案內容不會變。
- object 層只認表裡的形式：旗標會讓答案依 ref 集合、reflog、index 或 working tree 而變的（`rev-list <SHA> --not --all`、`diff --cached <SHA>`），即使運算元都是 SHA 也放 ref 層；只有一個 revision 的 `diff` 比的是 working tree。
- `diff --check` 放在 ref 層：它從 working tree 讀 `.gitattributes`，invocation 自己的 `merge --ff-only` 會改 working tree。它只在 `check()` 的 `diff_check_warning` 問一次，量測裡沒有重複，放哪一層都不影響收益。
- repository 層只快取 exit 0 的答案；失敗的（例如 `task_records.toplevel` 以 `check=False` 問 `--show-toplevel`）不快取，下次照問。
- 只有確定的答案進 object 層：exit 0，以及 `merge-base --is-ancestor` 的 exit 1（兩個 object 都在時，1 就是「不是祖先」）。其餘的失敗（例如 object 還不在，`fetch` 之後可能就在了）放進 ref 層，跟著 ref 一起失效。
- 用 stdin 的讀取（`cat-file --batch`、`rev-list --stdin`、`diff-tree --stdin`、`patch-id`）不快取也不觸發失效；量測裡它們每次 invocation 不到 1 次，沒有重複。
- 同一件事的兩種拼法（`topic` 與 `refs/heads/topic`、`refs/heads/main:AGENTS.md` 與 `<main SHA>:AGENTS.md`）是不同的 key，各問一次。

### 3.3 ref 層的失效

ref 層代表「這一段快照裡 ref 與 working tree 的樣子」。下列任何一點都會清掉整個 ref 層（所有 repository 的；候選 worktree 與 main checkout 共用 refs）：

1. **經過 `gp.run_git` 的表外呼叫**：`fetch`、`update-ref`、`merge`、`worktree add`/`remove`、`commit-tree`，以及之後新增而沒進表的命令。不認得的命令當成寫入，所以經過 `run_git` 新加的寫入不會漏掉失效；不經過它的寫入靠 § 3.1 的不變式與明確的 `gp.memo_invalidate()`，由 § 5 的 test 守住。
2. **一次 run 開始**：`check()`、`verify()` 的開頭，與 `integrate()` 拿到 Integration Slot 之後。
   - `resolve` 讀到的值只留在 `Target` 裡供比對；`merge_preflight` 一定從新讀的 ref 開始。
   - 這保住兩個現有的檢查：`integrate` :1173 與 `verify` :2024 的 `REF_DRIFT`（main 在讀完 verification section 之後移動）。`test_main_moved_since_its_declaration_was_read_is_ref_drift` 與 `test_atc_verify_stops_when_main_moved_since_its_declaration_was_read` 就是在 `resolve` 之後移動 main。
   - 在 `integrate` 裡也涵蓋等 slot 的時間：另一個 `atc integrate` 在這段時間移動 main，slot 之後的讀取看得到。
3. **verifier 結束**：`_run_verifier` 回來之後，:797、:799 讀到的是 verifier 之後的候選。
4. **刻意的漂移檢查**：§ 2 列的 :1178、:1203、:1205、:1207 以 `fresh=True` 呼叫（`gp.rev(..., fresh=True)`、`gp.git(..., fresh=True)`），不讀快取、讀完寫回。

不經過 `run_git` 的外部寫入（Owner 手動的 git、另一個行程）只在 2、4 被看到，這與現在相同：現在也只有那幾個檢查負責偵測別人移動 ref。

### 3.4 不變的東西

- 每個 STOP、ERROR 的 token、detail 與 exit code 不變；`--json` 的鍵與值不變。
- 寫入的順序與次數不變；只少掉讀取。
- `shared/conformance/CLI.md` 規定的輸出不受影響，不需要版本號變更。

## 5. 測試

task 是 `tests: strict`。實作步驟加的 test：

- memo 本身（`test_git_preflight.py`）：
  - 沒有啟用時不快取：同一個查詢跑兩次就啟動兩次。
  - § 3.2 表裡每一層各一個形式命中；表外的形式不快取。
  - object 層的失敗答案在寫入之後重問；`--is-ancestor` 的 exit 1 不重問。
  - 表外的呼叫清掉 ref 層、不動 object 與 repository 層；`fresh=True` 不讀快取。
  - env 的 `GIT_*` 項不同時不共用答案。
  - repository 層的失敗答案不快取。
  - 兩個 wrapper 問同一個查詢、解碼不同（`task_records` 用 `errors="replace"`）時各自問一次。
  - `gp.memo_invalidate()` 清掉 ref 層。
- § 3.1 的不變式：
  - 一次 `integrate` 與一次 `atc test --candidate`，包住 `subprocess.Popen` 記下每個 git 子行程與呼叫端，斷言不經過 `gp.run_git` 的都在 § 3.1 表裡、且 argv 是唯讀形式。新增的繞過呼叫會讓它失敗。
  - 候選目錄已被刪掉時，`_remove_candidate` 走 `forget_worktree` 之後，memo 的 ref 層是空的。
- 每個失效點各一個 test，證明快取沒有讓它變成永遠通過。缺的補上：
  - 已有，都在 `test_git_integrate.py`：:1173（`test_main_moved_since_its_declaration_was_read_is_ref_drift`）、:2024（`test_atc_verify_stops_when_main_moved_since_its_declaration_was_read`）、:1178（`test_main_moved_after_preflight_stops`）、:1205（`test_no_ff_parents_mismatch_fails_verification`）、寫入之後的 :1231（`test_a_stopped_update_is_recorded_when_another_request_drops_its_ref`）。
  - 新增，這幾個檢查現在都沒有 test 讓它們觸發：verification 期間 source branch 移動（:1203）、verification 期間 checkout 變髒（:1207）、verifier 移動候選的 `HEAD`（:797）、verifier 弄髒候選（:799）、等 slot 時另一個行程移動 main（slot 之後的失效）。
- 新增的漂移 test 在 `tests/test_integrate_memo.py`。每個 `fresh=True` 讀取（:1178 的 main 與 `HEAD`，:1203、:1205、:1207）各有一個 test：在檢查之前把同一個查詢的答案放進 memo 的當前段落，再從 `gp.run_git` 之外改 ref 或 working tree，所以只有 `fresh=True` 讓檢查看到改變。

## 7. 不採的方案

- **把 ref 解析併成一次查多個（`rev-parse` 帶多個參數、`cat-file --batch`）作為主要機制。** 每個呼叫端得事先知道之後要問什麼，要改寫 `resolve`、`merge_preflight`、`task_authority` 的呼叫順序。memo 不改呼叫順序就消掉重複。memo 之後一次 `integrate` 還有約 36 次 ref 與 object 讀取，其中哪些能併，要另外量。
- **把解析過的值一路當參數傳下去（擴充 `Target`）。** 要改 `git_preflight`、`task_authority`、`task_records` 十幾個函式的簽名，每個重複各自處理，等於每個問題一套機制；刻意重讀的地方也更難審。
- **行程層級的 `functools.lru_cache`。** 沒有失效：自己寫入之後會讀到舊值，in-process 的 test 在同一個行程裡跑很多次 `atc integrate`，也會跨 invocation 讀到別的 repository 狀態。
- **跨 invocation 的磁碟快取。** ref 在兩次 invocation 之間由別人移動是常態，失效無從判斷。
- **統一同一件事的拼法（`topic` 改成 `refs/heads/topic`）。** 同名的 tag 存在時，短名稱會解析到 tag，改成全名會改變行為。這是另一個行為問題，每次 invocation 只差約 1 次，不放進本 task。
