# ATC-0053 設計：hook 自己維護 table；`atc guard --install` 只寫 harness entries

範圍見 `.atc/tasks/ATC-0053.yaml`。Owner 11-16 的裁決：這項改動在下一次發版之前落地，發版等它。

## 1. 現況與目標

`atc guard --install` 目前做兩件事：

- 寫 harness entries；
- 把 workspace policy、各 project policy 和 workspace map 組成 `~/.atc/enforcement/pretooluse.json`。

只要 table 的任何一個輸入變了，table 就過期：裝了新的 `atc`、policy 改了、`atc add`/`atc remove`。之後 `atc doctor` 會一直報 drift，直到 Owner 重跑。

目標是讓 `atc hook` 從經過 review 的輸入自己組 table，用 key 快取。`--install` 變成每台主機只跑一次的步驟，只寫 harness entries。

## 2. 輸入解析

一次組合（compose）讀進下列輸入，順序與今天的 `hook_table` 相同。

| # | 輸入 | 從哪裡讀 | 進 key 的形式 |
| --- | --- | --- | --- |
| 1 | workspace map | `--workspace` 指定的檔案（hook entry 帶的，見 § 7） | 檔案 bytes 的 sha256 |
| 2 | workspace policy | 見下方 2a/2b | 2a：commit SHA；2b：檔案 bytes 的 sha256 |
| 3 | 每個已註冊 project 的 policy | map 裡 `projects.<name>.repo` 的 `refs/heads/main` 所指 commit，讀 Git objects 的 `policies/<kind>.yaml` | 每個 repo 的 main SHA |
| 4 | composer | 正在執行的 `atc` 本身的組合程式碼與 schemas | 檔案指紋（§ 3） |

**2a. governance checkout 主機**（例如本機，workspace 目錄本身就是 ATC repo）：workspace policy 從 content repository 讀，也就是 `content.repository(root, fetch=False)`，與 sync 用同一條規則：

- 有 `governance_checkout` 時，讀它的 `refs/heads/main`；
- 否則讀 `~/.atc/content/<owner>/<repo>.git` 的 `refs/heads/main`。

workspace 目錄是 governance checkout、map 卻沒寫 `governance_checkout: .` 時，與 sync 一樣停在 `GOVERNANCE_CHECKOUT_UNSET`。（本機目前的 `workspace.yaml` 就缺這一行，見 § 10。）

**2b. 一般 consumer workspace**：workspace policy 是 sync 以 `create-only` 寫進 workspace 目錄的 `policies/hard-deny.yaml`（`atc-manifest.yaml` 的 `workspace-policy`）。它跟 map 一樣是機器本地、不在 Git 裡的檔案，所以處理方式比照 map：

- 檔案 bytes 的 hash 進 key；
- 檔案加進 protected 清單（§ 9）。

**Project policy 的讀法。**

- 對 `refs/heads/main` 的 commit，每個 repo 開一次 `git cat-file --batch`，依 `policies.KINDS` 讀四種 policy 檔。
- 檔案內容在記憶體裡交給 `policies` 驗證：新增 `policies.load_texts({kind: text})`，`load(directory)` 改成呼叫它，所以 schema 檢查和 contradiction 檢查都跟今天一樣。
- 某個 project 的 main 上沒有 `hard-deny.yaml`：那個 project 不貢獻 policy 規則，但它的 state、worktrees 照樣進 table。這與今天跳過缺檔的行為相同。

**不會進 table 的東西。**

- worktree 裡的編輯、canonical checkout 裡尚未 commit 的編輯：都不讀，只讀 main 的 Git objects。
- topic branch 上的 commit：只認 `refs/heads/main`，不認 `HEAD`。

**Git 子行程的環境。** hook 會繼承 harness 的環境變數，所以呼叫 git 前要清掉 `GIT_DIR`、`GIT_WORK_TREE`、`GIT_INDEX_FILE`、`GIT_OBJECT_DIRECTORY`、`GIT_ALTERNATE_OBJECT_DIRECTORIES`、`GIT_COMMON_DIR`、`GIT_NAMESPACE`（governance `GIT_WORKFLOW.md` § Git environment in hooks and tests），並帶 `-C <repo>`。

**命中路徑讀 main SHA 不開 git。** 依序讀：

1. `<gitdir>/refs/heads/main`（loose ref）；
2. 讀不到就找 `<gitdir>/packed-refs` 裡 `refs/heads/main` 那一行。

`<gitdir>` 是 repo 的 `.git` 目錄；bare cache 則是 repo 本身。只有遇到下列三種情況，才退回 `git rev-parse --verify -q refs/heads/main^{commit}`：

- `.git` 是一個 `gitdir:` 檔；
- `config` 宣告了 `extensions.refStorage`；
- ref 檔的內容是 symbolic ref。

## 3. 快取：key 與位置

**位置。** 放在 `~/.atc/enforcement/`，這個目錄本來就在 protected 清單裡。每個 map 一組檔案，以 map 絕對路徑（long form、case-folded）的 sha256 前 16 個 hex 字元 `<m>` 命名：

- `table-<m>.json`：快取。內容是 `{"version": 2, "key": {...}, "table": {...} | null, "failure": {...} | null, "retained": {...}, "atc": {"version", "commit"}}`。`table` 的格式就是今天的 version 1 table，引擎直接讀它。
- `compose-<m>.lock`：組合時拿的鎖（§ 5）。

一台主機上的每個 map 各有一份，所以為另一個 map 組出來的 table 永遠不會碰到真正 map 的那份（§ 9 G22）。

**Key** 是下面這些欄位組成的 JSON 物件，全部相等才算命中：

- `map`：map 檔 bytes 的 sha256。
- `workspace_policy`：2a 時是 `{"repo": <路徑>, "main": <SHA>}`，2b 時是檔案 bytes 的 sha256。
- `projects`：`[[name, repo 路徑, main SHA], ...]`，依 map 的順序。
- `composer`：一串 sha256，涵蓋正在執行的 `atc_cli/scripts/{generate_enforcement,policies,globs,shell_words,write_targets,pretooluse_hook}.py` 和 `atc_cli/schemas/hard-deny.schema.json` 的 `(相對路徑, size, mtime_ns)`。`uv tool install` 會換掉這些檔案，所以裝了新版本，key 就會變。key 不直接放版本字串，因為在 worktree 的開發環境裡，同一個版本號可能對應不同的程式碼。`atc` 欄位另外記錄組合當時的版本與 `direct_url.json` commit，只供回報用。
- `format`：table 格式的版本，現在是 2。

命中時，hook 從快取裡讀出 project 清單，再逐一讀它們的 main SHA。這樣做是安全的：map hash 沒變，代表 project 清單也沒變，所以命中路徑完全不必解析 YAML（hook 只能用標準函式庫）。map hash 一變就直接視為未命中，此時才 import yaml 和 jsonschema 去組合；tool 環境裡本來就有這兩個套件。

## 4. 每次 tool call 的成本

以下是 11-16 在本機（Windows 11）實測的數字，每項取 15 次的中位數。已安裝的 0.6.0 還沒有 `atc hook`，所以基準是把各段分開量：

| 量測 | 中位數 |
| --- | --- |
| tool 環境的 python 空跑（`-c pass`） | 29 ms |
| 引擎直接跑（main 的 `pretooluse_hook.py` 加上現有的 table，一個 Bash payload） | 71 ms |
| `atc --version`（0.6.0 的 console entry） | 100 ms |
| 命中路徑原型：map sha256、5 個 repo 的 main ref、7 個 composer 檔的 stat | 0.95 ms（行程內） |
| 載入 table JSON（59 條規則） | 0.19 ms（行程內，與今天相同） |
| 未命中：`git show` ×20 + import yaml/jsonschema + 組合 | 668 ms（import 91、git 455、組合 51） |

結論：

- **命中時**，每次呼叫只多出約 1 ms，比行程啟動時間的雜訊還小。
- **未命中時**，把 20 次 `git show` 換成每個 repo 一次 `cat-file --batch`（5 個行程），預估約 300 ms。每次 key 改變，整台主機只付一次，遠低於 entry 的 `timeout: 10`。
- **不再開 `uv tool dir` 子行程**（它的 timeout 是 60 s）。要保護的 tool 環境改成：組合時正在執行的 `sys.prefix`，條件是它含有 uv 寫的 `uv-receipt.toml`。

## 5. 組合、ratchet 與 fail closed

### 5.1 組合流程（未命中）

1. 取得 `compose-<m>.lock`，最多等 8 s（低於 10 s 的 timeout）。拿到鎖後重讀快取，如果別的行程已經寫好相同的 key，直接用它的結果。
2. 讀入全部輸入，組出 fresh table（`hook_table` 的邏輯不變，只是改讀 § 2 的來源）。
3. 套用 ratchet（§ 5.2）得到 effective table。
4. 寫進暫存檔再 `os.replace`，然後放鎖。

鎖用 `msvcrt.locking`／`fcntl.flock` 鎖住鎖檔裡的一個 byte，持有者結束時 OS 會自動釋放，所以不會有殘留的鎖。

### 5.2 Ratchet：自動組合只會收緊

這是本設計的核心，需要 Owner 裁決（§ 11）。新的 effective table = 上一份 effective table ⊕ fresh table：

- `commands`、`filesystem`、`worktrees`、`protected`：取聯集。key 沿用今天的去重 key：command 用條件 JSON，filesystem 用 `[glob, modes, scope]`。同一個 key 的 `reason`/`source` 以 fresh 的為準。
- `write_roots` 是 allowlist，所以取交集：
  - fresh 的某個根，只有位在上一份某個根之內時才保留；
  - 上一份的某個根，只有位在 fresh 某個根之內時才保留（`within` 用 `shell_words.within`）。
- 只出現在上一份、不在 fresh 裡的項目，計入 `retained`：保留下來的規則數，以及 map 有、但尚未生效的 write roots。doctor 和 guard 會回報它（§ 6）。

理由：輸入裡有兩樣是 agent 不需要 Owner 就能動到的：

- 本地的 `main` ref（`git commit` 在 canonical checkout 的 main 上、`git update-ref`、直接寫 `.git/refs`）；
- `atc init --force` 改寫 map。

只要有 ratchet，這兩條路最多只能把 table 收緊，永遠放鬆不了（§ 8）。放鬆是很少見的 Owner 動作：拿掉一條規則、`atc remove`、加一個 write root。這時由 Owner 跑：

```text
atc guard --reset
```

它會刪掉 `table-<m>.json`，也刪掉舊版 `pretooluse.json`，下一次 hook call 就只用 fresh table 重新開始。`--reset` 和 `--install` 一樣是 hard-deny（§ 7）。

第一次組合時，如果沒有快取但有舊版 `pretooluse.json`，就拿它當「上一份」，所以遷移也不會放鬆（§ 10）。

### 5.3 Fail closed 與訊息

組合失敗時，hook 一律 deny 每一個 call，與今天 table 壞掉時一樣（範圍要求）。失敗會連同 key 寫進快取的 `failure` 欄位，所以 key 不變時後續 call 直接 deny，不會每次重組；輸入一修好，key 就跟著變，下一次 call 自動恢復。

| 原因 | token | deny 訊息的重點（每則都以 `Refused: the PreToolUse hook cannot compose its table:` 開頭） | 修法 |
| --- | --- | --- | --- |
| map 不存在或讀不到 | `WORKSPACE_MISSING` | `<map> cannot be read (<err>)` | Owner 恢復 map，或重跑 `atc guard --install` 指向正確的 map |
| map 不是合法 YAML 或欄位錯誤 | `WORKSPACE_INVALID` | `<map>: <err>` | Owner 修正 map |
| policy 不合 schema 或互相矛盾 | `POLICY_INVALID` | `<label>@<sha7>: <problem>`，每個 problem 一行 | 在 topic 修 policy，經 review 後整合進 main |
| repo 沒有 main 或讀不到 | `MAIN_UNREADABLE` | `<label>: <repo> has no refs/heads/main (<err>)` | Owner 修 repo，或 `atc remove` |
| governance checkout 沒在 map 宣告 | `GOVERNANCE_CHECKOUT_UNSET` | 同 sync 的 detail | 在 map 加上 `governance_checkout: .` |
| 鎖等超過 8 s | `COMPOSE_BUSY` | `another process is composing` | 重試這個 call；不會寫進 `failure` |
| 快取讀不到或不是合法 JSON | （不算失敗） | 當作未命中，重新組合 | — |
| 引擎本身出錯 | 今天的訊息 | 今天的訊息，`REPAIR` 改為 `atc doctor` | Owner 跑 `atc doctor` |

每則訊息的結尾都是：`Every session is blocked until this is fixed; the Owner runs atc doctor from their own terminal for the cause.`

agent 在 deny 期間仍然可以用 Read/Grep（不在 matcher 裡）去看原因，並把訊息轉給 Owner。

## 6. `atc doctor` 與 `atc guard`（check）回報什麼

兩者都在記憶體裡組合，絕不寫快取（doctor「不改任何東西」）。各列一行：

| 檢查 | READY | 其他狀態 |
| --- | --- | --- |
| `pretooluse entries` | 兩個 harness 的 entry 都恰好是 rendered group，且帶著這個 map 的 `--workspace` | `ERROR ENTRY_MISSING`／`ENTRY_OUTDATED`（例如舊 entry 沒有 `--workspace`，或指向別的 map）→ the Owner runs atc guard --install |
| `pretooluse table` | `composes; <n> rules; inputs root@<sha7>, <project>@<sha7>...`，再加上 `cached` 或 `recomposes on the next call` | `ERROR <token>: <detail>`，內容與 § 5.3 相同，附上修法 |
| `pretooluse retained` | 沒有 retained 時不列 | `WARN <n> rules kept from earlier inputs; write roots not in effect: <roots>; the Owner runs atc guard --reset to drop them` |
| `pretooluse legacy` | 不存在時不列 | `WARN <path> is the static table of an older entry; atc guard --reset removes it`（只在 entry 已經是新格式時列出） |

「table 和 policy 不一致」不再是 Owner 要處理的事項。cache 過期是正常狀態，下一次 call 會自己重組。

`atc guard` 的結束碼：

- `0` 代表 entries 都是最新、table 也能組合；
- `1` 代表 STOP，原因是 `ENTRY_MISSING`、`ENTRY_OUTDATED` 或 table 組合不出來（token 同 § 5.3）；
- `retained` 只列 WARN，不影響結束碼。

`--json` 欄位：`entries`、`table`（`composes`、`rules`、`inputs`、`cached`、`failure`）、`retained`、`legacy`。

`atc sync --check` 的 `report_hook` 改成只回報 entries 與「table 組合不出來」，仍然只回報，不讓 sync 失敗。

### 6.1 版本落差先行（version skew）

Owner 11-16 追加這一項。實例：ATC-0049 整合後，主機仍跑 0.6.0，`atc doctor` 報了 5 個 ERROR（各 project 的 integration drift、guard table），卻沒有一行說出根因：已安裝的 `atc` 比 workspace main 舊。

**比較對象。**

- 已安裝的一方：`release_pin.installed()` 的 commit 與 tag，加上 `atc_cli.package_version()`。
- workspace 的一方：`release_pin.history(root)`（content repository，不 fetch）的 `refs/heads/main`，含它的 release tag（`sync_project.merged_release_tags`）和 `atc-manifest.yaml` 的 `min_atc`。
- `adapters/python/pyproject.toml` 的版本只在發版時才改（main 上目前仍是 0.6.0），比不出未發版的落差，所以判斷以 commit 和 tag 為準，版本號只用在 `min_atc`。

**狀態**，依序判斷，第一個成立的就是結果：

| 狀態 | 條件 | 根因行 | 修法 |
| --- | --- | --- | --- |
| development install | `release_pin.editable()` 有值 | `READY`，不比較 | — |
| 沒有安裝紀錄 | `installed()` 是 None | 今天的 `WARN`，不比較 | 今天的 install 指令 |
| 無法比較 | 已安裝的 commit 不在 history repo 裡（例如 cache 還沒 fetch） | `WARN ATC_SKEW_UNKNOWN` | 跑一次 `atc sync`（會 fetch），或確認安裝來源 |
| `ATC_NOT_ON_MAIN` | 已安裝的 commit 不在 main 的歷史裡 | `ERROR` | 安裝 main 上的 release tag |
| `ATC_BELOW_MIN` | main 的 `min_atc` 高於已安裝的版本 | `ERROR` | 安裝 main 上最新的 release tag（附完整指令） |
| `ATC_BEHIND_RELEASE` | main 上有比已安裝 commit 更新的 release tag | `ERROR` | `release_pin.install_command(url, <最新 tag>)` |
| `ATC_BEHIND_MAIN` | 沒有更新的 tag，但已安裝 commit 之後，main 有 commit 改到 `adapters/python/`、`atc-manifest.yaml`、`shared/` 或 `policies/` | `WARN`，附 commit 數 | 「the Owner tags and installs a release when ready」；發版節奏由 Owner 決定，所以這只是 WARN |
| 一致 | 以上皆非 | `READY installed atc is main's latest release <tag>` | — |

`ATC_BEHIND_MAIN` 有路徑過濾，因為 main 上經常有只改 task record 或 docs 的 commit，那些不會造成落差。

**輸出。**

- 這一行取代今天的 `installed atc` 檢查，排在 `workspace root` 之後、其他檢查之前，不論有沒有 `-v` 都印。
- 狀態屬於 `ATC_NOT_ON_MAIN`、`ATC_BELOW_MIN`、`ATC_BEHIND_RELEASE`、`ATC_BEHIND_MAIN` 之一時，下列「衍生」檢查原本的 `ERROR` 改成新狀態 `NOTE`，detail 前面加上 `follows from installed atc:`，並且緊接在根因行之下印出：
  - `workspace-managed adapters`；
  - `projects.<name>.integration`；
  - `projects.<name>.testkit`；
  - `projects.<name>.pin`，只限 project 比已安裝 release 新的那一種（`release_pin.ahead`）。
- `NOTE` 不算 ERROR 也不算 WARN。verdict 行多一個計數：`… , N note(s)`。`--json` 的 check 物件多一個 `"follows": "installed atc"`。
- 結束碼：`ATC_NOT_ON_MAIN`、`ATC_BELOW_MIN`、`ATC_BEHIND_RELEASE` 這三種落差只算一個 ERROR，結束碼 1，原因就是根因行；`ATC_BEHIND_MAIN` 加上 notes 的結束碼是 0。
- `pretooluse table` 的組合失敗**不**降級：hook 確實會擋住所有 call，所以它仍是 `ERROR`。有落差時，detail 末尾加上 `the installed atc is older than main; installing the latest release may fix it`。`atc guard`（check）的同一項也這樣處理。hook 的 deny 訊息碰到 `POLICY_INVALID` 時，固定附一句「if `atc doctor` reports the installed atc older than main, installing the latest release may be the fix」，不在 hook 裡跑 git。

代價：有落差時，真正獨立存在的 drift 也會暫時以 NOTE 顯示。每個 NOTE 都保留完整的 detail，裝上 release 之後若仍存在，就會回到 ERROR。

## 7. CLI 變更

- **`atc hook --harness X --workspace FILE`**：新的正式形式。由 map 組合並使用快取。
- **`atc hook --harness X [--table FILE]`**：維持今天的 static 模式，讀一份固定的 table，不組合。conformance、測試，以及升級後還沒重跑 `--install` 的舊 entry 都靠它（§ 10）。`--workspace` 和 `--table` 不能同時給。
- **`atc guard --install`**：
  - 先在記憶體裡組合；組合失敗就以 § 5.3 的 token 拒絕，而且不寫任何 entry，避免 Owner 裝上一個會擋住所有 call 的 hook。
  - 組合成功後，只寫兩個 harness 的 entry：`atc hook --harness claude --workspace "<map 的 forward-slash 絕對路徑>"`。
  - 不寫 table，也不再接受 table 目錄的參數（`engine_command` 的 `--table` 分支移除）。
- **`atc guard --reset`**：Owner 專用，見 § 5.2。
- **`atc add`**：註冊前先組合「加上這個 project 之後」的 table；組合不出來就以 `POLICY_INVALID`／`MAIN_UNREADABLE` 拒絕，map 不變。這樣 agent 跑 `atc add` 時，不會因為一個 policy 壞掉的 project 擋住整台主機。
- **hard-deny 的增修**：這些都是在收緊。規則的 schema 不變，只是 `policies/hard-deny.yaml` 多了幾條：
  - `atc-guard-install`：`with_args` 改成 `[--install, --reset]`，id 和 reason 一併改成涵蓋兩者；
  - `atc-hook-workspace`：`[atc, hook]` 搭配 `with_args: [--workspace]`。只有 harness 可以觸發組合（harness 跑 entry，不經過 tool call，所以不受影響）；
  - `atc-init-force`：`[atc, init]` 搭配 `with_args: [--force]`，因為重寫 map 是 Owner 的事；
  - `uv-tool-install`／`uv-tool-upgrade`／`uv-tool-uninstall`：`[uv, tool, install|upgrade|uninstall]`。換掉 `atc` 就等於換掉 composer 和引擎；WORKFLOW 已經寫明「agents never install atc」，這條規則只是把那句話落實成技術限制。

## 8. Threat check：agent 不經 Owner 能跑的每一個指令

規則：只有 Owner 才能讓 table 變鬆。依 § 5.2，effective table 只會在 `--reset` 時變鬆，而 `--reset` 是 hard-deny。所以下表要證明的是兩件事：

- 每個指令能動到哪些輸入；
- 動到輸入的那些指令，最多只能讓 table 變緊。

| 指令（agent 可直接跑） | 動到的輸入 | 能否放鬆 |
| --- | --- | --- |
| Edit/Write/NotebookEdit/apply_patch、shell 寫入 | map、2b 的 workspace policy、快取目錄、composer 檔：protected，會被拒絕。worktree 或 canonical checkout 工作樹裡的 policy：不是輸入 | 否 |
| `git commit`、`git rebase` 等在 topic branch 上的操作 | 無，只讀 main | 否 |
| 在本地移動 `main`：canonical checkout 上的 `git commit`/`merge`/`reset`、`git branch -f main`、`git update-ref`、寫 `.git/refs/heads/main` | project/root 的 main SHA | 否，ratchet 只收緊（這是殘餘風險：可能把自己擋住；§ 11） |
| `git push` 到 main、`--force` 系列 | — | 已被 hard-deny（`git-push-main`、`git-push-force*`） |
| `atc task create/update/list/resume/close` | 無（只 commit 在 topic worktree，只刪 topic worktree/branch） | 否 |
| `atc test`（所有形式）、`atc integrate --check`、`atc push --check`、`atc remove --check` | 無（scratch、candidate） | 否 |
| `atc sync` | 會 commit 到各 project 的 main，但依 manifest 只寫 `.atc/`、`AGENTS.md` 的 pointer line、`CLAUDE.md`、skills，從不寫 `policies/`。對 workspace 只會 `create-only` workspace policy（已存在時不碰） | 否：policy blob 不變；main SHA 變了只會觸發重組 |
| `atc sync --check`、`atc doctor`、`atc guard`（check）、`atc checkout` | 無 | 否 |
| `atc add` | map 加入一個新 project（名稱已存在會拒絕） | 否：只增加規則；新的 worktrees/state 也只會收緊 |
| `atc init`（不帶 `--force`） | map 存在時拒絕（`WORKSPACE_EXISTS`） | 否 |
| `atc init --force` | 重寫 map | 新增 hard-deny；即使繞過，ratchet 也只會收緊 |
| `atc hook --table FILE` | 無，static 模式不寫快取 | 否 |
| `atc hook --workspace OTHER` | 寫 `table-<m'>.json`，那是另一個 map 的快取 | 新增 hard-deny；而且快取依 map 分開存，不影響真正 map 的那份 |
| `atc-maintain`（只在 worktree 跑）：`sync --root`、`validate`、`policies check`、`guard --policies/--out` | worktree 的檔案 | 否；`guard --hook-out` 已被 hard-deny |
| `uv tool install/upgrade/uninstall` | composer 和引擎 | 新增 hard-deny |

已知限制（不變）：hook 只讀 call 的文字，不是 sandbox。用 `python -c`、執行一支腳本檔等方式繞過 protected 清單（例如直接刪掉 `~/.atc/enforcement`），屬於 ENFORCEMENT § Known limits 的蓄意規避。即使如此，刪掉 ratchet 狀態後，table 也只會回到「目前輸入」組出的結果，不會比 main 加 map 更鬆。

## 10. 從今天寫出的 table 遷移

每台主機在裝好含這項改動的 release 之後，Owner 做一次：

1. **governance checkout 主機**：map 必須有 `governance_checkout: .`。本機目前的 `workspace.yaml` 沒有這一行，所以第一次組合會是 `GOVERNANCE_CHECKOUT_UNSET`。下一步的 `--install` 會先拒絕並給出修法，不會裝上一個會擋住一切的 hook。
2. **`atc guard --install`**：寫入帶 `--workspace` 的 entry。Codex 會在 `/hooks` 要求再信任一次，因為 entry 的文字變了。

在第 2 步之前，舊的 entry（`atc hook --harness claude`，沒有 `--workspace`）由新的引擎以 static 模式讀舊的 `pretooluse.json`，行為和今天一模一樣（table 會過期）。doctor 回報 `ENTRY_OUTDATED`。所以「先裝 release、晚點才跑 `--install`」不會出現保護的空窗。

第一次組合會把舊 `pretooluse.json` 當作 ratchet 的種子（§ 5.2）。之後那個檔案就不再被讀取；doctor 會以 WARN 列出它，Owner 想清掉時跑 `atc guard --reset`。

舊的 `atc-maintain guard --hook-out`、`--live-hook-table` 保留給維護者比對用，改從同樣的輸入組合（Git objects 加 map），而不是讀工作樹。
