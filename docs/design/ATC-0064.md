# ATC-0064 設計：release 工具、maintainer 的 releasing 文件與安裝前置檢查

範圍見 task record `.atc/tasks/ATC-0064.yaml`。§ 1 是 `atc-maintain release prepare`，§ 2 是 `atc-maintain release check`，§ 3 是 `docs/development/RELEASING.md`，§ 4 是安裝前置檢查，§ 5 是 AGENTS.md，§ 6 是 ATC-0060 的兩個 docs site 後續，§ 7 是測試，§ 8 是要 Owner 裁決的事。

## 1. `atc-maintain release prepare`

```text
atc-maintain release prepare <atc version> [--testkit <version>] [--min-atc <version>]
```

在 release task 的 worktree 執行（`atc-maintain` 本來就拒絕 canonical checkout）。三件事，只改 working tree，不 commit：

1. **版號。** 一個表列出每個釘版號的位置，`prepare` 改寫它們，`check`（§ 2）比對它們，兩者讀同一個表：

   | 檔案 | 位置 | 版號 |
   | --- | --- | --- |
   | `adapters/python/pyproject.toml` | `[project] version` | atc |
   | `adapters/python/uv.lock` | `agent-traffic-control` 套件的 `version` | atc |
   | `README.md` | § Status 的 `Version X,` | atc |
   | `README.zh-TW.md` | § 狀態的 `目前版本是 X` | atc |
   | `adapters/python/atc-testkit/src/atc_testkit/__init__.py` | `__version__` | testkit |
   | `adapters/python/atc-testkit/README.md` | `` `atc-testkit` X `` 與 `atc-testkit==X` | testkit |
   | `atc-manifest.yaml` | `min_atc` | 只在給 `--min-atc` 時改 |

   這張表就是 0.8.0 的 release commit（aaad973）改過的那 8 個檔扣掉 notes。`--testkit` 省略時 testkit 版號不動。`min_atc` 是判斷（§ 3），`prepare` 不猜，只照 `--min-atc` 寫。新版號必須大於上一個 tag 的版號，否則 exit 2。
2. **上一個 tag 以來整合的 task。** 從 `<git common dir>/atc/integrations.jsonl` 讀：取整合列（有 `candidate_sha`、`records_only` 不為 true），其 `commits` 有任何一個落在 `<last tag>..HEAD` 的，取其 `task`，去重、依整合時間排序。上一個 tag 是 HEAD 可達的最高 `v*` tag。同時以 § 2.3 的樹內規則算一次，兩者不同時印 `NOTE` 列出差異（例如 ledger 從別台機器來、或 records-only 的 task），不中止。
3. **notes 骨架。** 寫 `docs/releases/v<atc>.md`（已存在則 exit 2，不覆寫），內容是 § 2.2 要求的每一節，task 清單已填好 `- ATC-NNNN: TODO(release)`，判斷性的段落是 `TODO(release)` 加一行指向 RELEASING.md 對應節的說明。

輸出：每改一個檔一行 `UPDATED <path> <old> -> <new>`，最後 `WROTE docs/releases/v<atc>.md (<n> tasks)`。exit 0 成功，2 用法錯誤或拒絕。

## 2. `atc-maintain release check`

在 lint stage 執行：`.pre-commit-config.yaml` 新增 local hook `release-notes`，entry `uv run --quiet --locked --project adapters/python atc-maintain release check`，`pass_filenames: false`、`always_run: true`。always_run 是因為 task 覆蓋由 Git 範圍決定，不由本次改了哪些檔決定；它只跑幾個 `git` 指令，成本可忽略。`workspace-contract` hook 已經在 lint stage 跑 `atc-maintain`，所以 commit hook、`atc test ID --lint`、verifier 的候選 checkout 與 CI（`validate.yml`，`fetch-depth: 0`，有 tag）都能跑它。

### 2.1 兩種狀態

- **已發布**：HEAD 可達 `v<atc version>` 這個 tag。只檢查版號一致與 `min_atc`，以及 `docs/releases/v<atc>.md` 存在。兩次 release 之間的每個 commit 都是這個狀態。
- **發布中**：該 tag 不存在。atc 版號必須大於上一個 tag 的版號，並做 § 2.2 與 § 2.3 的全部檢查。

### 2.2 一律檢查

- 版號一致：§ 1 表中同一欄的每個位置相同；notes 第一行是 `atc X (atc-testkit Y)`，X、Y 等於兩個版號。
- `min_atc` ≤ atc 版號。
- `drift.py testkit-version` 併入這裡（testkit 的 dynamic version 與 README），`drift.py` 只留 `schemas`，hook `testkit-version` 移除：同一件事只留一個機制。

發布中另外檢查 notes 的必要節：

- `## Breaking`
- `## atc-testkit Y`：testkit 版號與上一個 tag 時（`git show <tag>:.../__init__.py`）不同時才必要
- `## Tasks`
- `## Upgrade`，其下 `### Projects`，且這一節有連到 `../TESTKIT.md#upgrading-a-projects-testkit`（ATC-0062 的升級程序）
- `## Assets`
- 全檔沒有 `TODO(release)`

所以 `prepare` 的骨架在填完前不能 commit：commit hook 會擋。這是刻意的。

### 2.3 task 覆蓋：從樹裡算，不從 ledger 算

`integrations.jsonl` 在主機的 Git common dir，CI 與其他主機沒有它；lint stage 必須在每個 checkout 給同一個答案。所以 `check` 用樹內規則：**`<last tag>..HEAD` 中新增（`--diff-filter=A`）的 `.atc/tasks/<ID>.yaml`**。task 的 open commit 是 topic branch 的第一個 commit，整合時才進 `main`，所以「上一個 tag 之後整合的 task」恰好是「上一個 tag 之後新增 record 的 task」；release task 自己的 record 也在範圍內，所以 notes 要列它。以 v0.7.0..v0.8.0 驗證：新增的是 ATC-0057、0058、0059、0061，正是 v0.8.0 § Tasks 的四項。

規則：這個集合與 `## Tasks` 底下每個 `- ATC-NNNN:` 項目雙向相等。缺的、多的各一行。

效果：release task 整合之後、Owner 打 tag 之前若又整合別的 task，該 task 的 lint 會因 notes 缺它而失敗；這正是 ATC-0061 進 0.8.0 時要手動補 notes 的情況，現在由檢查擋下。

輸出：每個問題一行 `RELEASE_<KIND> <detail>`（`RELEASE_VERSION_MISMATCH`、`RELEASE_MIN_ATC`、`RELEASE_SECTION_MISSING`、`RELEASE_TASK_MISSING`、`RELEASE_TASK_EXTRA`、`RELEASE_PLACEHOLDER`、`RELEASE_NOT_AHEAD`），exit 1；全過 exit 0；用法錯誤 exit 2。`--json` 走 `atc-maintain` 既有的 envelope。

## 3. `docs/development/RELEASING.md`

新目錄 `docs/development/` 放 maintainer 文件；`docs/LAYOUT.md` 加一行。`docs/WORKFLOW.md` 保持給使用者，§ Installing a release 留著（只加 § 4 的前置條件）。內容：

1. **流程**：開 release task → `prepare` → 填判斷性段落 → `check`（commit hook 已跑）→ review → Owner 整合。
2. **判斷性段落怎麼寫**：Breaking 要完整（每個移除或改名的指令、flag、輸出 token、exit code、record 欄位、skill 契約、governance 規則，各附替代與 task）；每個 testkit 變更的 required/skippable 表；`min_atc` 的理由（取能讀 testkit 新版所寫格式的最低 atc）；首次執行成本（例如 lint stage 首次建 hook 環境）。這些取自 ATC-0056、ATC-0059 的 scope，集中到一處。
3. **Owner 整合後的步驟**：打 tag、push tag、安裝（§ 4 前置條件先過）、`atc sync --check`、`atc sync`、`atc doctor`、`atc push root`，以及各專案的 re-sync；每個指令一行，無環境變數前綴。

## 4. 安裝前置檢查

11-17 的根因：`atc test` 持有 tool env 的 `python.exe`，`uv tool install --force` 刪 `Scripts` 時 os error 5，留下沒有 `atc_cli` 的 `atc.exe`，所有 session 的 PreToolUse hook 失敗關閉。

- **`atc doctor` 新增 `atc environment` 一行。** 用 testkit 已有的 `children.list_processes()`（Windows 走 Toolhelp snapshot 與 command line，POSIX 走 `/proc`），找 command line 含本程式 `sys.prefix`（大小寫與分隔符正規化）的程序，排除 doctor 自己與它的祖先（`children.ancestors()`）。無則 `READY no other process runs from <prefix>`；有則 `WARN ATC_ENV_IN_USE: <n> processes run from <prefix>; uv tool install fails until they end`，其下每個程序一行 `pid <pid> <command 前 120 字>`。WARN 不改 doctor 的 exit 規則。`--json` 多一個 `atc_environment` 欄位。worker pool 那幾行只涵蓋持有 token 的測試，這一行涵蓋所有從該環境跑的程序（`atc integrate` 的 lint stage、長跑的 `atc task` 等）。
- **`docs/WORKFLOW.md` § Installing a release** 的安裝步驟前加：沒有 `atc test`、verifier 或其他 `atc` 指令在跑，`atc doctor` 的 `atc environment` 是 READY。
- **notes 骨架的 `## Upgrade` 第 1 步**就是這一條，RELEASING.md 也寫。

## 6. ATC-0060 的 docs site 後續

- **`docs_site.plain()` 的接行。** 現在任一側是 CJK 就不加空格，所以 `…的` 換行接 `Claude` 會黏成 `的Claude`，但原文的慣例是 CJK 與拉丁字之間有空格。改為：兩側都是 CJK 字元，或任一側是全形標點（U+3000–U+303F、U+FF00–U+FFEF），不加空格；其他一律一個空格。現行 `CJK` 的範圍不含 U+3000–U+303F，所以 `。` 換行接拉丁字現在會加空格，這也一併修正。
- **`site/overrides/partials/language.html`。** 新測試從已安裝的 `zensical` 套件讀主題的 `partials/language.html`，把 override 的 Jinja 註解拿掉、把 `page.meta.language` 的 if 區塊還原成主題原本那一行，兩者正規化空白後必須相等。主題升級改了 partial 時測試失敗，訊息指出要重新複製。主題 partial 的確切路徑在實作時以已安裝的 zensical 0.1.1 確認。

testkit `docs.py` 的 `LINKED_IMAGE` 變更寫進下一個 release 自己的 notes，本 task 不碰。
