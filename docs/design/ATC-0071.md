## 1. 量測

### 1.1 既有證據

- `~/.atc/run/timings.jsonl` 只有 stage 層級的秒數（`docs/TESTKIT.md` § Stage times），沒有逐 test 的時間。
- task 引用的「510 tests、431 s」對得上兩筆 record：ATC-0070 的 mutants baseline（`stage` `baseline`，515 tests，425.1 s，`workers` 2，帶 line recording），與 ATC-0058 的 related run（431.1 s，18 workers，舊格式無 test 數）。前者的 baseline 雖記有逐 test 秒數（`lines.Record.seconds`），但 ATC-0070 的 scratch 已在 close-out 刪除。
- 沒有可用的逐 test 證據，所以跑了一次整個 suite。

### 1.2 這次的 run

- 命令：`atc test ATC-0071 -- tests -m "not slow" -n 4 --dist loadgroup -p tests._atc0071_measure --durations=40`，在 worktree `bb8727c` 上，private desktop（排除 `interactive_desktop`）。
- 用 4 workers，讓逐 test 秒數接近沒有競爭的值，整個 run 也在前景時限內。
- 結果：3193 tests（3152 passed、1 failed、40 skipped），ELAPSED 577.1 s。
  - 失敗的 `test_doctor_environment.py::test_a_live_process_running_from_the_environment_is_found` 是行程清單在負載下的時序問題，與時間量測無關，見 § 6 第 4 點。
- 量測 plugin 不 commit。它在每個 xdist worker 裡做兩件事：
  - 記下每個 test 的 setup、call、teardown 秒數（`report.duration`）。
  - 包住 `subprocess.Popen`，記下 test process 直接啟動的每個子行程：它屬於哪個 test 與 phase、argv 分類、以及從啟動到 `wait`/`poll` 看到結束的 wall time。
  - 子行程再啟動的孫行程（例如 `atc` 子行程裡的 `git`）算在父行程的 wall time 裡，不重複計。
- 分類依 argv：
  - `atc`：`atc_cli` 模組或腳本、`atc`/`atc-maintain` 執行檔。
  - `testkit`：`atc_testkit` 模組、`integration_verify`、`select_tests`。
  - 其餘依 argv[0]：`git`、`python`、`uv`、`powershell` 等。

## 3. 對假設的判定

- task 假設主要成本是經 uv 與 Python 啟動 `atc` 子行程。這個假設不成立。
  - `atc` 子行程共 252 次、88.8 s，占 test 總秒數 3.9%。
  - 單次啟動比 in-process 呼叫多約 0.06–0.08 s：`python -I -m atc_cli --version` 0.114 s，對照 `import atc_cli` 0.053 s。
  - 全部改成 in-process，最多省約 89 worker-秒，18 workers 下牆鐘約 5 s。
  - 經 uv tool launcher 的啟動只有 5 次，uv 不是成本。
- 主要成本是 `git` 子行程：32549 次、1242.1 s，占 54.4%。每次約 31 ms，幾乎全是行程啟動。
- 其次是巢狀 pytest：`testkit` 類別共 398.7 s，占 17.5%，集中在 `test_testkit_testrun.py`。這些 test 測的是 runner 從啟動到判定的整條路徑，也就是行程邊界本身。

## 4. 提案

### 4.1 用一次 `git fast-import` 建 fixture repo

- 共用 helper 是 `tests/git_history.py`，自己的 test 在 `tests/test_git_history.py`。
- `import_commits` 用一次 `git fast-import` 在一個 branch 上依序做多個 commit，回傳各自的 SHA。
  - 每個 commit 是檔案內容（`None` 表示刪除）加 message。第一個 commit 的 parent 是 `start` 指的 commit。
  - working tree、index 與 `HEAD` 不動，所以它取代「switch 到 branch、add、commit、switch 回來」這種寫法。
  - 文字內容存成 `Path.write_text` 寫出、再由 `git add` 存入的 bytes：行尾是平台的，前提是 repo 沒有 content filter。
  - author 與 committer 取自 `GIT_AUTHOR_*`、`GIT_COMMITTER_*`，日期是當下時間，與 `git commit` 相同。
- `new_repository` 是 `git init`、一次 `import_commits`、`git reset --hard`，共三個行程。
- `copied` 讓同一形狀的 repo 在一個 pytest session 裡只建一次，之後用 `shutil.copytree` 複製給每個 test。
  - 複製只是檔案操作，不啟動行程。
  - 建法可以是 `new_repository`，也可以是該檔原本的建 repo 程式，這樣 repo 內容與改動前完全相同。
  - 被複製的內容不能含建置目錄的路徑，所以會寫進自身路徑的檔案（例如 `workspace.yaml`）在複製之後才寫。
- 只換 fixture 的建法，受測程式的 git 呼叫不變。
- 預期只算 setup phase 的建 repo：5821 次、276.5 s，涉及 1083 個 repo（setup 的 `init` 次數）。
  - 每個 repo 都改成 `git init` 加一次 `git fast-import`：剩約 2 × 1083 次，以 `init` 的平均 46 ms 與一次 fast-import 約 50 ms 計約 100 s，省約 175 s。
  - 同形狀的 repo 在 session 內只建一次再複製：剩下的主要是複製成本，以每個 repo 10–50 ms 計約 10–55 s，省約 220–265 s。
  - 合計約 175–265 worker-秒，約為 test 總秒數的 8–12%。
  - call phase 的 2465 次（約 127 s）不算在內。它要省，test 本體得在受測程式執行前，把整段情境 history 交給 helper 一次建好；受測程式自己做的 commit 則不變。這要逐 test 改寫，不列入本提案的預期。
  - 這些是用 § 2.3 的平均秒數推估的，實際數字以實作後同一個量測 run 為準。
- 這是 tests-only 的變更，task 的 `tests: strict` 涵蓋。
- 範圍依秒數排序，先做 § 2.4 前 10 個檔，其餘的檔分批跟上。
- 共用 helper 也消掉約 20 份重複的建 repo 寫法；atc-review 步驟 5 會把同一問題的第二套機制當成 finding。

### 4.2 量出查詢類 git 呼叫的呼叫端，再決定是否改受測程式

- 查詢類 git 約 838 s，但這次的量測沒有記下呼叫端：分不出是受測程式（`atc_cli`、`atc_testkit`）在重複查，還是 test 的斷言在查。
  - 從形式看兩者都有：帶 `--git-common-dir` 的各種形式合計 1829 次（上表的 1447 次加 `--git-dir --git-common-dir` 270 次與單獨 `--git-common-dir` 112 次）、`--show-toplevel` 503 次多半來自受測程式反覆問同一件事；`rev-parse HEAD` 3194 次多半來自 test helper。
- 下一步在同一個 plugin 加上呼叫端（第一個不在 `subprocess` 裡的 frame 的檔案），對 § 2.4 前 10 個檔跑一次，產出每個（呼叫端檔案、子命令形式）的次數與秒數。
- 若受測程式的重複查詢占大宗，改法是讓同一行程內的事實只查一次，或一次查多個 ref（`rev-parse --verify` 一次帶多個參數、`cat-file --batch-check`）。這會改產品行為，真正的 `atc integrate` 也會變快，但要 behaviour 等級的審查。
- 是否做、放在本 task 還是另開 task，由 Owner 依那次量測決定（§ 6 第 2 點）。

### 4.3 巢狀 pytest 保持子行程

- `test_testkit_testrun.py` 的 319 s 測的是 runner 的行程邊界：baseline、mutant、timeout、import guard。這些不能改成 in-process。
- 只在同一 test 檔裡有多個 test 讀同一次 baseline 的地方，可以改成 module scope 的 fixture 共用一次 run。這要逐 test 看斷言是否只讀結果，本設計不列入範圍。

## 5. 不採的方案

- **CLI 改 in-process（task 原本的提案）。** § 3 量出上限是 3.9%。而且 252 次裡多數是 `python -I <腳本>`、`pretooluse_hook` 這種直接測腳本入口的 test，這些 test 測的正是行程邊界。
- **加 workers。** 牆鐘已經隨 workers 縮短：ATC-0070 的 verify parallel stage 用 18 workers 跑 2160 tests，花 164.1 s。總 worker-秒不會因為加 workers 而減少，在 host pool 裡反而會擠掉其他 run。
- **把 `~/.atc/tmp` 排除在防毒即時掃描之外。** 這是安全設定，不在本 task 的權限內。這次的量測也無法判斷掃描是否在加時間：`git --version` 不寫檔，而寫檔的命令平均較高（`commit` 約 64 ms、`init` 約 46 ms、`add` 約 38 ms），差距可能來自 git 本身的工作，也可能來自掃描。

## 6. 要 Owner 裁決

1. 採 § 4.1：用 `git fast-import` 加 session 內複製的共用 helper 建 fixture repo，作為本 task 的實作步驟，依 § 2.4 的順序。建議：採用。
2. § 4.2 的呼叫端量測放在本 task 的下一步；它是否導向受測程式的變更，等量測結果再裁決。替代：§ 4.2 整個另開 task。建議：量測放本 task（同一個 plugin，成本低），產品變更若成立則另開 task，以免本 task 從 tests-only 變成 behaviour。
3. 不做 CLI in-process 化（§ 5 第一點）。建議：不做。
4. `test_doctor_environment.py::test_a_live_process_running_from_the_environment_is_found` 在這次 4 workers 的 run 失敗：子行程被 kill 並 wait 之後，10 s 內 `environment_checks` 仍回 `WARN`。這不在本 task 範圍。建議：列為 workspace 的 follow-up，由 Owner 決定是否開 task。
5. ATC-0070 的 mutants baseline 為何只拿到 2 workers（515 tests、425.1 s），scratch 已刪，無法還原。這是那個「510 tests、431 s」慢的直接原因之一，與逐 test 成本無關。建議：下次 mutants run 若再出現，從它的 log 的 `workers:` 行查原因。
