# ATC-0057 設計：integration ledger 逐 commit 記錄，`atc push` 依記錄判斷

範圍見 task record `.atc/tasks/ATC-0057.yaml`，含 Owner 11-16 「授權並併入」：governance `GIT_WORKFLOW.md` § Integrate 可以改，ledger 不再依賴 Git 物件圖，既有行在物件還在時補記，`atc push` 依記錄判斷。

要改的：

- `adapters/python/src/atc_cli/scripts/git_preflight.py`：`read_integrations`、`push_listing`、`render_push`。
- `git_integrate.py`：`_note_integration` 寫 `commits`；`atc integrate` 補記舊行。
- `sync_project.py`：sync 行寫 `commits`。
- `atc push` 的 help、`docs/WORKFLOW.md` § 7、governance `GIT_WORKFLOW.md` § Integrate 的 integration record 段落（§ 7）。

## 1. 現況與根因

`push_listing` 把 `origin/main..main` 的每個 commit 對到 ledger（`<git common dir>/atc/integrations.jsonl`）的一行：

1. 只取 `candidate_sha` 落在 `origin/main..main` 的行（下稱 live 行）。
2. 依 candidate 在 `main` 上的順序，每行擁有 `rev-list candidate --not origin/main <較早的 live candidate> main_before`；同一 commit 歸最早的行。
3. 沒有歸屬的 commit 就是 `UNRECORDED_COMMITS`。

這個 workspace 的情況：

- 11-14 ATC-0049 的整合行 `main_before` c1de26a、candidate a785fb1，帶進 c0cd5f6、1a2e566、a785fb1。
- 11-15 Owner 把 `main` reset 到 c0cd5f6（撤回 ATC-0050），之後 ATC-0049 從 c0cd5f6 再整合：`main_before` c0cd5f6、candidate 76eedde。
- c0cd5f6 只在第一行的範圍內，那行的 candidate 已不在 `main` 上，第 1 步就把整行丟掉；第二行把 c0cd5f6 當 `main_before` 排除。c0cd5f6 因此沒有歸屬。

根因有兩層：

- **讀法**：push 要問「這個 commit 有沒有被某次 Owner 核准的整合帶進 `main`」，實作問的卻是「那次整合的 candidate 現在還在不在 `main` 上」。只要有不經 `atc integrate` 的 ref 移動（Owner 的 `git reset`），兩者就不同。
- **記錄**：ledger 只記兩個端點（`main_before`、`candidate_sha`），整合帶進的 commit 集合要靠 Git 物件圖現算。candidate 一旦不在 `main` 上，就只靠 reflog 存活（a785fb1 目前只在 reflog，`gc.reflogExpireUnreachable` 預設 30 天，約 12-15 過期），gc 之後集合再也算不出來。

## 2. 選擇

**ledger 每行記錄它帶進 `main` 的 commit 清單（`commits`）；`atc push` 以 commit SHA 查清單判斷 recorded，不再看 candidate 是否還在 `main` 上。** 寫入當下 candidate 一定存在，所以清單一定算得出來；之後的判斷只是 SHA 比對，不需要任何 Git 物件。

業界做法：

- 供應鏈的來源證明以 digest 列出主體：in-toto / SLSA provenance 的 `subject` 是逐一列出的 digest；Sigstore 的 transparency log 是 append-only，每筆記錄自含要驗證的 digest。這和 ledger 的性質一致：append-only 的稽核記錄，判斷「這個 commit 有沒有被核准」只看記錄本身。
- 「commit 屬於哪個已合併的 PR」在 GitHub、Gerrit 都由伺服器端的資料庫（GitHub 的 PR 與 commit 關聯、Gerrit 的 NoteDb change 記錄）回答，不是在查詢時從分支目前的形狀推算。

不採「每個已整合 candidate 保留一個 ref」（Gerrit `refs/changes/*`、GitHub `refs/pull/*/head`；`atc` 已有前例 `refs/atc/integration-candidates/*`，`git_integrate.py` 的 `CANDIDATE_REFS`，供 recovery 用）。這個做法是工具內部的變更、不改 governance 列出的 record key；不採的理由與成本無關：

- ref 只讓物件不被 gc，判斷仍要從兩個端點遍歷物件圖，ledger 仍不自含。「這個 commit 有沒有被核准」的答案分散在 ledger 與 ref 兩處，任何一處缺了就答不出來。
- Gerrit、GitHub 保留這些 ref，是為了伺服器能再取出 patch set 或 PR 的內容；「哪些 commit 經過核准的 change 或 PR 進來」它們用資料庫回答（§ 2 上一段）。ledger 就是 `atc` 的那個資料庫，對應的做法是把答案寫進 ledger。
- ledger 和 ref 都是本機狀態，`atc` 以外都改得到；ref 方案讓答案分在兩個 store，清單方案只有 ledger 一個來源。
- 讀取時，清單是 SHA 比對；ref 方案每行要一次 `rev-list`，行數隨時間增長。
- 每次整合多一個永久 ref，還要定 namespace、是否推送、close-out 是否保留；清單方案沒有這些生命週期。

清單方案改了 governance 列出的 record key（`GIT_WORKFLOW.md` § Integrate 的 integration record 段落），Owner 11-16 已授權這個變更（§ 7）。

不採「讓 `main` reset 留下記錄」：reset 是 Owner 直接用 Git 做的，不經過 `atc`；reflog 只說 ref 移到哪，不說誰核准，接受它等於接受 reset 到任意 commit，而且 reflog 會過期。以 commit 清單判斷之後，reset 不需要記錄：reset 後 `main` 上的 commit 不是在某行清單內（recorded），就是不在（照樣被拒）。

## 3. 記錄格式

### 3.1 新行

每個帶進 commit 的整合行多一個 key：

- `commits`：`git rev-list --reverse main_before..candidate_sha` 的完整 SHA 清單，舊到新。FF 時是 topic 的 commit；`NO_FF` 時含 merge commit 與 topic 的 commit；records-only binding 是 binding 範圍；一個 binding 寫多行時每行同一份清單。
- recovery 行（`main_before` 為 `null`）沒有下界，不寫 `commits`。
- sync 行（`sync_project.py`）寫 `[<sync commit>]`，也就是 `before..sha`。
- squash 行（governance § Explicitly authorized squash）由寫它的人照同一規則寫 `commits`：`main_before..squash`，即 `[<squash commit>]`。

寫入時 `_note_integration` 已持有 integration slot，candidate 剛建立；`rev-list` 失敗時整行照寫、不含 `commits`，並在結果的 `integration_record_warning` 說明（與現行寫入失敗的回報同一處），之後由補記（§ 3.2）處理。

### 3.2 舊行的補記

ledger 不改寫既有行（append-only）。舊行補一條補記行：

```json
{"kind": "commits", "of": "<candidate_sha>", "main_before": "<main_before>", "commits": ["..."], "recorded_at": "..."}
```

- 補記行沒有 `candidate_sha`，所以 `read_integrations` 與所有讀 integration 行的程式（task status、close-out、ID 配號）照舊略過它；舊版 `atc` 讀到也略過。
- 對象：有 `candidate_sha`、`main_before` 是字串、沒有 `commits`、也還沒有同一對 `(of, main_before)` 補記行的行。同一 candidate 與 `main_before` 的多行（多 task binding）只補一條。
- 條件：`main_before` 與 candidate 都解析成它們自己（`rev-parse --verify <sha>^{commit}`）。算出來的清單就是 § 3.1 的 `rev-list --reverse main_before..candidate`。
- 誰執行、何時：`atc integrate`（非 `--check`）寫自己的行時（`main` 已到 candidate、仍持有 integration slot），在同一次 append 中先寫補記行、再寫自己的行。被拒的 run（`main` 沒有移動）不寫自己的行，也不寫補記；recovery 寫自己的行時同樣補記。Owner 跑的每次成功整合都會補，而且補記是冪等的：已補過、已有 `commits` 的行不再處理。不另開指令：補記是一次性的格式遷移，跟著會寫 ledger 的 Owner 指令走，不需要再教 Owner 一個指令，也不會多一個 writer 搶 slot。
- `--check`、`atc push --check` 不寫入（check 指令一律唯讀）；它們在記憶體中用同一規則算出還沒補記的行（§ 4），所以 check 的結果與真正執行時相同。
- 結果：`atc integrate` 的 JSON 多一個 key `ledger_backfill`：`{"added": <補記行數>, "unresolvable": <物件已不在而無法補記的行數>}`；文字輸出在 `added` 大於 0 時多一行 `ledger: backfilled N lines`。

### 3.3 物件已經不在的舊行

`main_before` 或 candidate 已被 gc（或從未在這個 clone 存在）的舊行無法補記，也無法在記憶體中算出。它的 commit 不算 recorded：

- 這些 commit 若已在 `origin/main` 上，push 根本不列它們，沒有影響。
- 若仍在 `origin/main..main`，push 照樣 `UNRECORDED_COMMITS`（fail-closed）。補救是 Owner 的決定，`atc` 不猜。
- 補記結果的 `unresolvable` 讓 Owner 看得到有幾行已經救不回來。

本 workspace：a785fb1 在 reflog 中到約 12-15，只要在那之前跑一次新版的 `atc integrate`（任何 task），它的行就補記完成，不再依賴 reflog。

## 4. `push_listing` 的讀法

每行的 commit 集合，優先順序：

1. 行自己的 `commits`；
2. 同一 `(candidate_sha, main_before)` 的補記行的 `commits`；
3. 都沒有時在記憶體中算（與補記同一規則，`main_before` 與 candidate 都解析得到才算）；
4. live 行且沒有 `main_before` 的舊行：今天的規則（candidate 能到、`origin/main` 與較早 live candidate 都不能到的 commit）。

歸屬：

- 先 live 行，依 candidate 在 `main` 上的順序；再其他行，依 ledger 順序。每個 commit 歸第一個集合含它的行（與今天「歸最早」一致）。
- 只處理 `origin/main..main` 內的 commit；所有 commit 都有歸屬時就停止，第 3 種現算只在還有未歸屬 commit 時做。
- 第 3 種現算先做一次預篩：把所有待算行的 candidate 與 `^<origin/main>` 經 stdin 交給 `git rev-list --ignore-missing --stdin`（不放在 argv：每個 SHA 41 字元，約 780 行就碰到 Windows 32K 命令列上限），聯集與未歸屬 commit 沒有交集就結束；有交集才逐行算。真的沒記錄的 commit 這條拒絕路徑因此只多一次 Git 呼叫。
- 不在任何集合內的 commit 是 `UNRECORDED_COMMITS`。

### 4.1 為什麼未記錄的 commit 仍被拒

- 集合來自 `atc integrate` 或 `atc sync` 在 Owner 核准的那次寫入時算出的範圍（或對同一範圍的補記）。從未進過任何整合範圍的 commit（直接 commit 到 `main`、reset 到未整合 topic 的 tip）不在任何集合內。
- 沒有 `main_before` 的行只在 live 時用今天的規則，不作 off-main 認領：沒有下界，範圍會是 candidate 的整個歷史。
- 現算時 `main_before` 必須存在；不能把它當成可略過的輸入，否則範圍擴大成 candidate 的整個歷史。

### 4.2 邊界：被撤回的整合

ledger 不記錄「撤回」。今天的程式已經接受 reset 回被撤回整合的 candidate tip（它讀起來就是 live 行，不加標記）；本設計再加上被撤回整合的部分範圍（例如 c0cd5f6），這些會標出「candidate off main」，Owner 推送前看得到。這是 Owner 自己的 ref 移動。撤回記錄是另一個 Owner／governance 議題，不在本 task。

## 5. 輸出

### 5.1 文字

`render_push` 每組的來源行在 candidate 不在 `main` 上時加上 `candidate off main`：

```text
push: 3 commits origin/main c1de26ac4de6 -> main 5d523c12fd1d
  integration a785fb1930bb task="ATC-0049" authority=owner_words candidate off main
    c0cd5f6914dc chore(tasks): open ATC-0049, ...
  integration 76eedde3a84b task="ATC-0049" authority=owner_words
    ...
```

### 5.2 `--json`

- `push_listing` 的每個 entry 多兩個 key：`candidate_on_main`（live 行 `true`，其他行 `false`，沒有歸屬 `null`）與 `recorded_by`（集合的來源：`"line"`、`"backfill"`、`"graph"`，沒有歸屬 `null`）。這個 listing 出現在 `atc integrate --json` 的 `push`。其他 key 不變。
- `atc push --json` 每個 repository row 形狀不變；`UNRECORDED_COMMITS` 的 `detail` 仍只列沒有歸屬的 commit。
- `atc integrate --json` 多 `ledger_backfill`（§ 3.2）。
- 只新增 key，不改既有 key 的意義（`shared/conformance/CLI.md` § Versions and compatibility）；task decision「No version bump」。

## 7. governance `GIT_WORKFLOW.md` § Integrate 的修改

現行段落（「Apart from that evidence, …」）：

> Apart from that evidence, the adapter records every integration that updates `main`, with or without a verification report, as one JSON line in `<git common dir>/atc/integrations.jsonl`: the candidate SHA, the reviewed SHA, the `main` it was integrated onto (`main_before`), the task, its authority, whether the range is records-only, and the time (the keys are in `Task and authority`). For a carried-over review, `reviewed` holds the rebased tip and `carried_over_from` the SHA the review named; the evidence record carries the same pair. The pre-push gate reads only the verification evidence of `Test evidence` below, never this record; `atc push` reads it to check every commit of a push (`Publication boundary`).

改為：

> Apart from that evidence, the adapter records every integration that updates `main`, with or without a verification report, as one JSON line in `<git common dir>/atc/integrations.jsonl`: the candidate SHA, the reviewed SHA, the `main` it was integrated onto (`main_before`), the commits the integration brought onto `main` (`commits`, every SHA of `main_before..candidate`, oldest first), the task, its authority, whether the range is records-only, and the time (the keys are in `Task and authority`). For a carried-over review, `reviewed` holds the rebased tip and `carried_over_from` the SHA the review named; the evidence record carries the same pair. The pre-push gate reads only the verification evidence of `Test evidence` below, never this record; `atc push` reads it to check every commit of a push (`Publication boundary`): a commit is recorded when a line's `commits` names it, whether or not that line's candidate is still on `main`.
>
> The log is append-only. A line written without `commits` gains a supplement line `{"kind": "commits", "of": <candidate SHA>, "main_before", "commits", "recorded_at"}`, which `atc integrate` appends while both commits still exist in the repository; until then `atc push` computes the same range from Git. A line with neither `commits` nor a supplement line, whose `main_before` or candidate no longer exists, records no commits, and a push that carries one of its commits refuses. A line without `main_before` records no `commits`; its commits count only while its candidate is in `origin/main..main`, as those its candidate reaches that `origin/main` and earlier such candidates do not.

§ Explicitly authorized squash 的 squash 行欄位清單加上 `commits`（「the squash commit as `candidate_sha`, the recorded target tip as `main_before`, `commits` as the one squash commit, …」）。

這兩處以外的 governance 不改。

## 9. 測試（strict）

`adapters/python/tests/test_push.py`、`test_git_integrate.py`、`test_sync_commit.py`，真實 Git：

1. reset 情境（舊格式行，沒有 `commits`）：L1 `base..c2`（c1、c2），`main` reset 到 c1，L2 `c1..c3`；`atc push root --check` 為 `CHECK`，c1 歸 L1、`candidate_on_main` `false`、`recorded_by` `"graph"`；c3 歸 L2、`true`；文字有 `candidate off main`。
2. 同一情境，L1 有 `commits` 而 candidate 物件不存在（以假 SHA 表示）：c1 仍 recorded，`recorded_by` `"line"`。
3. 同一情境，L1 沒有 `commits`、有補記行，candidate 物件不存在：c1 recorded，`recorded_by` `"backfill"`。
4. 加一個未記錄的 commit：`REFUSED`、`UNRECORDED_COMMITS`，`detail` 只列它。
5. 舊行的 `main_before` 不存在、或沒有 `main_before` key、或 candidate 不存在（都沒有 `commits`）：不認領，拒絕，不丟 `GIT_FAILED`。
6. live 行與 off-main 行都涵蓋同一 commit：歸 live 行；兩條 off-main 行：歸 ledger 中較早的一行。
7. 多 task binding 同一 off-main candidate：`tasks` 列出全部 task。
8. `atc integrate`（FF、`NO_FF`、records-only）寫的行有正確的 `commits`；recovery 行沒有。
9. `atc integrate` 補記：舊行得到一條補記行，內容正確；再跑一次不重複；同 candidate 多行只補一條；物件不在的行計入 `unresolvable`，不寫補記；`--check` 不寫入；被拒的 run（例如 verifier 失敗）不寫補記。
10. `atc sync` 寫的行有 `commits == [sync commit]`。
11. `read_integrations` 不回傳補記行（task status、close-out 不受影響）。
