# ATC-0057 設計：`main` reset 之後，`atc push` 仍認得已整合的 commit

範圍見 task record `.atc/tasks/ATC-0057.yaml`。要改的是 `adapters/python/src/atc_cli/scripts/git_preflight.py` 的 `push_listing`，以及 `atc push` 的 help 與 `docs/WORKFLOW.md` § 7。

## 1. 現況與根因

`push_listing` 把 `origin/main..main` 的每個 commit 對到 integration ledger（`<git common dir>/atc/integrations.jsonl`）的一行：

1. 只取 `candidate_sha` 落在 `origin/main..main` 的行（下稱 live 行）。
2. 依 candidate 在 `main` 上的順序，每行擁有 `rev-list candidate --not origin/main <較早的 live candidate> main_before`；同一 commit 歸最早的行。
3. 沒有歸屬的 commit 就是 `UNRECORDED_COMMITS`。

這個 workspace 的情況：

- 11-14 ATC-0049 的整合行 `main_before` c1de26a、candidate a785fb1，範圍是 c0cd5f6、1a2e566、a785fb1。
- 11-15 Owner 把 `main` reset 到 c0cd5f6（撤回 ATC-0050），之後 ATC-0049 從 c0cd5f6 再整合，行的 `main_before` c0cd5f6、candidate 76eedde。
- c0cd5f6 只在第一行的範圍內，而那行的 candidate a785fb1 已不在 `main` 上，第 1 步就把整行丟掉；第二行把 c0cd5f6 當 `main_before` 排除。c0cd5f6 因此沒有歸屬。

根因：push 檢查問的是「這個 commit 有沒有被某次 Owner 核准的整合記錄」，實作卻問「記錄它的那次整合，candidate 現在還在不在 `main` 上」。Ledger 記的是每次整合帶進 `main` 的 commit 集合（`main_before..candidate`）；這個集合不會因為之後 `main` 被 reset 而改變。只要 `main` 上的 ref 移動不經過 `atc integrate`（Owner 的 `git reset`、`update-ref`），candidate 的可達性就和「是否記錄過」脫鉤。

## 2. 選擇

採 (a) 的一般化：**一個 commit 只要落在 ledger 任一行的 `main_before..candidate` 範圍內，就是 recorded，不論那行的 candidate 現在是否在 `main` 上**。歸屬先給 live 行（今天的規則原樣保留），剩下的才由其他行依 ledger 順序認領。

理由（業界做法）：

- 來源追溯（provenance）以 commit 為單位，而不是以分支目前的形狀為單位。GitHub 的「commit 屬於哪個已合併的 PR」、Gerrit 的 change 與 commit 對應、SLSA 的 source provenance，都在 commit SHA 上回答「它經過了哪次核准」，與該分支後來是否被 force-push 或 reset 無關。
- Ledger 本身已記錄集合的兩個端點；改的是讀法，不需要新的寫入，也不需要改 ledger 格式。

不採 (b)「讓 `main` reset 留下記錄」：

- reset 是 Owner 直接用 Git 做的，不經過 `atc`。要它留下記錄，得新增一個 `atc` reset 指令並要求 Owner 只用它；Owner 照樣能用 plain git，所以它保證不了什麼。
- 讀 reflog 代替也不行：reflog 只說 ref 移到哪裡，不說誰核准、為什麼；它會讓「reset 到任意 commit」（例如某個未整合 topic 的 tip）都被接受，削弱拒絕。reflog 還會過期（`gc.reflogExpire`）。
- 11-15 那次 reset 已經發生，沒有記錄；(b) 需要回填 ledger，而 ledger 不能手寫。
- 以 commit 為單位認領之後，reset 根本不需要記錄：reset 只會讓 `main` 上出現兩種 commit，一種是某行範圍內的（recorded），一種不是（照樣被拒）。

## 3. 演算法

`push_listing(repo, main, own)` 改成兩段：

1. **live 段**：與今天完全相同（含沒有 `main_before` 的舊行、`own` 的語意）。
2. **off-main 段**：只在 live 段後仍有未歸屬 commit 時執行。
   - 候選行：ledger 中 `candidate_sha` 不是 live candidate、且 `main_before` 是字串的行，依 ledger 順序（最早優先，與 live 段「歸最早」一致）。
   - 先用一次 `git rev-list --ignore-missing <所有候選 candidate> --not origin/main` 求聯集；聯集與未歸屬 commit 沒有交集就結束。這讓「真的沒記錄」這條常見的拒絕路徑只多一次 Git 呼叫。
   - 否則逐行：`main_before` 必須解析成它自己（`rev(repo, base) == base`），candidate 必須解析成它自己；任一不成立就跳過這行。範圍是 `rev-list candidate --not origin/main main_before`，只把其中仍未歸屬的 commit 給這行；全部歸屬後停止。
3. `tasks`（一行一個 task 的 records-only binding 會有多行同一 candidate）改為對所有行收集，off-main 行的 task 名稱也照樣列出。

### 3.1 為什麼未記錄的 commit 仍被拒

- off-main 段只認領「某行 `main_before` 與 candidate 都還解析得到、且 commit 在兩者之間」的 commit。從未進過任何整合範圍的 commit（直接 commit 到 `main`、reset 到未整合 topic 的 tip）不在任何範圍內，照樣是 `UNRECORDED_COMMITS`。
- 沒有 `main_before` 的行（recovery 行、極舊的行）不進 off-main 段：沒有下界，範圍會是 candidate 的整個歷史。
- `main_before` 不存在（物件被 gc 或不是 commit）時跳過該行，不能用 `--ignore-missing` 掉下界，否則範圍會擴大成 candidate 的整個歷史。
- candidate 物件已被 gc（不在 `main` 上的 candidate 只靠 reflog 或其他 ref 活著）時跳過該行，commit 回到未記錄、被拒。這是 fail-closed：不會誤放，只會在 gc 之後重新拒絕（§ 6 後續）。

### 3.2 邊界：被撤回的整合

Ledger 不記錄「撤回」。被撤回整合的 commit 如果之後又回到 `main`（例如 Owner 把 `main` reset 回它們），它們仍屬於原本那行，會被認領。那是 Owner 自己的 ref 移動；`--check` 的列表會標出「candidate off main」，Owner 在推送前看得到。

## 4. 輸出

### 4.1 文字

`render_push` 每組的來源行在 candidate 不在 `main` 上時加上 `candidate off main`：

```text
push: 3 commits origin/main c1de26ac4de6 -> main 5d523c12fd1d
  integration a785fb1930bb task="ATC-0049" authority=owner_words candidate off main
    c0cd5f6914dc chore(tasks): open ATC-0049, ...
  integration 76eedde3a84b task="ATC-0049" authority=owner_words
    ...
```

### 4.2 `--json`

- `push_listing` 的每個 entry 多一個 key `candidate_on_main`：live 行為 `true`，off-main 行為 `false`，沒有歸屬為 `null`。這個 listing 出現在 `atc integrate --json` 的 `push`。其他 key 不變。
- `atc push --json` 的每個 repository row 形狀不變（`name`、`repo`、`commits`、`main_tip`、`verdict`，拒絕時 `reason`、`detail`、`hint`）；`UNRECORDED_COMMITS` 的 `detail` 仍只列真正沒有歸屬的 commit。
- 只新增 key，不改既有 key 的意義：不需要版本號（`shared/conformance/CLI.md` § Versions and compatibility；task decision「No version bump」）。

## 5. 文件

- `atc push` 的 help：「Every commit in origin/main..main must come from a recorded integration or sync」改為說明 recorded 的意思：落在 ledger 某行 `main_before..candidate` 範圍內，`main` reset 到該 candidate 之下之後也算。
- `docs/WORKFLOW.md` § 7：同一句話，並說明 `candidate off main` 標記。
- `push_listing` 的 docstring 換成新規則。
- governance `GIT_WORKFLOW.md` § Publication boundary 寫的是「refuses a push that carries a commit no integration or governance sync recorded in integrations.jsonl」，新行為正是這句話的字面意思，不需要改 governance。

## 6. 後續（不在本 task）

- off-main candidate 物件被 gc 後，它的範圍就無法再計算（§ 3.1，fail-closed）。根治是讓 ledger 不依賴 Git 物件圖：每行記錄它帶進 `main` 的 commit 清單，或為每個已整合 candidate 保留一個 ref（Gerrit `refs/changes/*`、GitHub `refs/pull/*` 的做法）。兩者都改 ledger 或 ref 的格式，而 ledger 行的 key 列在 governance `GIT_WORKFLOW.md` § Integrate 的 integration record 段落，需要 Owner 授權 governance 變更；本 task 只回報。
- 本 workspace 的 c0cd5f6 靠 reflog 讓 a785fb1 存活（`gc.reflogExpireUnreachable` 預設 30 天，自 11-15 起算）；本 task 整合後應儘早 push。

## 7. 測試（strict）

都在 `adapters/python/tests/test_push.py`，真實 Git：

1. reset 情境：行 L1 `base..c2`（c1、c2），`main` reset 到 c1，行 L2 `c1..c3`；`atc push root --check` 結果 `CHECK`，c1 歸 L1、`candidate_on_main` 為 `false`，c3 歸 L2、為 `true`；文字有 `candidate off main`。
2. 同一情境再加一個未記錄的 commit：`REFUSED`、`UNRECORDED_COMMITS`，`detail` 只列它。
3. off-main 行的 `main_before` 不存在：不認領，拒絕。
4. off-main 行的 candidate 物件不存在：不認領，拒絕，不丟 `GIT_FAILED`。
5. off-main 行沒有 `main_before` key：不認領，拒絕。
6. live 行與 off-main 行都涵蓋同一 commit：歸 live 行。
7. 兩條 off-main 行都涵蓋同一 commit：歸 ledger 中較早的一行。
8. records-only binding 寫多行同一 off-main candidate：`tasks` 列出全部 task。
