# ATC-0060 設計：GitHub Pages 文件站，可被搜尋引擎索引

範圍見 task record `.atc/tasks/ATC-0060.yaml`。這份設計選定靜態站產生器與發佈路線、發佈範圍、搜尋基本項、建置與檢查的位置，以及整合後 Owner 的步驟。§ 8 記錄 Owner 的裁決。

## 1. 根因

repo 找不到的原因有三，站點只解第一個：

- github.com 的 URL 不能在 Google Search Console 認領，所以無法提交 sitemap、也看不到索引狀態。`yulinnliu.github.io/agent-traffic-control/` 可以用 URL-prefix property 認領（github.io 網域不屬 Owner，DNS 驗證不可行，只剩 HTML tag 或 HTML file）。
- 沒有外部連結。站點本身不產生連結；認領後提交 sitemap，再把 repo homepage 指向站點，是現在能做的。
- 名稱通用。站點的 `<title>`、description 與首段要用人會搜的詞（§ 4.6）。

## 2. 產生器：Zensical

### 2.1 候選與 2026-11 的狀態

| 候選 | 狀態 | 結論 |
| --- | --- | --- |
| MkDocs 1.6 + Material for MkDocs | MkDocs 1.x 已無人維護，原維護者另以 ProperDocs 延續；Material for MkDocs 自 2025-11-05 停止功能開發，只做 critical fix 與 security update，到 2027-05-05 end of life，upstream 引導使用者改用 Zensical | 不採：新站建在已停止開發、半年後 EOL 的主題上 |
| ProperDocs + MaterialX | 社群延續的 fork 組合，相容 1.x 外掛；ProperDocs 已有實際採用（scientific-python cookie 已改用），MaterialX 是第三方的主題 fork | 不採：主題一側是第三方 fork，不是 upstream 指定的後繼 |
| Jekyll（Pages branch build 的 `github-pages` gem，或 Actions 上的 Jekyll 4） | 穩定；GitHub 預設外掛 `jekyll-seo-tag`、`jekyll-sitemap`、`jekyll-relative-links` 涵蓋搜尋基本項 | 不採：需 Ruby 工具鏈。lint stage 要在 Owner 的 Windows host 上跑（docs/TESTKIT.md § Lint stage），pre-commit 無法在 Windows 自備 Ruby，uv.lock 也釘不住它 |
| Zensical | Material for MkDocs 團隊的後繼產生器；0.1.1（PyPI 最新，classifier `4 - Beta`，需要 Python >=3.11）自 2026-11-05 起為 upstream 所稱可依賴的版線；讀 Material 的設定與主題覆寫；公開的 module API 尚未釋出 | **採用**，釘 `zensical>=0.1.1` |

來源：Material for MkDocs 公告 <https://squidfunk.github.io/mkdocs-material/blog/2025/11/05/zensical/>（2026-10-17 更新，critical maintenance 到 2027-05-05）；mkdocs-material 9.8.0 notice <https://newreleases.io/project/pypi/mkdocs-material/release/9.8.0>；<https://pypi.org/pypi/zensical/json>；ProperDocs <https://github.com/orgs/ProperDocs/discussions/33>、<https://github.com/scientific-python/cookie/pull/838>。

### 2.2 為什麼是 Zensical

- 它是 Material 生態的維護中後繼者；文件站業界最常見的 Python 路線（MkDocs + Material）的使用者正往這裡遷。
- 它是 Python 套件，以 `zensical>=0.1.1` 進 `adapters/python/pyproject.toml` 的新 dependency group `site`，由 `uv.lock` 釘確切版本；`site` 列入 `default-groups`，所以測試與 lint stage 的環境裡都有它。lint stage、本機與 CI 用同一個版本，Windows 與 Linux 都能跑，不需另一套工具鏈。
- 它沒有外掛 API，所以本設計不依賴任何外掛或 hook：把 repo 的文件「擺成站點來源」這一步由我們自己的 staging 腳本做（§ 3），產生器只負責把一個普通的 docs 目錄建成 HTML。產生器之後若要換（例如 Zensical 0.x 出現破壞性變更），staging 與檢查不動，只換建置那一行。

### 2.3 依賴的能力

本設計依賴 Zensical 0.1.1 的四項能力，皆有 upstream 文件：

1. `[project.theme] custom_dir` 覆寫 `main.html` 的 `extrahead` block（<https://zensical.org/docs/customization/>），§ 4.4、§ 4.5 的 meta tag 靠它。
2. 有 `site_url` 時產生 `sitemap.xml` 與每頁的 `<link rel="canonical">`（<https://zensical.org/docs/setup/basics/>；zensical.org 本身由 0.1.1 建成，提供兩者）。
3. front matter 的 `description` 輸出為 head 的 description meta，`title` 覆寫 `<title>`（<https://zensical.org/docs/authoring/frontmatter/>）。
4. `--strict` 在連結與錨點問題上讓建置失敗（<https://zensical.org/docs/setup/validation/>）。

§ 6 的真實建置測試讓這四項在 `uv.lock` 釘住的版本上持續成立；升版而其中一項失效，測試失敗。Zensical 的輸出經過 minify、屬性不加引號，`html.parser` 能處理。

### 2.4 標題 id

Zensical 預設的 TOC slugify 與 GitHub 不同：非 ASCII 標題（`README.zh-TW.md` 的中文標題）與標點產生不同的 id，為 GitHub 寫的錨點連結上站後會斷。`site/zensical.toml` 的 `toc` 擴充把 `slugify` 設為 `pymdownx.slugs.slugify`，參數 `case = "lower"`，即 GitHub 相容的 slug：保留 Unicode 字母、轉小寫、空白轉 `-`、去除其餘標點。§ 5.2 的檢查以 `atc_testkit.docs.slugs` 算出的 GitHub 錨點逐頁比對建成頁面的 id，兩者不一致即失敗，所以兩邊的 slug 規則不會悄悄分岔。

## 3. 從既有文件建站：staging，不複製文字

Zensical 與 MkDocs 一樣只讀一個 `docs_dir`，而首頁要用的 `README.md`、`SCOPE.md`、`GLOSSARY.md` 在 repo 根目錄，`docs/` 裡又有不發佈的 `docs/design/`。所以建置分兩步：

1. **stage**：`adapters/python/scripts/docs_site.py` 依 § 3.1 的發佈表，把每份文件從它在 repo 裡的唯一來源讀出，寫到 `<out>/docs/<站點路徑>`，同時做兩件機械轉換：
   - 連結改寫：連結的找法沿用 `atc_testkit.docs`，不另寫一套 Markdown 連結解析。它以 `without_code` 把 fenced block 與 inline code 塗白（保留長度與換行），再以 `INLINE_LINK`、`LINKED_IMAGE` 與 `REFERENCE` 找出 inline 連結、圖片、以圖片為文字的連結（badge）與 reference 定義；`LINKED_IMAGE` 是這個 task 加的，`INLINE_LINK` 不允許連結文字含 `]`，badge 外層連結原本兩邊都看不到。今天 `link_targets` 只回傳行號與目標文字，staging 需要位置，所以在同一個模組加 `link_spans(text)`，回傳每個目標在正規化（CRLF 轉 LF）文字中的起訖，`link_targets` 改由它導出；兩者共用同一組 pattern 與同一個 code 遮罩，code 裡的連結因此原樣保留。每個目標以「來源在 repo 的路徑」解析：目標也在發佈表內的，改成站點內的相對路徑，錨點保留（§ 2.4 讓它在站上仍有效）；目標是 tracked 但不發佈的（`LICENSE`、`adapters/...`、`shared/governance/...`），改成 `https://github.com/yulinnliu/agent-traffic-control/blob/main/<path>`（目錄用 `tree`），tracked 與否以 `tracked_markdown` 用的同一個 `git ls-files` 判斷；外部 URL（`SCHEME` 判斷）與純錨點不動。raw HTML 裡的 `href`、`src` 不改寫，§ 5.2 的檢查會抓出其中斷掉的。
   - front matter：每頁加 `description`（§ 4.3）；首頁另加 `title`（§ 4.6）。
2. **build**：在 `<out>` 用 tracked 的 `site/zensical.toml` 建置（腳本把 `docs_dir`、`site_dir` 指向 `<out>` 內的目錄），之後寫 `robots.txt`（§ 4.2），再跑 § 5 的檢查。

staging 的輸出只在暫存目錄，從不 commit；repo 裡每份文件的來源不變，GitHub 上的閱讀也不受影響（不往 README 加 front matter）。

### 3.1 發佈範圍

站點路徑會成為永久的 canonical URL，所以由一條規則決定，不逐檔命名：來源相對於它的發佈根（repo 根或 `docs/`）的路徑，檔名轉小寫、`_` 換成 `-`，目錄名不變；兩個例外是 `README.md` 成為 `index.md`，`README.<lang>.md` 成為 `<lang>/index.md`。建成的 URL 是 Zensical 預設的目錄式 URL（`workflow.md` → `/agent-traffic-control/workflow/`）。兩個來源映到同一站點路徑時 staging 失敗。

| 站點路徑 | 來源 | 理由 |
| --- | --- | --- |
| `index.md` | `README.md` | 首頁 |
| `zh-TW/index.md` | `README.zh-TW.md` | 既有的繁中版，同一份內容的語言版本 |
| `scope.md` | `SCOPE.md` | 使用者判斷 ATC 做什麼、不做什麼 |
| `glossary.md` | `GLOSSARY.md` | 名詞 |
| `workflow.md`、`tasks.md`、`layout.md`、`enforcement.md`、`atc-home.md`（來自 `ATC_HOME.md`）、`testkit.md` | `docs/*.md`（`design/` 除外） | 操作文件 |
| `releases/v<version>.md` | `docs/releases/*.md` | release notes，對外有價值，也是搜尋版本號時的落點 |
| `assets/...` | `docs/assets/` | README 的 banner |

不發佈，連結改指 GitHub：

- `docs/design/`：task 的內部設計與量測紀錄，寫給 writer 與 reviewer。
- `.atc/tasks/`、`.agents/`、`.claude/`、`.dsh/`、`.out-of-scope/`：task record、managed copy 與內部紀錄。
- `shared/governance/`、`shared/skills/`、`shared/conformance/`：給 agent 讀的規範與契約，正本必須是 repo 裡被 sync 鎖定的版本；站上放一份會讓讀者以為站上那份是正本。
- `AGENTS.md`、`CLAUDE.md`、`adapters/**/README.md`：agent guidance 與開發者文件，GitHub 上讀即可。

發佈表是 `docs_site.py` 裡的一個常數，它就是「哪些發佈」的唯一來源；`docs/WORKFLOW.md` 引用它，不另列一份。

### 3.2 新增的 tracked 檔案

```text
site/zensical.toml          站名、site_url、repo_url、theme、nav、站點 extra
site/overrides/main.html    extrahead：Open Graph、Twitter card、Search Console meta
adapters/python/scripts/docs_site.py    stage / build / check（不叫 site.py：那會遮住標準函式庫的 site 模組）
adapters/python/tests/test_docs_site.py § 6
adapters/python/atc-testkit/src/atc_testkit/docs.py   加 link_spans，link_targets 由它導出（§ 3）
.github/workflows/pages.yml             § 5.3
```

`site/` 只放站點設定，不放內容；建置輸出永遠在暫存目錄，`.gitignore` 加 `/site/site/` 與 `/site/.cache/`，即有人在 `site/` 裡手動跑 Zensical 時的預設輸出。

## 4. 搜尋基本項

### 4.1 sitemap.xml 與 canonical

`site_url = "https://yulinnliu.github.io/agent-traffic-control/"`。sitemap 與每頁 canonical 由產生器依 `site_url` 產生（§ 2.3 第 2 項）；檢查確認 sitemap 的每個 URL 都對應到一個建成的頁面，且每頁 canonical 等於它在 sitemap 的 URL。

### 4.2 robots.txt

建置後由 `docs_site.py` 寫出，內容是允許全部抓取，加上 `Sitemap: <site_url>sitemap.xml`。注意：project site 的 `robots.txt` 位在 `/agent-traffic-control/robots.txt`，搜尋引擎只讀網域根的 `yulinnliu.github.io/robots.txt`，那屬於使用者站 `yulinnliu.github.io` repo；它不存在時 GitHub Pages 回 404，等同全部允許。所以這份檔案的實際作用是對讀子路徑的工具與 Owner 一目了然，sitemap 的提交走 Search Console（§ 7）。

### 4.3 每頁 title 與 description

- title：產生器用頁面的第一個標題與站名組成。
- description：staging 取每頁第一個正文段落（跳過標題、圖片、badge 行、語言切換行），去掉 Markdown 標記，截到 160 字元的詞邊界，寫進 front matter。來源只有文件本身，沒有另寫的摘要。

### 4.4 Open Graph

`site/overrides/main.html` 的 `extrahead` 輸出 `og:title`、`og:description`、`og:url`（canonical）、`og:type`、`og:site_name`、`og:image`（`docs/assets/atc-banner.png` 的絕對 URL）與 `twitter:card = summary_large_image`。不用 Material 的 social plugin：它要 Cairo 等原生函式庫，Zensical 也未提供同等功能。

### 4.5 Search Console 驗證的位置

用 HTML tag 方法。staging 把 token 寫進首頁 front matter 的 `google_site_verification`，`main.html` 在它非空時輸出 `<meta name="google-site-verification" content="...">`。值由建置環境變數 `GOOGLE_SITE_VERIFICATION` 提供，Pages workflow 從同名的 repository variable 讀取（§ 8 第 3 項）。這個 token 本來就會公開在頁面上，不是 secret。設定或更改 variable 後，workflow 要再跑一次，meta 才會出現在站上；刪除 variable 後的下一次發佈不再帶 meta，Search Console 的驗證隨之失效。

### 4.6 首頁

- `<title>`：首頁 front matter 的 `title` 取自 `site/zensical.toml` 的 `extra.home_title` 表，以語言為 key：`en` 是 `Agent Traffic Control: governance for Claude Code and Codex coding agents`，`zh-TW` 是 `Agent Traffic Control：Claude Code 與 Codex coding agent 的治理層`。`README.<lang>.md` 的首頁另帶 front matter `language`，`site/overrides/partials/language.html` 以它設定該頁的 `<html lang>` 與介面字串；首頁的 `<title>` 不再接站名。表裡缺某語言的 title 時 staging 失敗。
- description 的接行：CJK 字元相鄰的換行不加空格，其他文字之間的換行是一個空格。
- 首段：首頁就是 README，所以 README 的第一段本身要用人會搜的詞，GitHub 上的 repo 頁也同時受益。定稿（§ 8 第 2 項；只描述現有機制，不比較其他專案）：

  > Agent Traffic Control (`atc`) is a governance layer for running several coding agents (Claude Code, Codex) on the same repositories: one writer per branch and git worktree, handoffs that name exact SHAs, and a `main` that moves only to a reviewed, verified commit.

  `README.zh-TW.md` 的首段同步改為對應譯文。description 由 § 4.3 從這段導出。

## 5. 建置與檢查

### 5.1 lint stage

`.pre-commit-config.yaml` 加一個 local hook `docs-site`：

```text
entry: uv run --quiet --locked --project adapters/python python adapters/python/scripts/docs_site.py check
files: ^(README(\.[^/]+)?\.md|SCOPE\.md|GLOSSARY\.md|docs/.*|site/.*|adapters/python/(scripts/docs_site\.py|atc-testkit/src/atc_testkit/docs\.py|pyproject\.toml|uv\.lock)|\.github/workflows/pages\.yml)$
pass_filenames: false
```

`check` 依序 stage、在暫存目錄 build（strict）、檢查建成的站點，失敗即非零退出。`pyproject.toml` 與 `uv.lock` 在 `files` 內，因為 Zensical 與 `pymdownx` 的版本釘在那裡：升版會重建站點。它因此同時涵蓋站點設定（`site/zensical.toml` 解析與建置成功）與連結。同一份清單由 commit hook、`atc test ID`、integration verifier 與 CI 的 `python-adapter` job 跑（docs/TESTKIT.md § Lint stage），不另開一條檢查路線。

既有的 `markdown-links` hook 繼續檢查 repo 內 Markdown 的相對連結與錨點；`docs-site` 檢查的是轉換後的站點，兩者對象不同。

### 5.2 建成站點的檢查

`docs_site.py check` 讀建成目錄裡每個 HTML，標準函式庫 `html.parser` 解析：

- 每個站內 `href`、`src` 指到存在的檔案；帶錨點的，目標頁有該 `id`。
- 每頁有非空的 `<title>`、`<meta name="description">`、canonical，以及 § 4.4 的 Open Graph tag，每個 OG 與 Twitter tag 恰好出現一次（防主題日後自帶一份而重複）；canonical 在 `site_url` 之下。
- 每頁的標題 id 等於 `atc_testkit.docs.slugs` 對該頁來源算出的 GitHub 錨點（§ 2.4）。
- 一份發佈文件內，標題的 slug 不得重複；staging 遇到重複即失敗，指出檔案與兩個標題的行號。理由：重複標題的錨點靠編號後綴區分，GitHub 與 `slugs` 給第二個 `task-records-1`，Python-Markdown 的 toc 在 `unique()` 裡固定用 `_1`，`pymdownx.slugs` 只換 slugify、不碰這個後綴，兩邊無法用設定對齊。分歧的根因是重複本身，而後綴錨點又依標題的出現順序而定，插一個同名標題就讓既有連結指到別處；不允許重複，兩個渲染器對每個標題都產生同一個 id，GitHub 上可用的錨點在站上全都可用。只比第一次出現、並禁止連到後綴錨點的作法（另一候選）留下一類「GitHub 能連、站上不能連」的錨點，只是把分歧從檢查裡移開。目前的發佈文件（§ 3.1 的 15 份）以 `atc_testkit.docs` 的 `FENCE`、`HEADING`、`SLUG_DROP` 掃過，沒有重複的標題 slug；`docs/TASKS.md` 第 16 行的 `## Task records` 在 fenced block 裡（`AGENTS.md` 宣告的範例），不是標題，GitHub 與 Python-Markdown 都不為它產生 id。所以這條規則今天不需要改任何文件，它擋的是之後新增的重複。實作第一步實測 Python-Markdown 對重複標題的後綴，確認上述前提。
- sitemap 的每個 URL 對應到建成的頁面，發佈表的每一項都在 sitemap 裡。
- `robots.txt` 存在且列出 sitemap。
- 設定了驗證 token 時，首頁有對應的 meta。

外部連結（github.com、shields.io）不在檢查範圍：網路結果不穩定，會讓 lint stage 隨外站狀態失敗；改寫成 GitHub 的連結由 staging 依 Git 的 tracked 路徑產生，指向不存在路徑的改寫會在 staging 階段就失敗。

選擇自寫檢查而非 lychee 或 htmlproofer：後兩者要另一套 Rust 或 Ruby 二進位，且只檢查連結；這裡同一次走訪也要斷言 § 4 的每一項 tag。

### 5.3 發佈：GitHub Actions 的 Pages 來源

`.github/workflows/pages.yml`，GitHub 現行建議的「Source: GitHub Actions」路線，不用 `gh-pages` 分支：

- 觸發：`push` 到 `main`，`paths` 限 § 5.1 的路徑（含 `adapters/python/pyproject.toml` 與 `adapters/python/uv.lock`）加上 workflow 本身；以及 `workflow_dispatch`。
- `build` job：checkout、setup-uv、`docs_site.py build`（同一支腳本，`GOOGLE_SITE_VERIFICATION` 取自 `vars`）、`actions/upload-pages-artifact`；權限 `contents: read`。
- `deploy` job：`actions/deploy-pages`，`environment: github-pages`，權限只有 `pages: write`、`id-token: write`。
- `concurrency: pages`，不中途取消。
- 每個 action 以完整 commit SHA 釘版並註明版本，與 `validate.yml` 一致。

`main` 只由 Owner 的 `atc push` 推上去，所以站點只會發佈已整合、已推送的文件。

## 6. 測試

test level `standard`。`adapters/python/tests/test_docs_site.py` 以 `tmp_path` 上的合成 repo 測 `docs_site.py`，不讀真實文件文字：

- 連結改寫：發佈內目標、不發佈目標（檔案與目錄）、外部 URL、錨點、圖片、reference 定義；fenced block 與 inline code 裡的連結原樣保留；指向不存在路徑時失敗。
- `link_spans`：與 `link_targets` 對同一份文字給出相同的目標與行號（`atc_testkit` 既有的 docs 測試照舊通過）。
