# ATC-0055 設計：mutant baseline 分片執行，同一 tree 重用

範圍見 task record `.atc/tasks/ATC-0055.yaml`；要改的 spec 是 `docs/TESTKIT.md` § `atc test ID --mutants FILE`、§ Host worker budget、§ Stage times。

## 1. 現況與目標

`atc test ID --mutants FILE` 先跑 baseline：判定測試的聯集，單一 pytest 行程（`-n 0`），沒有 `-- TEST...` 時開著行記錄器（ATC-0054）。整個指令只取一個 host worker token。ATC-0054 在 9f06f65 量到 baseline 473 s（510 個測試），23 個 mutant 合計 159 s，所以 baseline 是主要成本；reviewer 在同一個 tree 上重跑 `--mutants`（只修 fix 的再審、加一個 mutant）又要付一次 baseline。

目標：

- baseline 依 host worker budget 分片平行執行，各分片的行記錄在判定前合併，判定結果與單行程 baseline 相同（等價的界線見 § 4）。
- 同一 tree SHA、同一判定集合、同一記錄器與 testkit 版本的 `--mutants` 重用上一次 baseline 的結果與行記錄，並在輸出中說明。

不變：mutant run 仍在一個 worker token 上串行、`-n 0`；`-- TEST...` 與 `NO_TESTS` 照舊；每個 run 仍是 `-x`、900 秒 timeout。

## 2. 分片

### 2.1 一次 xdist 呼叫

baseline 是一次 pytest 呼叫，`-n <granted> --dist loadgroup`，也就是 verifier parallel stage 的 xdist 方式（`atc test ID` 只給 `-n`，`--dist` 用 pytest-xdist 的預設 `load`）。分片就是 xdist worker：

- 不自己切測試清單。自己切要先 collect、再分給 K 個 pytest 行程，K 次啟動與 collection 的成本比 xdist 多，而且 `-x` 跨行程停止要自己做。
- `--dist loadgroup` 下，tree 載入 `atc_testkit.plugin` 時（這個 repo 的 `tests/conftest.py` 有），用到 module、class、package 範圍 fixture 的測試會被分到同一組，這類 fixture 和單行程一樣只建一次（§ 4）。
- `-x` 在 xdist 下仍有效：第一個失敗後不再派新測試，執行中的測試跑完。

這個 tree 沒有 pytest-xdist（`xdist_installed` 為否）時，baseline 照今天單行程執行，不帶 worker 選項。

`serial` marker：verifier 的 stages 把它分到 `-n 0` 的 serial stage，但 `atc test ID` 一次呼叫就把 serial 測試和其他測試一起平行跑。baseline 採 `atc test ID` 的方式，不另開 serial 呼叫。理由：baseline 只回答「未 mutate 的測試是否全綠」；serial 測試在負載下失敗，結果是 `BASELINE-RED`，指令停下並點名該測試，不會產生錯的 verdict。另開 serial 呼叫要多一次 pytest 啟動與 collection，而且兩次呼叫的 collection 順序要再合併（§ 3.2）。這個 repo 目前沒有 `serial` 測試。

### 2.2 worker 數與 host worker budget

baseline 的 worker 數沿用 `atc test ID` 的規則（`docs/TESTKIT.md` § Commands，`atc test ID` 第 6 步；程式是 `testrun._worker_request`、`Workers.capped`、`_granted_arguments`）：

- 判定測試的參數中沒有 `-n`：預設數量。pool 內最多 pool 大小，先以 `--collect-only` 數出測試數，每 8 個測試最多一個 worker，至少 2；grant 只有 1 時以 `-n 0` 在行程內跑。
- 參數中有 `-n K`：當作 flag，受記憶體上限與 pool 大小裁減；`-n 0` 單行程。
- 巢狀 run（`ATC_TEST_WORKERS_HELD` 已設）不取 token，1 個 worker；CI 不用 pool。

token 的取得與交還：

1. 決定是否重用（§ 5）之後才取 token。
2. 重用：照今天取 1 個 token（`acquire("mutants", 1, 1)`），持有到指令結束。
3. 不重用：`acquire("mutants", want, floor)`，`want`、`floor` 同 `atc test ID`。印出 `workers:` 行（§ Stages 的格式），並寫進這次 run 的 ledger row。baseline 結束後，`Budget` 的新方法 `shrink(grant, 1)` 交還 1 個以外的 token，並像 `release` 一樣記錄這個 stage 的每 worker 記憶體（4 個 worker 以上時）；剩下的 1 個 token 持有到指令結束，涵蓋所有 mutant run。

不先取 1 個再加取：兩個 `--mutants` 各持 1 個、各等更多時，pool 只有 2 個 token 就會互等到 `WORKER_WAIT_TIMEOUT`。先取整份、跑完再縮小，沒有這個問題，baseline 與第一個 mutant 之間也不必重新排隊。

等待規則與上限不變：等待超過 900 秒以 `WORKER_WAIT_TIMEOUT`（exit 124）停止，等待中被中斷以 `INTERRUPTED`（exit 130）停止，都在 baseline 之前。

`ELAPSED baseline <s>s workers <n> PASS|FAIL` 的 `workers` 是這次 baseline 實際的 `-n`（行程內為 1）。

### 2.3 baseline 失敗

仍然停止並以 exit 1 結束，不套用任何 mutant。xdist 下 `-x` 停止前可能已有多個測試失敗，所以 `BASELINE-RED` 改為點名全部：

`BASELINE-RED <第一個 FAILED 行>; failed: <nodeid>, <nodeid>...`

失敗與 error 的 nodeid 取自 pytest 輸出的 `FAILED `、`ERROR ` 行，與 `atc test ID` 摘要行的 `failed:` 同一個解析（`testrun.summary`）。timeout 與其他結束方式照今天的 `_verdict`。

## 3. 行記錄與合併

### 3.1 每個分片自己的檔案

記錄器本來就以行程為單位寫檔，不需要分片目錄。xdist worker 是獨立行程，透過 execnet 啟動時繼承環境（`PYTHONPATH` 上的 hook、`ATC_LINES_*`），所以 `sitecustomize` 在每個 worker 啟動記錄器，`-p atc_lines_plugin` 也傳到每個 worker。每個 worker（以及它的子行程）寫自己的檔案，都在 `<scratch>/lines/data/`：

- `<pid>-<random>.tsv`：記錄列，格式不變。
- `loaded-<pid>`（新）：plugin 在 `pytest_configure` 一律寫，不論記錄器是否啟動。
- `started-<pid>`：plugin 在 `pytest_configure` 確認記錄器已在本行程啟動才寫（不變）。
- `collected-<pid>.txt`（新，取代 `order-<pid>.txt`）：plugin 在 `pytest_collection_finish` 依 `session.items` 的順序寫出每個測試的識別（`_name(item)`，格式不變）。

xdist controller 也載入 plugin，會寫 `loaded-`、`started-`，但不 collect，所以沒有 `collected-`。

### 3.2 合併（`lines.read`）

- 記錄是否成立：至少一個 `started-`，而且每個 `loaded-<pid>` 都有對應的 `started-<pid>`。只要有一個載入 plugin 的行程沒啟動記錄器，那個 worker 跑過的測試就沒有記錄，判定會漏測試；這時整體退回，印 `NOTE lines: not recorded; every mutant is judged by its file-level tests`（與今天記錄器沒啟動時相同）。單行程時這條規則等於今天的規則。
- 記錄列：所有 `*.tsv` 的聯集，規則不變。每個測試只在一個 worker 執行，所以 `(path, line) -> 測試集合` 的聯集就是每個測試自己記到的行。
- 順序：取 `collected-*.txt` 中檔名排序的第一個。xdist 要求每個 worker collect 到相同的測試、相同的順序（不同時 xdist 自己報錯），單行程時它就是唯一的那個。collection 順序就是單行程 baseline 的執行順序，所以 `Record.order` 與單行程相同，與 worker 數、派送方式無關。今天的 `order-*.txt` 是「實際執行順序」，分片後跨 worker 的執行順序沒有意義，因此改用 collection 順序。

### 3.3 其餘不變

被改行的計算、選擇規則、`NOT_COVERED`、退回、`mutants-covered.json`、argfile 都不變（ATC-0054 設計 § 3、§ 4）。

## 4. 與單行程 baseline 的等價

scope 要求 verdict 與每個 mutant 的測試選擇等於單行程 baseline。能保證的範圍：

- 順序：相同（§ 3.2）。
- 一個測試記到的行：該測試在它的 worker 中執行時跑過的行。行程內不帶狀態的程式碼，與它在單行程中跑過的行相同。
- 只執行一次的狀態不同：session 範圍 fixture、模組層的 cache（`lru_cache`、延遲 import、模組全域的初始化）在每個 worker 第一個用到它的測試執行。單行程時只歸給全體第一個用到的測試；分片時歸給每個 worker 第一個用到的測試。module、class、package 範圍 fixture 在 `loadgroup` 下同組、只建一次，不在此列（§ 2.1）。

分片後的歸屬因此在兩個方向都可能不同：

- 多出：另一個 worker 中第一個用到該狀態的測試也記到這些行。
- 換人：`loadgroup` 把一個 group 整組派給同一個 worker，group 的位置取它第一個測試的位置；所以一個 worker 內的順序不一定是 collection 順序的子序列。全體第一個用到該狀態的測試 T，可能在它的 worker 中排在某個 group 的較後測試 U 之後，這時該狀態由 U 建立，記到這些行的是 U，不是 T。

所以：沒有 mutant 改到「只執行一次」的行時，選擇與單行程完全相同；改到時，選擇中執行該行的測試可能換成別的測試，或多出幾個。但每個 worker 第一個用到該狀態的測試都在記錄裡，所以只要該狀態被任何測試用到，選擇就不會是空的：這種差異不會產生 `NOT_COVERED`。mutant run 是 `-n 0`、依 collection 順序，選上的測試中排第一個用到該狀態的那個一定會執行被改的行。不同的只有「殺傷力」：被選上的測試是否會因為該行改變而失敗。少了單行程會選的 T，可能得到 `SURVIVED`（exit 1）；多出的測試可能殺死原本存活的 mutant；在 `-x` 下，多出的測試也可能先以 error 或非 assertion 失敗結束，使 `KILLED` 變 `INCONCLUSIVE`（exit 1）。

完全相等在任何平行分片下都做不到：只執行一次的狀態本來就取決於行程的歷史。另一個選項是 `--dist load`：它依 collection 順序逐批派送，每個 worker 的順序是子序列，全體第一個用到的測試在它的 worker 中也是第一個，所以分片記錄是單行程記錄的超集（只會多出、不會少掉）。代價是 module、class、package 範圍 fixture 在每個 worker 各建一次：這個 repo 有建 git repo、export 等昂貴的 module fixture，重建會吃掉分片的收益；fixture 若不能在多個 worker 同時建，baseline 還會變紅。本設計選 `loadgroup`，與 verifier 的 parallel stage 一致。

設計審查接受這個解讀：scope 的「equal」在本設計中是「相同順序；行程無狀態的行完全相同；只執行一次的狀態的歸屬可能不同」。§ 8 的量測比對同一份 mutant 清單在單行程與分片下的 `mutants-covered.json` 與 verdict，實際列出差異；差異若出現在真實的 mutant 上，再決定是否改 `--dist load`。

## 5. 重用

### 5.1 記錄放在哪

都在 task 的 registered scratch `<ID>-<sha7>` 裡，close-out 刪 scratch 時一起刪：

- `<scratch>/lines/`：hook 與記錄資料，同 ATC-0054。
- `<scratch>/baseline.json`（新）：成功 baseline 的 key 與結果。
- `<scratch>/mutants-touched.txt`（新）：每個 mutant 套用前，把它要寫的路徑 append 進來（先寫檔再改 tree）。只增不清，scratch 刪除時才消失。
- `<scratch>/mutants.lock`（新）：同一 scratch 一次只有一個 `--mutants` run（§ 5.5）。

### 5.2 key

`baseline.json`：

| 欄位 | 內容 | 重用條件 |
| --- | --- | --- |
| `sha` | export 的 commit（完整 40 字元） | 相等 |
| `tests` | baseline 的參數清單（判定集合，依序） | 相等（清單，不是集合：順序決定 collection 順序） |
| `lines` | 是否記錄（沒有 `-- TEST...`） | 相等 |
| `files` | 記錄的 `.py` 檔（`ATC_LINES_FILES`，相對 tree） | 這次要記錄的檔案都在其中 |
| `recorder` | `HOOK_FILES` 三個原始碼文字的 sha256 | 相等 |
| `testkit` | 執行中的 `atc_testkit` 套件所有 `*.py` 原始碼的 sha256（依相對路徑排序，去掉 `\r`） | 相等 |
| `python` | 執行 pytest 的 interpreter 路徑 | 相等 |
| `private` | 是否 private desktop（決定 `not interactive_desktop` 排除） | 相等 |
| `recorded` | 讀到記錄（`true`），或 `NOTE lines: not recorded`（`false`） | 照存的值處理 |
| `time`、`summary`、`seconds`、`workers` | baseline 的 UTC 時間、`BASELINE-OK` 的摘要、ELAPSED 秒數與 worker 數 | 只供輸出 |

`files` 用包含而非相等：加一個改同一檔案的 mutant 照樣重用；改到新檔案時舊記錄沒觀察那個檔，不能重用（否則那個 mutant 會被誤判為「沒記錄到」而退回）。記錄器與 testkit 都用原始碼 digest，而不是版號：`__version__` 只在 release 時 bump，從 worktree 跑的 testkit 若改了 baseline 的邏輯（xdist 選項、排除、`-x`）而版號沒變，就會重用新程式碼沒產生過的 baseline。digest 涵蓋整個套件，原始碼一改就自動失效。worker 數不在 key 裡，因為選擇與它無關（§ 3.2、§ 4）。

### 5.3 tree 必須仍是 pristine

mutant 會改 export 的 tree 並在 `finally` 還原；行程被強制終止時 tree 可能留著 mutation。在留著 mutation 的 tree 上，重用會跳過能發現它的測試，而重跑 baseline 也可能通過、記下 mutant 的行，同樣是過期的 baseline。所以每個 run 都在取得 scratch 鎖（§ 5.5）之後、決定重用與跑任何 baseline 之前檢查：這次所有 edit 的路徑與 `mutants-touched.txt` 的所有路徑，每個檔案的內容（忽略 `\r`）都等於 `<sha>` 的 Git object，與結尾的 restore 檢查同一個比較（`_digest`、`_blob`）。有任何不同就拒絕，不論能否重用：

`STOP TREE_NOT_PRISTINE: <path> differs from <sha7>`，`hint: atc test ID --clean, then run again to export the tree anew`，exit 9。

這個檢查不跑測試，只比對少數檔案。

### 5.4 流程

1. scratch 登記之後，取得 scratch 鎖（§ 5.5），再做 § 5.3 的 pristine 檢查。
2. 讀 mutant 清單、決定 baseline 參數與要記錄的檔案之後，讀 `baseline.json`。檔案不存在、無法解析、key 不符，或 `recorded` 為 `true` 但 `lines.read` 讀不到記錄：不重用。檔案存在卻不重用時印 `NOTE baseline: not reused: <第一個不符的欄位>`，然後跑 baseline。
3. 跑 baseline 之前先刪 `baseline.json`，再清空並重建 `<scratch>/lines/`（`lines.prepare`，不變）。所以失敗、timeout、被中斷的 baseline 都不會留下可重用的記錄。
4. baseline 通過、讀完記錄之後，寫 `baseline.json`：先寫暫存檔再 `os.replace`，寫一半被中斷不會留下殘檔。
5. 重用時：不跑 baseline、不印 ELAPSED 行（沒有執行任何東西，與 `NOT_COVERED` 相同），印
   `BASELINE-OK reused <time> (<seconds>s, workers <n>) <summary>`，
   然後用 `lines/data` 的記錄與這次重讀的 pristine 文字照常選擇，寫新的 `mutants-covered.json`。`recorded` 為 `false` 時照樣印 `NOTE lines: not recorded; ...`。

`lines.prepare` 分成兩部分：清空並寫 hook（只在跑 baseline 時），與讀 pristine 文字（兩種情況都要）。

鎖一直持有到結尾的 restore 檢查與 `done:` 行之後。

### 5.5 同一 scratch 一次一個 run

今天沒有任何東西讓同一 scratch 上的兩個 `--mutants` run 互斥：指令只取 pool token，`scratch._locked` 只鎖 registry。有了重用之後，並行會產生錯的記錄：run B 的 `lines.prepare` 在 run A 的 worker 寫入時清空 `<scratch>/lines/`，兩個 run 都寫 `baseline.json`，之後的 run 可能重用一半是 A、一半是 B 的記錄；B 也可能通過 pristine 檢查後，跑在 A 剛 mutate 的 tree 上。

所以：

- 每個 `--mutants` run 在 scratch 登記之後、pristine 檢查與重用判斷之前，以 `<scratch>/mutants.lock` 取得排他鎖，持有到結尾的 restore 檢查之後。`atc test ID --mutants` 在 export 之後、寫 `<scratch>/mutants-selected.json` 之前就取得鎖（`task_tests.run_mutants`），`testrun.mutants` 在同一行程內巢狀持有同一把鎖，所以第二個 run 改寫不了第一個 run 的 listing。鎖用 `scratch._locked` 的作法：Windows 以 `msvcrt.locking` 鎖第 0 個 byte，其他平台 `fcntl.flock`；行程不論怎麼結束，作業系統都會釋放鎖。
- 不等待：鎖已被持有時立刻拒絕，`STOP MUTANTS_RUNNING: another atc test --mutants runs on <scratch> (pid <pid>, since <UTC time>)`，exit 9，在任何 baseline、任何 token 等待之前。取得鎖的 run 在鎖定的 byte 之後寫入自己的 pid 與開始時間，拒絕訊息從那裡讀出；讀不到時省略括號。
- `atc test ID --clean`（以及走同一刪除的 close-out）在刪除一個 scratch 之前先試這把鎖：鎖被持有時整個 scratch 以 `REFUSED <dir> (an atc test --mutants run holds it (pid <pid>, since <time>))` 拒絕，裡面什麼都不刪（`docs/ATC_HOME.md` § Deleting 第 3 步）。
