# ATC-0062 設計：sync 擁有的路徑不再逼出 full suite，以及單一的 testkit 升級程序

範圍見 task record `.atc/tasks/ATC-0062.yaml`。§ 1 是根因，§ 2 是修正，§ 3 是 ATC-owned 路徑選什麼，§ 4 是哪些專案、何時拿到修正，§ 5 是升級程序，§ 6 是要 Owner 裁決的事。

## 1. 根因

### 1.1 每一行由哪段程式決定

hqt 的 gate 是 `scripts/prepush_select.py`（專案自己的檔），它先跑自己的 `atc_owned()`，沒認領的才交給 vendored testkit 0.10.0 的 `selection.classify`：

| 路徑 | 決定者 | 結果 |
| --- | --- | --- |
| `.atc/README.md`、`.atc/atc.lock`、`.atc/governance/**`、`{.claude,.agents,.dsh}/skills/atc-*/**` | hqt `atc_owned()`：`ATC_OWNED_FILES`、`ATC_OWNED_PREFIXES`、`ATC_SKILL_ROOTS` + 名稱前綴 `atc-` | `ATC-owned document` |
| `.claude/skills/hami-retro/SKILL.md`、`.agents/skills/hami-retro/SKILL.md` | 不是 `atc-` 開頭，hqt 不認領；testkit `classify` 的 `root_prefixes`（hqt 的 `ROOT_TEST_PREFIXES = ("scripts/", ".claude/", ".agents/")`） | `root app/tooling`，跑 `scripts/tests` 的子集 |
| `.dsh/skills/hami-retro/SKILL.md` | 同上，但 `ROOT_TEST_PREFIXES` 沒有 `.dsh/`；testkit 沒有任何規則 | `no selection rule -> full suite` |
| `.atc/lint/**`（0.8.0 新增） | hqt 的清單沒有 `.atc/lint/`；testkit 沒有任何規則 | `no selection rule -> full suite` |

hq（`scripts/prepush_select.py`，testkit 0.10.1）是同一份手寫清單（`ATC_OWNED_FILES`、`ATC_GOVERNANCE`、`ATC_SKILL_ADAPTERS` 只認 `atc-`），所以它的 sync push 結果相同。heartopia、ria 沒有 vendored testkit 也沒有 gate，不受影響。

### 1.2 為什麼會漏

「sync 在專案裡擁有哪些路徑」有三份手寫的副本，沒有一份從 sync 自己的規則推出：

1. hqt 的 `atc_owned()`；
2. hq 的 `atc_owned()`；
3. testkit verifier 的 `is_atc_managed()`（`verifier.py` 的 `SYNC_FILES = {.atc/atc.lock, .atc/README.md}`、`SYNC_PREFIX = .atc/governance/`、`SKILL_COPY` 只列 `.claude|.agents|.dsh`），用於 documentation-only 分類與 input set。它同樣沒有 `.atc/lint/`：0.15.0 的 verifier 會把一個只送 `.atc/lint/` 的 sync 判成 impact-selected。

而 testkit 的共用 `selection.classify` 根本沒有「ATC-owned」這一類，每個專案只好自己寫。0.8.0 在 `.atc/` 下多送一個 `lint/`，三份副本都沒跟上；sync 渲染的 `hami-*` 共用 skill 一直不在專案的 `atc-` 前綴規則裡；`.dsh` 是較晚加的 harness，hqt 的 `ROOT_TEST_PREFIXES` 沒跟上。

### 1.3 同一個 skill 的 `.claude/` 與 `.dsh/` 副本為什麼答案不同

兩者都沒被 hqt 的 `atc_owned()` 認領（名稱不是 `atc-`），之後落到專案的一般規則：`.claude/` 在 `ROOT_TEST_PREFIXES` 裡，`.dsh/` 不在。答案不同不是 skill 的差別，是專案前綴清單的差別。

## 2. 修正：從 sync 寫進專案的紀錄分類，不從清單

### 2.1 sync 在專案裡已經記下的所有權

sync 的所有權已經由兩個寫在專案裡、與版本無關的紀錄決定，不需要新檔：

- **`.atc/` 的路徑規則**（`docs/LAYOUT.md` § Inside a consuming repository）：`.atc/` 依路徑劃分，`tasks/` 是專案的，其餘每個檔都是 sync 寫的；validation 把其他檔報為 stray，sync 把它當 collision 而不寫任何東西。所以「`.atc/` 下、`.atc/tasks/` 以外」恰好等於 sync 擁有的集合，新 release 在 `.atc/` 下多送的東西（如 `lint/`）自動落在裡面。
- **skill 副本的 `managed-by: agent-traffic-control` frontmatter 標記**：sync 只改寫帶這個標記的副本（`sync_project.managed_adapter`），沒有標記的 skill 是專案的。標記在檔案裡，任何 harness 目錄、任何 skill 名稱都適用。

這是業界對「生成檔／受管檔」的常見作法：Go 的 `// Code generated ... DO NOT EDIT.` 標頭讓工具辨識生成檔，Kubernetes 的 `app.kubernetes.io/managed-by` 標在物件本身，`vendor/` 一類目錄依路徑歸屬。標記和路徑命名空間都隨檔案走，release 加新檔不用改任何讀者。

### 2.2 讓這個規則成為 manifest 的格式要求

目前 manifest 的 `owned` 目標都在 `.atc/` 下，但格式沒規定。修正把它變成格式規則：`owned` item 的 `target` 必須在 `.atc/` 下、不在 `.atc/tasks/` 下，否則 `MANIFEST_INVALID`（`manifest.py`）。這樣「sync 擁有的檔 = `.atc/` 非 `tasks/` + 帶標記的 skill 副本」對每個 revision 都成立，讀者永遠不必知道某個 release 送了什麼。`pointer-line`（`AGENTS.md` 的一行）與 `create-only`（`CLAUDE.md`）建立後屬於專案，不在 sync 擁有的集合內，維持專案自己的規則。

`docs/LAYOUT.md` § Inside a consuming repository 的樹狀圖與「Sync writes `README.md`, `atc.lock` and `governance/` and nothing else」漏了 `lint/`，一併改成上面的規則。

### 2.3 一個實作，三個使用者

testkit 新增一個模組 `atc_testkit.managed`，是「ATC 管理的路徑」唯一的定義：

- `.atc/` 下、`.atc/tasks/` 以外的檔：sync 擁有；
- `.atc/tasks/<name>.yaml`：atc 寫的 task record（verifier 現有的分類，保留）；
- `<dir>/skills/<name>/` 下的任何檔，當 `<dir>/skills/<name>/SKILL.md` 的 frontmatter 帶標記：sync 渲染的 skill 副本。不列 harness 目錄名，標記才是依據。SKILL.md 在工作樹讀；被這個 range 刪掉的，讀給定的 `base`，沒有 `base` 時讀刪掉它那個 commit 的 parent。

使用者：

1. `selection.classify`：在現有規則之前先問 `managed`，認領的路徑只選點名它的測試（§ 3）。`SelectionPolicy` 加 `root: Path | None = None`：有 `root` 時三種都認領；沒有 `root` 時只認領不需讀檔的前兩種（`.atc/` 與 task record），skill 副本照專案規則走，即 fail-safe 的舊行為。
2. `verifier.is_atc_managed`：改成呼叫 `managed`，刪掉 `SYNC_FILES`、`SYNC_PREFIX`、`SKILL_COPY`。
3. 專案：升級後刪掉自己的 `atc_owned()` 與相關常數，在 `SelectionPolicy(...)` 傳 `root=REPO_ROOT`（§ 5 的程序一步）。

沒人認領的路徑照舊走 `no selection rule -> full suite`，fail-safe 不變。

### 2.4 不採的方案

- **sync 另寫一份受管檔清單（如 `.atc/managed.txt`，projen 的 `.projen/files.json` 那種）。** 它重複 §2.1 已有的兩個紀錄，每次 sync 都要重寫、會有合併衝突；被刪的路徑還是得讀舊版清單。路徑規則加標記已經完整，而且不需要專案多一個檔。
- **擴充 `atc.lock` 列出檔案。** lock 的格式是固定三行（`docs/LAYOUT.md`），多個讀者依賴；改格式要 `version = 2` 與所有讀者同時升級，換來的資訊和 §2.1 相同。
- **讓 testkit 內建一份目前 release 的路徑清單。** 這就是現在的問題：每個 release 都要專案升級 testkit。
- **在 gate／verifier 外層先過濾 ATC-owned 路徑，不經專案的 `select`。** 這樣就拿不到專案的 `referenced_by`，會漏掉點名 governance 檔的測試（例如讀 `.atc/governance/` 的專案測試）。

## 3. ATC-owned 路徑選什麼

- **pytest：只選點名它的測試**（`referenced_by(basename)`，即 test 原始碼的字串常值裡出現它的檔名），沒有就不選。理由：sync 擁有的檔沒有任何產品程式會 import 或讀；會讀它的只有專案的測試，而 `test_sources` 已經把它們找出來。這和 hqt／hq 現在對 `atc-*` skill 與 governance 的行為相同，只是範圍改成完整的集合。
- **verifier 的 documentation-only**：ATC-owned 路徑在 `documentation_only` 裡算 managed（現行規則），所以只動 sync 擁有的檔、又沒有測試點名它的 range 是 documentation-only。
- **lint stage**：`.atc/lint/**` 是 lint stage 的輸入，不是 pytest 的輸入。沒採用 lint stage 的專案（目前 hq、hqt、heartopia、ria 都沒有 `.pre-commit-config.yaml`），它什麼也不跑。採用了的專案，verifier 的 lint 列跑 `pre-commit run --from-ref --to-ref`，只 lint 這個 range 改到的檔；而模板 `exclude` 掉 `.atc/`，所以規則檔一變，現有的檔不會依新規則重新 lint，要等 CI 的 all-files job 才發現。這是 lint stage 的範圍缺口，不是 selection 的問題；處理方式見 § 6 決定 1。

## 4. 哪些專案、何時拿到修正

修正在兩處：

- **testkit**（`managed`、`selection`、`verifier`）：專案在 vendor 帶有這個修正的 testkit release 時拿到。依 task 的 decision，這個 task 不 bump 版本；下一個 release 帶它。
- **atc**（manifest 格式規則、`docs/LAYOUT.md`）：Owner 安裝下一個 release 時生效；它只約束未來的 manifest，對專案沒有動作。

| 專案 | 現況 | 何時好 |
| --- | --- | --- |
| hqt | testkit 0.10.0，自寫 `atc_owned()` | 依 § 5 升級到下一個 testkit release，同一個變更刪掉 `atc_owned()`、傳 `root`。之前每次 sync push 照舊跑 full suite |
| hq | testkit 0.10.1，自寫 `atc_owned()` | 同上 |
| heartopia、ria | 沒有 testkit、沒有 gate | 不受影響 |

升級之後，之後的 release 在 `.atc/` 下或以新 skill 加的檔不需要專案再升級 testkit。升級 testkit 的那一次 push 本身會跑 full suite：它改了 `pyproject.toml` 與 `uv.lock`，這是真正的依賴輸入，應該跑。

在升級前先替 hqt、hq 的清單補上 `.atc/lint/` 與 `.dsh/`，只是把第三份副本再修一次；除非下一個 release 很遠，不建議（§ 6 決定 2）。

## 5. 程序：專案升級 vendored atc-testkit

新增 `docs/TESTKIT.md` § Upgrading a project's testkit，是固定、對使用者的程序。release notes 的 § Projects 從此只列該版本的差異，並指向這一節；這條規則寫在 `docs/LAYOUT.md` 對 `docs/releases/v<version>.md` 的說明。程序：

1. **先 re-sync。** `atc sync <project>`。lock 沒指到新 release 前，task 流程會停在 `STOP RELEASE_MISMATCH`；sync 依專案目前 vendor 的 testkit 版本判斷 contract，所以升級前就能 sync。
2. **讀差異。** 從目前 vendor 的版本到目標版本之間，每個 release notes 的 § atc-testkit 表與 § Breaking：要刪的 key、移除的 token 與 API。
3. **在專案的 task 裡 vendor wheel。** 在 ATC checkout 的 release tag 上以 `scripts/build_testkit_release.py` 建 wheel 與 `vendor/atc-testkit.json`，換掉 `vendor/` 下的舊檔，development dependency 釘 `atc-testkit==<version>`，更新 `uv.lock`。
4. **依 vendored 版本的 contract 調整。** `python -m atc_testkit.check --installed` 的問題逐一修掉：例如 0.15.0 起 `lint_scope` 不是 key；採用 lint stage 時要 `pre-commit`。
5. **取代移除的 token 與 API。** 依步驟 2 的清單改專案的 gate、CI、verifier 與腳本（例如 0.15.0 的 `DIFF_CHECK_FAILED` 等改為 `LINT_FAILED`）。
6. **selection。** 從帶本修正的版本起：刪掉專案自己的 ATC-owned 清單，在 `SelectionPolicy` 傳 `root`；`<gate> --paths` 對一個 sync commit 的路徑印出 `ATC-owned`。
7. **（選用）採用 lint stage**，在自己的一個 commit：複製 `shared/templates/pre-commit-config.yaml` 為 `.pre-commit-config.yaml`，development dependencies 加 `pre-commit`；專案的 ruff 設定 `extend = ".atc/lint/ruff.toml"`、`.markdownlint-cli2.jsonc` extends `.atc/lint/markdownlint.jsonc`；`atc test ID --lint` 並修掉發現。
8. **依三層重新分類測試**（governance `VERIFICATION.md` § Testing）：先盤點讀檔案文字或結構的測試；每一個以一條 lint rule 一對一取代，該 rule 先證明會咬（對一個刻意違規的檔失敗），再刪測試；刪除的測試列進 removed-test audit。
9. **首跑成本。** 第一次 lint 在 host 上建 hook 環境（§ Lint stage：Vale 約 35 秒、300 MB）；升級 commit 改了依賴輸入，第一次 verifier 與 gate 不重用任何舊 evidence，跑完整 stage 一次。
10. **驗證。** `atc test ID`；reviewer 的 `atc test ID --candidate` 是那一次完整的 run。

v0.8.0 的 § Projects 與 § atc-testkit 0.15.0 的升級段落、`docs/TESTKIT.md` § Adoption 與 § Lint stage 最後一點，改成只說該處的事實，升級步驟一律指向這一節。已發佈的 `docs/releases/v0.8.0.md` 是 GitHub Release 的本文，不改；從下一個 release 起照新規則寫。

## 6. 要 Owner 裁決的事

1. **lint stage 在規則變更時的範圍（§ 3）。** 一個 range 改到 lint stage 的輸入（`.pre-commit-config.yaml`、`.atc/lint/**`；workspace root 是 `shared/lint/**`）時，lint stage 要不要改跑 `--all-files`？pre-commit 自己的建議是改了 hook 後跑 `--all-files`。建議：**另開 task**。它改的是 lint stage 的 contract、root 與專案的輸入不同，和本 task 的 selection 修正互相獨立；目前沒有專案採用 lint stage，只有 root 會遇到，而 root 的 CI 已跑 all-files。
2. **hqt、hq 在升級前要不要先修自己的清單（§ 4）。** 建議：**不修**，等下一個 release 依 § 5 升級。代價是升級前的每次 sync push 照舊跑 full suite。
3. **manifest 的 `owned` 目標限在 `.atc/`（§ 2.2）。** 這是格式規則的收緊；目前的 manifest 已符合。建議：採用。

## 7. 附錄：hqt push 的 `evidence: SCHEMA_MISMATCH`

### 7.1 現象與寫入者

11-17 16:41 hqt 的 `git push origin main` 推了 `1ae94a5d..c023bb44`（HQT-0043、HQT-0044 的整合）。gate 印 `pre-push: tests RUN (evidence: SCHEMA_MISMATCH)`，並跑了 full default suite；full suite 是 selection 的結果，與 evidence 無關。

gate 讀的是 `.git/atc/verification-evidence/c023bb44….json`，它由 Owner 安裝的 atc 0.8.0 的 `atc integrate` 寫入（`git_integrate.py` 的 evidence record）。檔案內容：`schema` 是 `atc-verification-evidence/3`，包住的 `report.schema` 是 `atc-verification-report/2`（hqt vendor 的 testkit 0.10.0 verifier 寫的）。`718cc64b….json` 相同；更早由 atc 0.7.0 寫的 `be6a0e87….json` 是 `/2` 包 `/2`。

testkit 0.10.0 的 `evidence._well_formed` 只接受 record `/1`、`/2` 與 report `/2`，所以 `/3` 一律 `SCHEMA_MISMATCH`。

### 7.2 根因

atc 0.8.0（ATC-0058）把每個整合 record 都標成 `/3`，不管它包的是哪一版 report。`/3` 相對 `/2` 的差別只在 report（`/3` 有 `inputs`）與 `reused.reused_from`；而包住 `/2` report 的 record 沒有 `inputs`，也不可能有 `reused`（重用需要 `/3` report 的 `inputs`）。所以它的內容就是一個合法的 `/2` record，只是 schema 標記換了，讀它的那一代 gate 就拒絕了。

report 的 schema 說明寫它的是哪一版 testkit，而讀 record 的 gate 正是同一個專案 vendor 的同一版 testkit。record 的版本應該跟著它的內容與讀者走，不該跟著寫入者的版本。v0.8.0 的 release notes 把這記成「skippable, at a cost」（舊 gate 每次 push 都跑測試），但這個代價是可以避免的。

### 7.3 修正

- **寫入端**：`atc integrate` 的 record 用它所包 report 讀者的格式。`/3` report 寫 `/3` record；`/2` 或 `/1` report 寫 `/2` record（`git_integrate.evidence_schema`），也就是 atc 0.7.0 原本寫的格式。這是常見的相容作法：寫入者輸出消費者讀得懂的那一版，只要內容表達得出來（Kubernetes 依 client 要求的 API version 提供物件，HTTP 依 content negotiation 回傳表示法），而不是用寫入者自己的最新版。
- **規格**：`shared/conformance/verification-evidence/README.md` § Record 寫明包住 `/2`、`/1` report 的 record 是 `/2`，以及哪個讀者會重用它。
- **不採：讓讀者放寬到接受較新的版本。** 已 vendor 的舊 testkit 改不了，hqt、hq 的 gate 仍會拒絕；而且 schema 版本號本身就是「讀者不認得就拒絕」的契約，放寬等於取消這個契約。
- `atc test --candidate` 的 candidate record 只有 `atc integrate` 自己讀，維持 `/3`。

### 7.4 誰、何時拿到

修正在 atc（不在 testkit）：Owner 安裝帶有它的 release 後，`atc integrate` 對 hqt、hq 寫 `/2` record，它們 0.10.x 的 gate 就能重用（仍需通過 commit、tree、platform、dependency、argv、selector、stages、slack、selection 各列）。專案不用任何步驟，§ 5 不加步驟。atc 0.8.0 已寫的 `/3` record 不改寫，14 天後由下一次寫入時清掉；它們對應的 commit（如 `c023bb44`）已經 push 過了。

不需要 Owner 裁決：這是寫入端恢復 0.7.0 的相容行為，沒有新的取捨。
