## 1. 文件類 range：ATC 管理的路徑

**問題。** consumer 的 verifier 用 `atc_testkit.verifier.documentation_only`：每個 path 都要是
Markdown，selection 不選任何 test，而且沒有 automation Markdown（`AGENTS.md`、`CLAUDE.md`、
專案在 `automation_markdown_prefixes` 列的前綴）。hami-quant 與 hami-quant-trading 都把
`.atc/`、`.claude/`、`.agents/` 列為前綴，`.yaml`、`.lock` 也不是 Markdown。結果：

- 每個 project topic 都帶自己的 `.atc/tasks/<ID>.yaml`，所以「record 加文件」的 range 永遠不是
  documentation-only。selector 不選 test 時（`pytest_paths is None`），stages 不跑，
  `documentation_check` 也不跑。static checks、`UV_LOCK_CHECK`、`DIFF_CHECK`、
  `TESTKIT_CONTRACT`、`RUFF_CHECK` 照跑（`verifier._consumer_checks`），跳過的是 stages 與
  文件的連結檢查。
- 只含 sync 寫的檔（`.atc/atc.lock`、`.atc/governance/**`、managed skill copy）的 range 同理。

**依據。** governance `VERIFICATION.md` § Documentation-only verification 依「誰消費這段文字」
分類。task record 由 record check 驗（同節最後一段）。sync 寫的檔內容由 ATC revision 決定，
那個 revision 已在 ATC repo 經 Owner 核准整合（`GIT_WORKFLOW.md` § Governance sync commits）。
兩者在 consumer 端都不是要它自己的 test 去驗的行為。

**規則（`documentation_only` 改為）**：range 非空、selection 不選 test（`pytest_paths is None`，
不變），而且每個 path 屬於下列之一：

1. Markdown（`.md`、`.markdown`），且不是 automation Markdown：現行規則，不變。
2. **ATC 管理的路徑**（新的 `verifier.is_atc_managed(path, tree, base)`），比 automation 前綴優先：
   - `.atc/tasks/*.yaml`：task record。
   - `.atc/atc.lock`、`.atc/README.md`、`.atc/governance/` 底下的任何檔：sync 擁有的檔
     （`docs/LAYOUT.md` § Inside a consuming repository）。
   - `.claude/skills/<name>/`、`.agents/skills/<name>/`、`.dsh/skills/<name>/` 底下的任何檔，
     當這個 skill 的 `SKILL.md` frontmatter 帶 `managed-by`：sync render 的 copy。candidate tree
     裡沒有這個 `SKILL.md`（range 刪掉了它）時，讀 `ATC_EXPECTED_MAIN_SHA` 那一邊的
     `SKILL.md`。專案自己的 skill（沒有 `managed-by`）仍是 automation Markdown，不是文件類。

其餘不變：`AGENTS.md`、`CLAUDE.md`（sync 也會改 `AGENTS.md` 的 pointer 行，但它同時是專案自己的
guidance）、專案前綴下的其他檔，仍讓 range 不是 documentation-only。

**效果。** 這類 range 跑 `documentation_check`（`python -m atc_testkit.docs --range`）。
`--range` 檢查 range 新增或修改的 Markdown，所以 sync 寫的 Markdown 也會被檢查連結；skill 的
supporting file 一起 sync，governance 檔之間的連結都在 `.atc/governance/` 內。實作時用
hami-quant `6f82cec`（sync commit）與一個「record 加 docs」的 range，在 scratch copy 上實跑
`--range`，確認沒有誤報；有誤報時停下來報 coordinator，不自行加 exclude。

**root 的 verifier 不變。** `integration_verify.documentation_only` 已把 `.atc/tasks/` 當文件類；
root 的 `.claude/skills/**` 會被 selector 對到讀它的 test，本來就不是文件類，這是對的。

## 2. close-out 找到 task 的 scratch

**問題。** `close_out.py` 只取 registry 的 `row.task == ID`，而只有 `atc tmp checkout --task`
寫這一欄。writer 的 `atc test run --scratch S --tree <worktree>` 登記的列沒有 task，close-out
找不到。

**設計。**

- `atc test run`（`testrun.run` 與 `testrun.execute`）登記 scratch 時，`--tree` 若在一個 managed
  worktree 內，就把 task 記進去：取 tree 的 `git rev-parse --show-toplevel` 與目前 branch；branch
  符合 `worktree-<owner>+<topic>` 時，讀 toplevel 的 `.atc/tasks/*.yaml`，`branch` 等於這個 branch
  的 record 恰好一個時，用它的 `task_id`。零個或多個時不記（不猜）。實作在
  `atc_testkit.scratch`（新的 `task_of_tree(tree)`），PyYAML 已是 testkit 的 dependency。
- `scratch.register` 遇到已存在、task 欄空白的同一個 scratch 時，補上 task；已有 task 時不改。
- close-out 另外取 **tree 在這個 task 的 worktree 之內**的列：worktree path 用 close-out 已經算出的
  那一個（Git 列出的，或 branch 對應的 managed path），在移除 worktree **之前**算好。比對前兩邊
  都先 `os.path.normcase(os.path.realpath(...))`：`same_path` 只做 normcase，`is_relative_to`
  區分大小寫，而這台主機的 TEMP 是 8.3 short name（`ANDYLI~1`），專案也有 `data/` junction。
  兩個條件取聯集，同一個 scratch 只處理一次。

## 3. close-out 把 report 摘要寫進 `integrations.jsonl`（item 4）

刪每一個 report file 之前，append 一行到 task 那個 repository 的
`<git common dir>/atc/integrations.jsonl`：

```json
{"kind": "report", "task": "ATC-0026", "role": "reviewer", "sha": "1a2b3c4", "verdict": "PASS", "file": "ATC-0026-1a2b3c4-review.md", "closed_at": "2026-11-12T08:00:00+00:00"}
```

- `role`、`sha` 取自檔名（atc-review 的命名）：`<ID>-<sha>-review.md` 是 `reviewer`，
  `<ID>-<sha>.md` 是 `writer`；`sha` 是檔名裡的 7 到 40 個 hex。檔名不合這兩種時
  `role: "unknown"`、`sha: null`。
- `verdict`：reviewer 取第一個非空行，去掉開頭的 Markdown `#`，以整個字比對
  `CONDITIONAL PASS`、`PASS`、`FAIL`（`CONDITIONAL PASS` 先比；`PASSED`、`NO PASS` 都不算）；
  找不到時 `null`。writer 的 step report 沒有 verdict，
  記 `null`。
- 寫入失敗時，這個 report 記 `REFUSED <path> (ledger: <error>)` 且**不刪**，exit code 照現行
  `PARTIAL`/`STOP` 規則。`keep` 或 `--skip` 留下的 report 不寫摘要。
- 這一行沒有 `candidate_sha`。現有的讀者（`git_preflight.read_integrations`、
  `close_out.integrated`、`_record_integration` 的去重）都只取有 `candidate_sha` 的行，
  所以不受影響；`atc task list` 的 status 也不受影響。

## 4. sync commit 的版本標籤（item 2c）

`onboard_project.commit_sync` 的 subject 保留 SHA，加上 ATC revision 的 tag：

- revision 正好是 release tag：`chore(governance): sync from <source> v0.4.0 (c91d318)`
- 不是：`chore(governance): sync from <source> 1a2b3c4 (after v0.4.0)`
- revision 之前沒有任何 release tag：`chore(governance): sync from <source> 1a2b3c4`

tag 用 `git describe --tags --match "v[0-9]*" --exact-match <rev>`，失敗時
`git describe --tags --match "v[0-9]*" --abbrev=0 <rev>`，在 ATC checkout 執行。body 的
`Rendered by ... at <full sha>.` 不變。ledger 的 sync 行加 `"source_tag"`（exact 時是 tag，
否則 `null`）與 `"source_after"`（之前最近的 tag，或 `null`）。`atc preflight push` 顯示
`sync from <ATC revision>` 的規則（governance）不變：它讀 ledger 的 `source_revision`。
ATC checkout 沒有 fetch 到最新的 tag 時，`describe` 會退到較舊的 tag；`adapters/python/README.md` 的 `onboard` 一列註明（sync 標籤也寫在那裡）。

## 5. `atc integrate --check` 加 `git diff --check`

在 repository 跑 `git diff --check <merge-base(main, reviewed)> <reviewed>`，即 FF candidate 時
verifier 檢查的同一個 range。

- 有問題時：`resolved.warnings` 加一筆
  `DIFF_CHECK: <n> whitespace problems in <merge-base 12>..<reviewed 12>; first: <path>:<line>: <message>`，
  human 輸出印 `WARNING` 那一行。verdict 與 exit code 不變。
- 理由：governance `GIT_WORKFLOW.md` § Integrate 定義 `--check` 的 verdict 是「topology
  decision」，加一個 refusal 會改變它檢查的內容，需要改 governance（本 task 不授權）。
  warning 已在既有流程內生效：writer 的 step report 回報 check 的結果，reviewer 依 atc-review
  在 verified line 引用 `resolved.warnings` 的每一筆。真正擋住的仍是 verifier 的
  `DIFF_CHECK_FAILED`。若 Owner 要它變成 refusal，見 §9 Q3。
- `atc verify` 不加（它跑 verifier，verifier 本來就做）。

## 6. `atc task list`：overlap、版本、root 推斷

**root 推斷。** `atc task list` 沒有 `--project`、working directory 不在任何 registered project，
但在 canonical checkout（`ws.root`）之內時，target 是 root。只改 `list`；`new`、`start` 等寫入的
指令照現行（它們本來就要求在 topic worktree 內）。`managed_worktree.infer_project` 不改，
`atc worktree` 的行為不變。

**file overlap。** 對同一個 repository 裡 status 為 `open` 的 task，各取
`git diff --name-only main...<branch>`，兩兩取交集；排除 `.atc/tasks/`（每個 topic 只改自己的
record）。human 輸出在表格後面每對一行：

`OVERLAP ATC-0026 ATC-0027: 3 files: adapters/python/scripts/close_out.py, docs/TASKS.md, docs/ATC_HOME.md`

超過 5 個檔時列前 5 個加 `(+n)`。`--json` 加 `overlaps: [{"project", "tasks": [A, B], "files": [...]}]`。
`--all` 時只在同一個 repository 內比。`--status` 篩掉 `open` 時不算 overlap。

**claimed versions。** 見 §9 Q1。建議：record 加 optional 欄位 `version`（字串，例如
`"0.7.2"` 或 `"trading-app 0.7.2"`），`atc task new|plan|start --version TEXT` 寫入。表格的
`open`、`planned` 列多一格 `version <v>`；表格後印每個 repository 一行
`VERSIONS hami-quant-trading: 0.7.2 HQT-0010, HQT-0011; 0.8.0 HQT-0012`。只顯示，不警告：
同一個版本多個 task 是正常的（一個 release 批次收多個 task）。schema 在
`shared/policies/schemas/task.schema.json`（policy shape，不是 governance）。

## 8. 遺留的 candidate worktree

**證據。** 2026-11-11 的整合留下三個 detached candidate 和一筆 stale worktree record，已在
2026-11-12 依 Owner 的指示刪除，逐筆的成因無法回溯。程式裡找到三條路徑：

1. **`atc integrate`/`atc verify` 被硬性終止**：`build_and_verify` 靠 `finally` 移除 candidate；
   session 被停止、foreground call 超時被 kill（TerminateProcess）時 `finally` 不會執行。
   ATC-0023 設計 §2 記錄了 ATC-0022 的 verifier 在 2026-11-11 被中途停掉。
2. **`_remove_candidate` 不帶 `--force`**：`git worktree remove` 遇到 untracked 或 modified 的檔就拒絕
   （`CANDIDATE_DIRTY` 的情況、verifier 留下的檔、Windows 上還被 lock 的檔），只留下一個 warning，
   目錄和 record 都留著。
3. **測試寫進真正的 `<tmp>/candidates`**：`tests/test_testkit_evidence.py` 跑 `atc integrate`
   卻沒有用 `atc_tmp` fixture，candidate 建在使用者的 `~/.atc/tmp/candidates`，而 worktree 屬於
   pytest basetemp 裡的測試 repo。現在那個目錄的 197 個 `*.verify.log` 裡，142 個帶這個測試的
   verifier argv（`from atc_testkit import evidence as ev`）。測試被中斷（mutant timeout、
   session 被停）時，留下的 candidate 屬於一個已被刪掉的 repo，Git 再也列不出它。

**修正。**

- **owner marker**：`build_and_verify` 在 `git worktree add` 之前寫
  `<candidates>/<id>.owner.json`：`pid`、process 建立時間、`command`（`integrate` 或 `verify`）、
  `repo`、`task`、`created`。移除成功後刪掉它。存活判斷用 pid 加建立時間（避免 pid 被重用），
  Windows 用 `GetProcessTimes`，POSIX 用 `/proc/<pid>/stat` 或 `ps -o lstart`。
- **`_remove_candidate`** 改用 `git worktree remove -f -f`（兩個 `-f` 也移除 locked worktree）：
  candidate 是工具自己建的 detached worktree，結果已記錄在 evidence 和 candidate ref，裡面沒有要
  保留的東西。目錄已經不在、只剩 record 時，刪掉指向這個 candidate path 的那一個
  `.git/worktrees/<name>`（讀它的 `gitdir`，兩邊 normcase 後比對），不跑會影響其他 worktree 的
  `git worktree prune`。Windows 上檔案還被開著時仍會失敗，保留現行的 warning。
- **測試隔離**：root 的 `tests/conftest.py` 加一個 session 範圍的 autouse fixture，把 `ATC_TMP`
  指到一個 session 自己的短目錄，session 結束時刪除。目錄名要短，讓 `_new_root` 在它底下建的
  root 仍在 `TMP_NAME_BOUND` 之內。monkeypatch 是 function 範圍，所以這個 fixture 自己設定並還原
  `os.environ`。要測 default `<tmp>` 的測試已經用 `fake_home` 自己設定，`restored_process` 依
  test 開始時的 environ 還原，兩者不受影響；加一個 test 確認 `atc_tmp` 仍給出可用的 root。
  `test_testkit_evidence.py` 因此不再碰使用者的 `<tmp>`；這是整個類別的修正，不只修這一個檔。
- **看得到**（ruling：`atc tmp list` 或 `atc worktree audit`，兩者都做，各管一半）：
  - `atc worktree audit`：Git 列出、path 在 `<tmp>/candidates` 底下的 entry，不再顯示成
    `LEGACY_TARGET`，改為 `CANDIDATE_IN_USE`（owner 還活著，不是 finding）或
    `CANDIDATE_LEFTOVER`（owner 不在或沒有 marker，是 finding，exit 1），detail 帶 marker 的
    `command`、`task`、年齡，目錄不在時加 `record only`。
  - `atc tmp list`：`<tmp>/candidates` 底下沒有活著的 owner 的目錄，每個一行
    `candidates/<id>  <age>  leftover  <repo or "repository gone">`；`*.verify.log`、
    `*.report.json`、`*.owner.json` 不列。最後一行指向 `atc tmp prune`。
- **移除（Q2 裁決）**：`atc tmp prune` 除了現行 7 天的規則，另外移除 owner 已不在的 candidate，
  不論年齡。「不在」是 pid 加 process 建立時間對不上（pid 被重用也算不在）；`OpenProcess` 回
  access denied 算活著；沒有 marker 的 candidate 只在超過 1 小時後移除。目錄已不在、只剩 marker
  時刪掉 marker（及 record，若 Git 仍列著）。prune 仍是人執行的指令，`atc integrate` 開始時不自動
  移除。
- **access denied 與 7 天（Q4 裁決）**：access denied 的 owner 算活著，所以上面「owner 已不在」的移除
  不碰它；但現行 7 天的規則照樣移除它。7 天規則只跳過確認活著的 owner（pid 與建立時間都對得上）。

## 11. 測試

依 `scripts/select_tests.py` 選出的 test file 跑針對性測試；每條 guard 一個 mutant：

- §1：record 加 docs 的 range、只有 sync 檔的 range 是 documentation-only 並跑 docs check；
  沒有 `managed-by` 的專案 skill、`AGENTS.md`、selector 選到 test 的 range 仍不是；刪掉 managed
  skill 時讀 base 那一邊。
- §2：`atc test run --tree <managed worktree>` 記下 task；branch 對到 0 個或 2 個 record 時不記；
  close-out 取 tree 在 worktree 內的列，worktree 已移除時也取得到。
- §3：每個刪掉的 report 一行；`CONDITIONAL PASS` 不被讀成 `PASS`；寫不進 ledger 時不刪；
  `keep`/`--skip` 不寫；`read_integrations` 忽略 report 行。
- §4：exact tag、after tag、沒有 tag 三種 subject 與 ledger 欄位。
- §5：有 whitespace 問題時 warning 出現、verdict 不變。
- §6：canonical checkout 推斷成 root；overlap 排除 `.atc/tasks/`；只比 `open`；`version` 的
  schema 與顯示（Q1(a)）。
- §7：提示列出 missing 的名字。
- §8：marker 寫入與刪除；`--force` 移除 dirty candidate；只剩 record 時只刪那一個 admin dir；
  audit 的 `CANDIDATE_IN_USE`/`CANDIDATE_LEFTOVER`；`tmp list` 的 leftover 行；測試 session 的
  `ATC_TMP` 不是使用者的 `<tmp>`。
