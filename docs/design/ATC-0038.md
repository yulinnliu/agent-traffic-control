# ATC-0038 design: one PreToolUse deny hook

Task: ATC-0038 (`.atc/tasks/ATC-0038.yaml`), base 3bcc2ab. The record binds
this design: one PreToolUse hook built from `hard-deny.yaml` by `atc enforce`
for Claude Code and Codex, absorbing the two hand-written guards, failing
closed on its own errors, with a drift check. It is defense in depth, not a
security boundary. Governance changes appear here as proposals only; no code
lands in this step.

## 1. The layers today

| Layer | Source | Where it binds | Covers |
| --- | --- | --- | --- |
| Claude Code `permissions.deny` | a project's `policies/hard-deny.yaml`, rendered by `atc enforce` into its `.claude/settings.json` | sessions whose project is hami-quant or hami-quant-trading | `Bash(<prefix>:*)`, `PowerShell(<prefix> *)`, `Read(glob)`, `Edit(glob)` |
| Machine-local `Edit` deny | `workspace.yaml` state roots, merged by hand into `~/.claude/settings.json` | every Claude Code session | Edit/Write/NotebookEdit into `state/*` |
| Codex `prefix_rule` block | the same policy, spliced into `~/.codex/rules/default.rules` | every Codex session | argv prefixes |
| Git `pre-commit` | the same policy | commits in a project whose `core.hooksPath` points at it | staged paths |
| `worktree_cd_guard.py` | this repository, `adapters/python/scripts/`, run from the root checkout | every Claude Code session, `Bash\|PowerShell` | top-level `cd` into `worktrees/` |
| `write_scope_guard.py` | `~/.claude/hooks/`, untracked, hard-coded paths, imports the cd guard's lexer | every Claude Code session, `Edit\|Write\|NotebookEdit\|Bash\|PowerShell` | writes outside the allowed roots |
| `block-main-edit.sh` | hami-quant's own `scripts/hooks/` | hami-quant sessions, `Edit\|Write\|NotebookEdit` | edits in a checkout on `main` |

Gaps found while reading them:

- No shared `hard-deny.yaml` exists. Each project owns its policy; two of the
  four registered projects have one, and this repository has none, so a
  session whose project is the workspace root (every coordinator) or
  my-heartopia-tools or ria-project has no command deny at all.
- A prefix rule matches the start of a command only. `git -C <path> reset
  --hard`, `git -c k=v push --force`, `env X=1 git clean -fdx` and
  `bash -c "git push -f"` pass `Bash(git reset --hard:*)`. Claude Code splits
  `&&` chains before matching, Codex tokenises, neither strips git's global
  options.
- Three rules cannot be written as a prefix: `atc integrate` except
  `--check` (a prefix deny would also block `--check`), a push whose target is
  `main`, and `atc verify` / `atc test run` with `run_in_background`. They
  rely on briefs.
- A shell write into a denied path (`rm`, `mv`, `>` into `.env` or a state
  root) is outside every native rule (`docs/ENFORCEMENT.md` § Machine-local
  segment). Codex has no filesystem deny at all.
- Both guards return 0 on any exception. A crash or a missing interpreter is
  a non-blocking error in Claude Code, so both fail open.
- `write_scope_guard.py` lives outside every repository, with this machine's
  paths and a Claude-Data session folder id in its source, and no review path.

## 2. What each harness's hook protocol gives

Read from code.claude.com/docs/en/hooks and the Codex hooks page
(learn.chatgpt.com/docs/hooks) on 2026-11-13. The desktop app on this host
runs Claude Code 2.1.321; the `claude` CLI on `PATH` is 2.1.42; Codex is
0.153.4.

| | Claude Code | Codex |
| --- | --- | --- |
| Configuration | `hooks.PreToolUse` in any settings file; user-level `~/.claude/settings.json` binds every session | `~/.codex/hooks.json` or `[hooks]` in `config.toml`, user or trusted repo layer |
| Enabled | always | by default; `[features] hooks = false` turns them off. A new or changed hook is skipped until the user trusts it in `/hooks` |
| Tools seen | every tool; the matcher selects `Bash`, `PowerShell`, `Edit`, `Write`, `NotebookEdit` | shell and unified exec as `Bash`, `apply_patch`, MCP tools; hosted tools are not seen |
| Input | `cwd`, `permission_mode`, `tool_name`, `tool_input`; Bash and PowerShell carry `command`, `description`, `timeout`, `run_in_background`; Edit/Write carry `file_path` | `cwd`, `tool_name`, `tool_input.command` (a string for `Bash`, the patch text for `apply_patch`); no shell name, no background flag |
| Deny | exit 0 with `hookSpecificOutput.permissionDecision: "deny"` and a reason, or exit 2 with the reason on stderr | the same JSON, the legacy `{"decision": "block"}`, or exit 2; `ask` is parsed but unsupported |
| Several hooks | run in parallel; precedence `deny` > `defer` > `ask` > `allow`; deny and ask rules still apply whatever a hook returns | launched concurrently; how decisions combine is unstated |
| Failure | a hook that cannot start, exits other than 0 or 2, times out or prints invalid JSON lets the call proceed, unless the hook sets `"onFailure": "block"` (Claude Code 2.1.295 or later), which then blocks it | an unsupported output field fails the run and the call continues; for crashes and timeouts of a local hook the page states nothing and offers no fail-closed option |
| Timeout | per hook `timeout` in seconds, default 600 | per hook, default 600 |
| Stated limit | — | "a useful guardrail, not a complete enforcement boundary"; some tool paths bypass the hook |

Neither harness says whether a hook sees a command its own native deny
already refused; the design does not depend on it. The hooks page does not
state how a hook `deny` interacts with `bypassPermissions`; the
implementation step checks it in a real session and records the result in
`docs/ENFORCEMENT.md`.

## 3. Design

### 3.1 Shape

One fixed engine and one generated rule table:

- **Engine**: `adapters/python/scripts/pretooluse_hook.py`, standard library
  only, run from the root checkout like the cd guard today. It reads the
  payload on stdin and the table from disk, decides, and prints one
  decision. `--harness claude|codex` selects the payload and output dialect.
  The Bash and PowerShell lexers move from `worktree_cd_guard.py` into a
  sibling module the engine imports.
- **Table**: `~/.atc/enforcement/pretooluse.json`, machine-local, written by
  `atc enforce --workspace <map> --hook-out ~/.atc/enforcement`. It holds
  every rule the engine applies, already composed and with absolute paths
  resolved, so the engine reads one JSON file and never parses YAML or the
  workspace map per call.

Keeping the rules as data means the installed hook command never changes,
so Codex's trust review happens once, and a policy change shows as a table
diff, not a code diff.

### 3.2 Rule sources and composition

The composer reads, in this order:

1. The workspace policy: `policies/hard-deny.yaml` in this repository (new;
   see Q1). Its rules apply to every session on the machine.
2. Each registered project's `policies/hard-deny.yaml`, from its `repo` on
   `main`. Its command rules apply to every session; its repository-relative
   filesystem globs apply under that project's `repo` and `worktrees` roots;
   `~`-rooted globs apply everywhere (Q2).
3. `workspace.yaml`: each project's `state` root (an edit/write deny, as the
   machine-local segment renders today), the `worktrees` roots (the cd
   rule), and a new key `agent_write_roots` listing the directories outside
   `workspace_root` an agent may write (`%TEMP%`, `~/.claude`, `~/.atc`, the
   app's notes folder, ...), expanded at compose time (Q5). `workspace_root`
   is always a write root.

Each table rule keeps its `id`, its source file and its `reason`, which the
deny message quotes.

The hard-deny schema gains four optional fields on a `commands.deny` entry.
An entry that uses any of them is hook-only: the Claude Code and Codex
renderers skip it, since a prefix rule would deny more than it means. The
conditions of one entry all hold for it to deny: with both `with_args` and
`unless_args`, the command is denied when one `with_args` argument appears
and no `unless_args` argument does.

| Field | Meaning |
| --- | --- |
| `unless_args: [<arg>...]` | the command is denied unless one of these arguments appears after the prefix |
| `with_args: [<arg>...]` | the command is denied only when one of these arguments appears after the prefix |
| `push_targets: [<branch>...]` | for a `git push` prefix: denied when a destination is one of these branches (§ 3.4) |
| `background: true` | denied only when the command runs in the background (§ 3.4) |

The workspace policy then states the three rules as data:

```yaml
commands:
  deny:
    - id: atc-integrate-owner-voice
      argv_prefix: [atc, integrate]
      with_args: [--owner-run, --owner-words]
      unless_args: [--check]
      reason: These flags carry the Owner's own words; an agent never speaks them.
    - id: atc-integrate
      argv_prefix: [atc, integrate]
      unless_args: [--check]
      reason: Integration is the Owner's act; an agent runs only --check.
    - id: git-push-main
      argv_prefix: [git, push]
      push_targets: [main]
      reason: main moves only through atc integrate, run by the Owner.
    - id: atc-verify-background
      argv_prefix: [atc, verify]
      background: true
      reason: Verification runs in the foreground (governance DELIVERY.md § Background work).
    - id: atc-test-run-background
      argv_prefix: [atc, test, run]
      background: true
      reason: Tests run in the foreground (governance DELIVERY.md § Background work).
```

Existing fixtures use none of the new fields, so their `expected/` stays
byte-equal and the native renders of today's policies do not change.

### 3.3 Matching commands

The engine splits a `Bash` or `PowerShell` command into simple commands with
the lexers the guards use today (heredocs, quotes, subshells, `$(...)`,
backticks, PowerShell here-strings and comments). For every simple command
at any depth it normalises the argv, then compares it with each rule's
`argv_prefix`, token by token:

- Leading assignments and the prefixes `env [VAR=...]`, `command`, `exec`,
  `builtin`, `nohup`, `time`, PowerShell's `&` and `.` are dropped.
- `uv run [options]`, `uvx` and `python -m <module>` resolve to the command
  they launch, so `uv run --locked atc integrate ...` from a worktree's
  `adapters/python` matches the `atc integrate` rules (a fixture case).
- `argv[0]` compares by basename, case-folded, without `.exe`.
- For `git`, global options before the subcommand are dropped: `-C <path>`,
  `-c <k=v>`, `--git-dir[=]`, `--work-tree[=]`, `--namespace[=]`,
  `--no-pager`, `-p`, `--paginate`, `--bare`, `--literal-pathspecs` and the
  other `--*-pathspecs`. `-C <path>` is kept as the directory of that command.
- `bash -c`, `sh -c`, `pwsh -Command`/`-c` and `powershell -Command`/`-c`
  with a literal string are lexed again, one level deep.
- Arguments after the prefix compare exactly; flag bundles are not
  reordered, so the policy keeps listing permutations as it does for Codex.

A Codex `Bash` call carries no shell name, so the engine lexes it as Bash
and as PowerShell and denies when either reading matches. `apply_patch`
yields its target paths from the `*** Add File:`, `*** Update File:`,
`*** Delete File:` and `*** Move to:` lines, checked like an Edit.

### 3.4 The three rules a prefix cannot express

- **`atc integrate` except `--check`**: the normalised argv starts with
  `atc integrate` and no later argument is `--check` or starts with
  `--check=`. A separate rule denies `--owner-run` and `--owner-words` in an
  agent call without `--check`: they record the Owner's decision, and only
  the Owner's own terminal may carry it. `--check` writes nothing, and
  governance GIT_WORKFLOW.md § Integrate gives the agent-run check the form
  `atc integrate --check ... [--owner-words <quote>]`, so it stays allowed
  with either flag.
- **A PASS that carries integration** (the Owner's wish of 2026-11-12, as
  before ATC-0019): the two rules above are data in the workspace policy, so
  the path opens by policy, not by code. The Owner removes the
  `atc-integrate` entry; `atc-integrate-owner-voice` stays. An agent can then
  run `atc integrate --task <ID> --reviewed <SHA>` only on record authority,
  and `atc integrate` itself refuses without it (`AUTHORITY_MISSING`,
  `AUTHORITY_NOT_FF`): the grant is `integrate_main: true` in the record on
  `main`, which enters `main` only through a records-only `--owner-words`
  integration, which the hook keeps the Owner's. The Owner thus grants per
  task and the reviewer's PASS consumes the grant; close-out after it
  (`atc worktree clean`, `atc tmp clean`) needs no hook change, and the push
  of `main` stays denied (publication is governed separately). What the hook
  cannot tell is which session calls: a writer holding a granted record could
  integrate its own tip, so writer and reviewer separation stays with the
  briefs (Q7). Opening the path also changes GIT_WORKFLOW.md § Integrate
  ("The Owner runs every `atc integrate` but `--check`"), a governance change
  proposed in § 5 that the Owner authorizes on its own.
- **Push to `main`**: after the `git push` prefix, options are skipped and
  the first operand is the remote. A refspec's destination is the part after
  `:`, or the whole refspec without one, with a leading `+` and `refs/heads/`
  removed. The call is denied when a destination is a listed branch, when a
  refspec contains a glob (`*`), with `--all`, `--mirror` or `--delete
  <listed>`, and when no refspec is given (or the refspec is `HEAD`) while
  the command's directory is on a listed branch. The branch is read from the
  `HEAD` file of the directory's git dir (following a worktree's `.git`
  file); no git process starts. A directory the engine cannot resolve counts
  as on `main`.
- **Background verify and test**: a rule with `background: true` matches
  when `tool_input.run_in_background` is true, or when the command itself
  backgrounds it: a Bash simple command ended by a single `&`, a PowerShell
  pipeline ended by `&`, or `Start-Job` / `Start-Process` / `Start-ThreadJob`
  launching it. Codex has no background flag; only the in-command forms
  apply there.

### 3.5 The absorbed guards

- **Worktree cd**: unchanged semantics. A top-level Bash `cd`/`pushd`, or any
  PowerShell location change, into a `worktrees` root from the table is
  denied with today's message. The rule binds Claude Code only: Codex starts
  each command in the session's `cwd`, so a `cd` does not carry over.
- **Write scope**: unchanged target extraction (the verb tables, redirections,
  `cmd /c`, `--basetemp`, .NET writes). A target outside every write root is
  denied as today. In addition, a write target, and an Edit/Write/NotebookEdit
  or `apply_patch` path, that matches a filesystem rule denying `edit` or
  `write` is denied; this reaches the shell writes and Codex paths no native
  rule covers. A target the engine cannot resolve is allowed, as today.
- **Self-protection**: the table directory and the engine files in the root
  checkout are write-denied to every agent call, and so are `atc enforce`
  calls passing `--hook-out` or `--install-hooks` (Q6).

`worktree_cd_guard.py` is removed; the shared lexer module `shell_words.py` and the engine hold its rule. `write_scope_guard.py` and its test sit in `~/.claude/hooks/`,
which agents may not edit; the Owner deletes them after the switch. Its
test cases are ported into the repository's fixtures with the paths made
fixture inputs. hami-quant's `block-main-edit.sh` is that project's own and
stays outside this task.

### 3.6 Failure handling

- The engine wraps everything after reading stdin: an exception, an
  unreadable or invalid table, or an unknown table version prints a deny
  whose reason names the failure and the Owner-run command that repairs it
  (`atc enforce ... --hook-out ...`), and exits 0. If printing fails, it
  exits 2.
- Claude Code entries set `"onFailure": "block"` and `"timeout": 10`, so a
  hook that cannot start, crashes or stalls blocks the call. This needs
  Claude Code 2.1.295 or later; the 2.1.42 CLI on `PATH` here predates the
  field, so a session started from it fails open on start failures.
- Codex offers no fail-closed option. The engine's own errors still deny;
  a hook that cannot start or times out lets the call run.
- What the engine cannot read in a command (an unresolvable variable target,
  an unknown verb) is not a failure: the rule simply does not match.

A missing or broken table denies every matched call, including the agent's
attempts to repair it, so repair is the Owner's: the deny reason carries the
command for their terminal, which no hook sees.

### 3.7 Installation and drift

- `atc enforce --workspace <map> --hook-out <dir>` writes
  `<dir>/pretooluse.json`, LF, deterministic, keys and rules in source order.
- `atc enforce --install-hooks` (Owner-run) merges one entry into
  `~/.claude/settings.json` and one into `~/.codex/hooks.json`, and removes
  the entries that run `worktree_cd_guard.py` or `write_scope_guard.py`:

  ```json
  {"matcher": "Bash|PowerShell|Edit|Write|NotebookEdit",
   "hooks": [{"type": "command", "timeout": 10, "onFailure": "block",
              "command": "python \"<root>/adapters/python/scripts/pretooluse_hook.py\" --harness claude"}]}
  ```

  The Codex entry matches `Bash|apply_patch` with `--harness codex`; the
  Owner then trusts it once in Codex's `/hooks`.
- `atc enforce --check` gains three comparisons, each reporting `drift:` like
  the existing ones: `--live-hook-table FILE` (the installed table against a
  fresh compose), `--live-claude-hooks FILE` and `--live-codex-hooks FILE`
  (exactly one engine entry, equal to the rendered one, and no retired guard
  entry). The names avoid `--live-hook`, which means the git `pre-commit`.
- `atc validate --projects` and `atc doctor` report a stale or missing table
  without failing a project, as they report the machine-local segment today.
- The native renders stay: Claude Code `permissions.deny` and the Codex rules
  apply without any Python, and the hook adds what they cannot say.

### 3.8 Per-call cost

Measured on this host, five runs each, one `git status` payload: the cd
guard 88–105 ms, the write guard 98–106 ms, a bare `python -c` reading the
payload 62–106 ms. Interpreter start dominates; the matching work is small
beside it.

| Tool call | Today | With the engine |
| --- | --- | --- |
| `Bash`, `PowerShell` | 2 Python processes in parallel, about 100 ms wall | 1 process, about 100 ms wall |
| `Edit`, `Write`, `NotebookEdit` | 1 process (plus hami-quant's `bash` + `python`) | 1 process (plus hami-quant's own hook) |
| `Read`, `Grep`, `Glob`, others | none | none |
| Codex `Bash`, `apply_patch` | none | 1 process |

The engine imports the standard library only, reads one JSON file, and
starts no child process; `ctypes` long-path expansion runs per write target
as today. The implementation step reports the measured p50/p95 for the
engine against these numbers.

### 3.9 Limits

The hook sees the text of a tool call, not what a program does once it runs.
A script, an alias, `python -c` with `subprocess`, a variable built at run
time, or a tool path a harness routes around the hook all pass. A read of a
denied file through the shell (`cat .env`) stays outside it, as does `gh`
merging a pull request into `main` on the remote. The guarantee is the one
the record names: defense in depth that turns a mistaken command into a
refusal with a reason.

## 6. Open questions for the Owner

- **Q1. Where the workspace-wide rules live.** (a) A new
  `policies/hard-deny.yaml` in this repository whose rules apply to every
  session; (b) the same entries copied into every project's policy; (c)
  hard-coded in the engine. Recommendation: (a). It covers root, heartopia and
  ria sessions, which have no command deny today, and keeps one source.
- **Q2. Scope of a project's rules in the table.** (a) Command rules apply
  everywhere; repository-relative globs only under that project's repo and
  worktrees; (b) every rule only when the session's `cwd` is inside that
  project; (c) everything everywhere. Recommendation: (a). A coordinator at
  the root running `git -C projects/hami-quant reset --hard` is caught, and
  `authorizations/**` stays scoped to trading.
- **Q3. Engine and table versus a generated script.** (a) A fixed
  standard-library engine reading a composed JSON table; (b) `atc enforce`
  writes a self-contained script with the rules inlined. Recommendation: (a).
  The engine is tested once by fixtures, and the installed command never
  changes, so Codex's trust review is not repeated after each policy change.
- **Q4. What fails closed.** (a) Engine errors and a missing or invalid table
  deny; an unresolvable command target is allowed, as today; (b) unresolvable
  targets also deny. Recommendation: (a). (b) would deny every command
  holding a run-time variable, the false positives the write guard already
  had to be tuned against. One exception stays fail-closed under (a): a
  `git push` with no refspec whose directory the engine cannot resolve counts
  as on `main` (§ 3.4), since that push moves whatever branch is checked out.
- **Q5. Home of the write roots.** (a) `agent_write_roots` in
  `workspace.yaml`; (b) the root policy with `${...}` tokens.
  Recommendation: (a). The roots are machine paths, and the policy refuses
  tokens by design.
- **Q6. Installation and self-protection.** (a) An Owner-run
  `atc enforce --install-hooks`, with the hook denying agents the table, the
  engine files and that option; (b) `atc` prints the entry and the Owner
  edits each settings file by hand, `--check` verifying. Recommendation: (a).
  One command keeps the two harnesses and the retired entries consistent,
  and the agent cannot reach it.
- **Q7. How a PASS may carry integration.** (a) Agents never pass
  `--owner-run`/`--owner-words` outside `--check`; plain `atc integrate --task` is denied now
  and opens when the Owner removes the `atc-integrate` policy entry, with
  `atc integrate`'s record check as the gate (§ 3.4); (b) as (a), but the
  hook also reads the record on `main` (one `git show` per integrate call)
  and allows only a granted task, duplicating that check; (c) as (a), plus
  allow only from a subagent (the payload's `agent_type`), since reviewers
  run as subagents and writers as sessions, which a writer defeats by
  spawning one; (d) integration stays Owner-run for good. Recommendation:
  (a). The Owner's per-task grant stays the authority and stays out of an
  agent's reach; the hook adds no second copy of the rule, and the switch is
  a reviewed one-entry policy diff plus the governance change.
